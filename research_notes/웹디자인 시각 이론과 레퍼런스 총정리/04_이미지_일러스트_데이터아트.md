# 04. 이미지 · 일러스트 · 데이터 아트 — 프리미엄 웹 제품의 이미지 전략과 KOSAI 적용안

*조사일 2026-09-26. 범위: 프리미엄 금융·에디토리얼·제품 사이트의 이미지 전략(사진·일러스트·추상/생성 시각물·데이터 아트·이미지 처리 기법·차트·OG 카드·접근성/성능)과, "종이에 인쇄된 리서치 리포트" 방향(바탕 #f9f8f6 · 먹 #141414 · 헤어라인 · 카드 없음)을 가진 KOSAI가 무엇을 채택하고 무엇을 채택하지 말아야 하는지.*

*방법 메모: 웹 검색 15+23회, 원문 열람 약 40건. 조사 도중 세션의 웹 검색 예산이 소진되어 후반부는 이미 확보한 URL의 원문 열람만으로 진행했다. McKinsey "Year in visuals"·Communication Arts(Goldman Sachs)·X(트위터) 카드 규격·FT Origami 팔레트 페이지는 서버 오류(503/402/404)로 원문을 못 열었고, 그 항목은 검색 요약 수준에서만 인용하고 그렇게 표시했다. 한국어 "AI 티" 관련 문헌은 검색 예산 소진 전 확보하지 못해 공백으로 남겼다. 비용·수치 중 추정치는 "(추정)"으로 표시했다.*

## 1. 프리미엄 금융·리서치·제품 사이트는 실제로 무엇을 보여주나 — 유형 분류와 리서치 브랜드 적합도

### Takeaway
프리미엄으로 읽히는 사이트들은 "이미지가 많아서"가 아니라 **하나의 이미지 규율을 끝까지 지켜서** 프리미엄이 된다. 리서치·데이터 브랜드(Economist·FT·Bloomberg·Linear)는 차트·제품 화면·기술적 일러스트를 이미지로 쓰고, 소비자 금융 브랜드(Toss·카카오뱅크·Robinhood)는 캐릭터·3D·사진으로 친근함을 산다. KOSAI의 "인쇄된 리서치 리포트" 방향에 맞는 쪽은 명백히 전자다.

### Cited Findings

**에디토리얼(리서치형) — 차트가 곧 이미지**
- The Economist 비주얼 스타일가이드(v1.2, 2017-05-04)는 차트 자체를 표준화한 문서다. 웹 차트 표준 폭은 1단 290px·2단 595px이고, "Web charts are built at standard print widths and then exported at 179.22%"(인쇄 폭 332pt → 595px)로 인쇄 규격을 웹으로 옮긴다 — [The Economist visual styleguide (PDF)](https://sa.ipaa.org.au/wp-content/uploads/2026/02/Economist-CHARTstyleguide_20170505.pdf)

Emphasis should be on showing a clear overall message, rather than identifying values for every data point." 새 디자인의 변경 항목은 "White background · 24pt spacer between panels · No margins · Source text 75% black · New colour palette · New typeface" — [같은 PDF](https://sa.ipaa.org.au/wp-content/uploads/2026/02/Economist-CHARTstyleguide_20170505.pdf)

### Inferences
- 유형 분류와 KOSAI 적합도(조사자 판단):

| 유형 | 대표 | 프리미엄이 되는 조건 | 리서치 브랜드 적합 |
|---|---|---|---|
| 차트가 이미지 | Economist·FT·Bloomberg | 차트 규격이 서체 규격만큼 엄격 | **매우 높음** — KOSAI의 본질과 일치 |
| 제품 화면이 이미지 | Linear | 화면 자체가 아름답고 프레임이 절제 | 중간 — KOSAI는 "제품 화면"이 곧 리포트 지면이라 겹침 |
| 기술적 일러스트 | Robinhood | 그래프에서 파생된 언어, 재현·확장 쉬움 | 높음 — 단 선 굵기·팔레트 하나로 고정할 때만 |
| 의뢰 사진(시네마틱) | Mercury·Goldman | 스톡 배제·일관 그레이딩·풀블리드 | 낮음 — 비용·유지비, 종이 리포트 톤과 충돌 |
| 추상 그라디언트/3D | Stripe(2018~) | 당시엔 신선 | **낮음** — 2026년 현재 "AI 티"의 대표 신호(4절) |
| 캐릭터·3D 이모지 | Toss·카카오뱅크 | 방대한 시스템(3,600 글립)과 전담 인력 | 낮음 — 친근함은 리서치 신뢰와 반대 축 |
| 무이미지 | (네이버 금융 — 미검증) | 정보 밀도·표 조판 | 높음 — 단 "방치"가 아니라 "선택"으로 보이게 해야 함 |

- 공통점: 프리미엄 사례는 모두 **"스톡을 쓰지 않는다"**를 명시한다(Mercury "Commission, don't license", Goldman "replaces stock images with original photography", Linear "avoids stock photography, lifestyle imagery, and abstract illustration"). 즉 이미지의 유무보다 **출처의 고유성**이 프리미엄 신호다.
- Robinhood가 "복잡한 아트워크 → 재현 가능한 기술적 일러스트"로 옮긴 이유("easy to replicate and scale")는 2,682장을 자동 생성해야 하는 KOSAI에 그대로 적용된다. 손으로 그리는 자산은 규모가 커지는 순간 일관성이 깨진다.

- 네이버 금융의 "이미지 없음"은 과제 지문의 전제이며 이번 조사에서 원문으로 확인하지 못했다.

## 2. 데이터 아트 — 실제 데이터로 만드는 시각물, 종목별 자동 생성, OG 카드

### Takeaway
"데이터로 만든 그림"은 리서치 사이트가 가질 수 있는 **유일하게 정당한 장식**이다. 조건은 셋: 진짜 데이터(가격·거래량)에서 결정론적으로 나올 것, 작은 크기에서 글자처럼 읽힐 것(Tufte의 스파크라인), 그리고 색·효과를 최소로 둘 것. OG 카드는 1200×630의 **타이포그래피 카드**가 표준이며 빌드 시점에 전 페이지 생성이 가능하다(Satori/resvg 또는 Playwright).

### Cited Findings

**스파크라인·데이터 아트 원리**
- Tufte: 스파크라인은 "data-intense, design-simple, word-sized graphics"이며 "Avoid all data frames; the physical location of the numbers, words, and graphics enforces the implicit grid; that grid never needs to be expressed directly." 종횡비는 "lumpy" 프로파일(기울기 ~45°)을 목표로 하되 "use the maximum reasonable vertical space available under the word-like constraint, then adjust the horizontal stretch"; **금융 스파크라인은 통상 5:1** 비율; 색은 "modest, just strong enough to send the editorial or interpretative signal without masking or detracting"(빨강=최신/최고 값, 회색 밴드=정상 범위); 뮤추얼펀드 표 재설계는 데이터 면적 21%만 늘려 "an approximate look at 5,000 more numbers"를 얹었다 — [Edward Tufte, Sparkline theory and practice](https://www.edwardtufte.com/notebook/sparkline-theory-and-practice-edward-tufte/)
- 같은 글의 밀도 원칙: "500 sparklines on A3 size paper" 같은 공간적 인접이 "comparison, search, pattern-finding, exploration, replication, review"를 돕는다 — [같은 글](https://www.edwardtufte.com/notebook/sparkline-theory-and-practice-edward-tufte/)
- 데이터 아트 스튜디오 Visual Cinnamon은 DataViz와 DataArt를 구분해 작업하며(Google·Scientific American·NYT·UNESCO·Sony Music "Gold Record" 데이터 아트 등), 목적을 "make an impact, tell a story, evoke emotions"로 둔다 — [Visual Cinnamon](https://www.visualcinnamon.com/)
- 자동화된 데이터 아트의 산업 사례: Bloomberg Futures는 매주 자동 발행되면서 "4 graphic themes and 7 colour palettes" 안에서만 변주한다(1절 참조) — [illo](https://illo.tv/bloombergfutures)
- Stripe식 메시 그라디언트는 데이터가 아니라 노이즈(Simplex FBM)로 만든 장식이다 — [exzenter/gradient-stripe](https://github.com/exzenter/gradient-stripe)

**OG(소셜 공유) 이미지 — 규격과 생성 스택**
- 권장 크기 1200×630px; `@vercel/og`는 Satori + Resvg로 HTML/CSS → PNG; 지원 폰트 `ttf`·`otf`·`woff`뿐(파싱 속도는 ttf/otf 우선, **woff2 미지원**); 레이아웃은 `display:flex`와 CSS 일부만(grid 불가); 번들(JSX·CSS·폰트·이미지 포함) 최대 500KB; robots.txt에 OG 경로 `Allow` 권장 — [Vercel Docs, OG Image Generation](https://vercel.com/docs/og-image-generation)
- Satori: React Native와 같은 Flexbox 엔진; `z-index`·`calc()`·3D transform 미지원; 폰트는 ArrayBuffer/Buffer로 직접 공급해야 하며 CJK 등 누락 글리프는 `loadAdditionalAsset` 콜백으로 동적 로드; 이미지는 base64 data URI 권장; 이모지는 `graphemeImages`로 매핑; 기본 출력은 글자를 `<path>`로 임베드한 SVG(`embedFont:false`면 `<text>`); PNG 변환은 resvg 같은 외부 도구 — [vercel/satori](https://github.com/vercel/satori)
- Vercel의 성능 주장: Chromium+Puppeteer(50MB) 대비 "100x more lightweight"(500KB), P99 TTFB 4.96s → 0.99s(5배), Next.js Conf 티켓 10만 장 평균 800ms; 캐시 헤더 `public, immutable, no-transform, max-age=31536000`; "The engagement rate of Tweets that embed a card is 40% higher" — [Vercel Blog, Introducing OG Image Generation](https://vercel.com/blog/introducing-vercel-og-image-generation-fast-dynamic-social-card-images)
- GitHub의 OG 시스템: Node + Puppeteer로 템플릿 HTML을 스크린샷; 하루 약 200만 장, 평균 280ms, 요청의 40%가 캐시 히트; `waitUntil: networkIdle0` 대신 `domcontentloaded` + `document.fonts.ready` + 이미지 load 대기로 ~2.25s → ~600ms; 메모리 512MB → 1GB로 "reduction of almost 500ms"(512MB 미만에선 Chromium 병렬 처리가 꺼짐) — [GitHub Blog, A framework for building Open Graph images](https://github.blog/open-source/git/framework-building-open-graph-images/); 도입 취지는 "the author's face" 대신 리소스의 맥락 정보를 보여주는 것 — [GitHub Blog, Custom Open Graph Images](https://github.blog/news-insights/product-news/custom-open-graph-images-for-repositories/)
- Facebook/Meta 크롤러 요건: 최소 200×200, 고해상도 표시를 위해 "at least 1200 x 630", 큰 이미지 표시 하한 600×315, 비율 "as close to 1.91:1", 파일 8MB 이하, `og:image:width`·`og:image:height`를 넣으면 첫 공유 때도 비동기 처리 없이 즉시 렌더 — [Meta for Developers, Images in Link Shares](https://developers.facebook.com/docs/sharing/webmasters/images/)
- 빌드/워커 환경 레시피 예: satori(JSX→SVG) + sharp(SVG→JPEG, 품질 90 + mozjpeg), 1200×630, 폰트는 TTF를 버퍼로 로드, 이미지는 base64 data URL로 삽입 — [Trigger.dev, Generate OG Images using Satori](https://trigger.dev/docs/guides/examples/satori)
- Python 대안: Playwright는 `page.screenshot(path=..., full_page=True)`, 요소 단위 `page.locator(".header").screenshot(...)`, 버퍼 반환 `page.screenshot()`을 지원하며 "many parameters for image format, clip area, quality, etc."가 있다 — [Playwright Python, Screenshots](https://playwright.dev/python/docs/screenshots)

### Inferences
- **종목별 이미지는 "스파크라인 명판"으로 충분하다.** 1년(약 250 거래일) 종가를 5:1 비율의 SVG 한 줄로 그리고, 마지막 값 점 하나와 52주 고저 회색 밴드만 얹는다. 이건 Tufte의 규칙(프레임 없음·색 최소·정상 범위 밴드)을 그대로 따른 것이고, 데이터가 같으면 항상 같은 그림이 나오므로 "무작위 시드"가 필요 없다 — 결정론은 데이터 자체가 준다.
- **"김빠진(gimmicky) 데이터 아트"를 피하는 기준(조사자 정리):** (1) 값을 읽을 수 있어야 한다(축 없이도 마지막 값·기간 표기), (2) 한 종류의 마크만(선 또는 면, 섞지 않음), (3) 색은 잉크 1 + 강조 1 + 회색, (4) 애니메이션·글로우·그라디언트 없음, (5) 같은 규격을 2,682장에 예외 없이. Bloomberg Futures가 "4 테마 × 7 팔레트"로 변주를 **제한**한 것이 자동화 시각물의 핵심 교훈이다.
- **섹터 페이지의 이미지는 "스몰 멀티플 태피스트리"**가 어울린다: 섹터 구성 종목의 스파크라인을 격자로 깔면 Tufte가 말한 "500 sparklines on A3"의 웹판이 된다. 종목 수가 많으면 시총 상위 24~40개만 그리고 나머지는 숫자로 처리한다.
- **OG 카드는 타이포그래피 카드로 간다.** GitHub·Vercel 모두 "얼굴/사진 대신 맥락 정보"를 택했고, 프리미엄 신호는 정확한 정보 배치(종목명·티커·날짜·한 줄 결론·작은 스파크라인)와 브랜드 팔레트의 일관성에서 온다. 정적 사이트(GitHub Pages)라 런타임 함수가 없으므로 **빌드 시점 생성**이 답이다: Node Satori+resvg(폰트는 TTF/OTF, 한글 서브셋 필수 — 500KB 번들 제한은 서버리스 기준이라 로컬 빌드엔 해당 없음) 또는 Python Playwright 스크린샷(GitHub 방식; 러너 메모리 1GB 이상 확보). 2,682장 × 280~800ms ≈ 13~36분(추정)이므로 **변경된 종목만 재생성**하는 해시 캐시가 필요하다.
- 소셜 크롤러는 다크 모드가 없다. OG는 항상 라이트(종이 `#f9f8f6` · 먹 `#141414`) 한 벌만 만든다.

### Gaps
- X(트위터) `summary_large_image` 규격 페이지는 402로 열리지 않아 최소/최대 픽셀·용량 제한을 확인하지 못했다(통념상 2:1·5MB 이하이나 **미검증**). Meta 규격(1.91:1·8MB)만 확보했다.
- "Stripe Sessions 아트"는 검색에서 특정 프로젝트가 확인되지 않았다. NYT·Reuters 그래픽스·The Pudding의 데이터 아트 사례는 검색 예산 소진으로 원문을 확보하지 못했다.
- 결정론적 시드 기반 생성 아트(예: 티커 해시 → 패턴)에 대한 신뢰할 만한 사례·지침은 찾지 못했다. 위 추론은 Tufte·Bloomberg 사례에서 조사자가 도출한 것이다.

## 3. 사진을 쓴다면 — 방향, 조달, 비용, 클리셰

### Takeaway
프리미엄 사례들은 사진을 **의뢰하거나(Mercury·Goldman) 단일 피사체를 그래픽하게 찍는다(Robinhood)**. 스톡을 쓰는 순간 경쟁사와 같은 라이브러리를 공유하게 되고, "서울 야경·거래소 전광판·악수"는 그 자체로 카테고리 클리셰다. 비용은 국내 스톡이 장당 1,000원~수만 원, Getty RF 장당 $175~499, 구독 월 €145~195(10장)로 넓게 벌어지며, 진짜 비용은 라이선스가 아니라 "일관성을 유지하는 노동"이다.

- **클리셰 목록(조사자 판단, Robinhood·Mercury 원칙에서 역산):** 서울 야경/한강/롯데타워, 여의도 증권가 건물, 거래소 전광판·빨간 캔들 화면, 악수·정장 회의, 노트북 앞의 사람, 지폐·동전 더미, 상승 화살표 합성. Robinhood식 대안은 "해석에 열린 단일 피사체"(정물)이고, Mercury식 대안은 의뢰 촬영이다.
- 사진을 쓴다면 종이 팔레트에 맞추는 처리가 필수다: 흑백 또는 먹/종이 2색 듀오톤(5절 레시피), 가벼운 그레인, 전 사이트 동일 처리. 이렇게 하면 서로 다른 출처의 사진도 한 벌로 보인다.
- 비용 감각(추정): 랜딩·About에 필요한 3~5장이면 크라우드픽 확장 라이선스 기준 수만 원, 게티이미지뱅크 월 정액 39,000원 한 달이면 충분하다. 의뢰 촬영(Mercury식)은 국내 상업 촬영 하루 단가가 수백만 원대로 알려져 있으나 이번 조사에서 출처를 확보하지 못했다.

### Gaps
- 국내 스톡의 모델 릴리스·초상권 범위, 게티이미지뱅크 낱장 RF 가격(플랜 외)은 페이지에서 확인되지 않았다.
- "서울/시장/건물 사진이 클리셰"라는 직접적 문헌은 찾지 못했다. 위 목록은 조사자의 판단이다.

## 4. 일러스트 시스템과 "AI 티" 체크리스트

### Takeaway
유지 가능한 일러스트 시스템은 **규칙이 먼저**다(토스페이스: 기본 도형·시선 방향 통일·45° 각도·배경 두 가지에 다 맞는 단일 팔레트·모듈 조립). 반대로 "AI 티"는 규칙의 부재, 즉 학습 데이터의 평균값(Inter·인디고-보라 그라디언트·둥근 카드 3개·얇은 선 아이콘·광택 3D·손가락 오류·깨진 글자)이다. KOSAI가 일러스트를 쓴다면 잉크 한 색·선 굵기 하나의 기술적 도해에 한정하고, 생성형 3D는 쓰지 않는다.

### Cited Findings

**일러스트 시스템의 일관성 규칙**
- 토스페이스 설계 규칙: "기본 도형을 바탕으로 가장 단순한 형태의 솔리드 타입", 방향 있는 이모지는 "전부 왼쪽에서 오른쪽", 각도 있는 사물은 "모두 오른쪽 45도", "하나의 컬러 팔레트만 사용해서 흰 배경과 검은 배경 둘 다"; 제작은 기본형 얼굴·상반신·전신을 만든 뒤 성별·피부색·머리카락·옷을 조립하는 모듈 방식; 결과적으로 "토스 그래픽 디자인의 원석"이 되어 "맨 땅부터 시작하지 않을 수 있게" 됐다 — [Toss Tech](https://toss.tech/article/22205)
- 토스 3D 그래픽을 Adobe Firefly로 재현한 실험: 프롬프트 + 스타일 참조 이미지(팔레트 역할) 조합이면 "정적인 그래픽만 보았을 때 몇 개는 꽤 그럴듯"했지만, 원본 대비 "손가락 표현, 미세한 질감, 정밀한 형태 묘사"에서 한계가 드러났고, 저자는 "브랜드만의 독특한 그래픽 시스템이 더욱 중요해질 것"으로 결론 — [Surfit, 토스의 3D 그래픽을 생성형 AI로 대체할 수 있을까?](https://www.surfit.io/mag/adobe-firefly-creating-toss-graphic/)
- Robinhood: 기술적 일러스트는 "easy to replicate and scale, allowing Robinhood to set an expert tone in touchpoints large and small" — [PORTO ROCHA](https://www.portorocha.com/robinhood)
- Linear: 일러스트·사진·추상 배경 대신 제품 화면; "No atmospheric gradients, no spotlight cards" — [DESIGN.md 티어다운](https://github.com/voltagent/awesome-design-md/blob/main/design-md/linear.app/DESIGN.md)

**"AI 티"의 신호(tells)**
- 웹 디자인 층위의 신호: Inter 서체("The safest possible answer"), 인디고→보라 그라디언트(Tailwind `indigo-500` 기본값에서 유래), "Three rounded cards in a row"(Tailwind 그리드 튜토리얼 레이아웃), 카드의 소프트 섀도, "Thin, interchangeable line icons that could illustrate any product", 어디에나 둥근 모서리, 다크 히어로 + 그라디언트 배경, "Get Started" 그라디언트 버튼, "Build faster. Ship smarter." 같은 무게 없는 카피; 원인은 모델이 "the statistical average"를 내기 때문이며 해법은 **constraint** — [925 Studios, AI Slop Design Tells](https://www.925studios.co/blog/ai-slop-design-tells)
- 보라 그라디언트의 기원: Tailwind 제작자 Adam Wathan이 "formally apologize for making every button in Tailwind UI bg-indigo-500 five years ago, leading to every AI generated UI on earth also being indigo"라고 농담했다는 인용; 2015–2020년 "모던" 웹(Instagram 리브랜드·Stripe/Twitch식 테크 브랜딩)의 보라 그라디언트가 학습 데이터의 중심값이 됐다 — [prg.sh](https://prg.sh/ramblings/Why-Your-AI-Keeps-Building-the-Same-Purple-Gradient-Website); [Jack Pearce](https://www.jackpearce.co.uk/notes/purple-gradient-ai-aesthetics/); [Kai Ni (Medium)](https://medium.com/@kai.ni/design-observation-why-do-ai-generated-websites-always-favour-blue-purple-gradients-ea91bf038d4c)
- 이미지 층위의 신호: 해부학 오류(끊어진 손가락·잘못된 뼈대·여분의 손가락), 글자 왜곡("Coca-Coola" 등 뒤틀린 배경 텍스트), 초현실적 비일관성, "incredibly banal, realistic style", 스트리밍 썸네일의 "smudged faces"; "AI slop"의 세 가지 원형 속성은 superficial competence · asymmetric effort · mass producibility — [Wikipedia, AI slop](https://en.wikipedia.org/wiki/AI_slop)

### Inferences
- **KOSAI용 "AI 티" 점검표**(위 출처를 종합해 조사자가 정리; 발행 전 모든 시각 자산에 적용):
  1. 색: 인디고·보라·틸(teal) 그라디언트, 네온 글로우, 무지개 팔레트 → 탈락.
  2. 형태: 광택 3D 블롭·유리구슬·떠 있는 아이소메트릭 도시·추상 "AI 뇌/회로" → 탈락.
  3. 질감: 플라스틱 광택, 과도한 피사계 심도, 균일한 스튜디오 조명 → 탈락. (허용: 종이 질감, 미세 그레인, 잉크 선)
  4. 인물: 손·치아·귀·문자 왜곡 여부를 100% 배율로 확인. 인물 자체를 피하는 편이 안전.
  5. 글자: 이미지 안의 글자는 반드시 실제 폰트로 조판(생성 모델이 만든 글자 금지).
  6. 레이아웃: 둥근 카드 3열, 카드 그림자, 다크 히어로 그라디언트 → KOSAI 헌장(카드 없음·헤어라인)과도 충돌.
  7. 카피: "Build faster"류 무게 없는 문장 → 숫자·고유명사가 들어간 문장으로.
  8. 출처: 생성형 이미지는 저작권·초상권 판단이 어렵다(surfit 저자도 "저작권 윤리 문제"를 지적). 리서치 사이트의 신뢰 자산과 상충.
- **일러스트를 쓴다면 "기술적 도해(technical illustration)" 한 종류만.** 규칙 초안: 선 1.5px(24px 아이콘 기준) 또는 1px 헤어라인, 먹 `#141414` 단색(다크는 토큰 반전), 채움 없음 또는 10% 워시, 45° 등각 규칙(토스페이스식 각도 통일), 시선/화살표 방향은 왼→오. 이 규칙은 곧 차트 마크 규칙(6절)과 같아서 별도 자산 없이 SVG 생성기 하나로 관리된다.
- 토스페이스는 TTF/SVG로 공개돼 있지만 KOSAI가 쓰면 곧바로 "토스 같다"가 된다. 참고는 규칙만.

### Gaps
- 한국어로 된 "AI 티 나는 디자인" 문헌은 검색 예산 소진으로 확보하지 못했다(영문 자료로 대체).
- 아이콘 시스템의 유지비(제작 시간·비용)에 대한 정량 자료는 찾지 못했다. 토스페이스 3,600 글립은 전담 조직 규모의 사례이고 소규모 팀의 기준치는 아니다.

## 5. 이미지 처리 기법 — 듀오톤·그레인·아트디렉션·포맷·지연 로딩·다크 모드

### Takeaway
종이 팔레트에 이미지를 맞추는 기술(듀오톤·그레인)은 CSS/SVG만으로 되고, 포맷은 AVIF(품질 45~60) + WebP(70~82) + 폴백이 표준이며, 다크 모드는 **콘텐츠 이미지를 어둡게 필터링하지 말고** 테마별 소스를 주거나 SVG를 토큰 색으로 그리는 것이 접근성 관점의 정답이다. KOSAI처럼 사이트 자체 토글(`data-theme`)이 있으면 `prefers-color-scheme` 기반 `<picture>`는 토글을 못 따라간다는 점이 중요하다.

### Cited Findings

**듀오톤·그레인**
- CSS 듀오톤: 이미지에 `filter: grayscale(100%) sepia(100%)`, 위에 색 오버레이 레이어 `mix-blend-mode: color`, 이미지 자체엔 `mix-blend-mode: screen` — [DEV, How to apply a duotone effect with CSS](https://dev.to/itsjp/how-to-apply-a-duotone-effect-to-images-with-css-5gj2)
- 그레인: SVG `<feTurbulence type='fractalNoise' baseFrequency='0.65' numOctaves='3' stitchTiles='stitch'/>`를 배경으로 깔고 `filter: contrast(170%) brightness(1000%)`로 회색을 흑백으로 밀어낸 뒤 `mix-blend-mode: multiply` 등으로 그라디언트와 합성; Blink와 WebKit의 `mix-blend-mode` 구현이 조금 다르고, 극단적 contrast/brightness는 성능 우려가 있다는 지적 — [CSS-Tricks, Grainy Gradients](https://css-tricks.com/grainy-gradients/)

**포맷·품질**
- sharp 기본값: `.avif()` quality **50**, effort 4(0–9), chromaSubsampling `4:4:4`; `.webp()` quality **80**, effort 4(0–6); `.jpeg()` quality 80, mozjpeg false, progressive false; `.png()` compressionLevel 6 — [sharp API, Output](https://sharp.pixelplumbing.com/api-output)
- AVIF 절감(Imgix 자료 인용): JPEG 대비 60%, WebP 대비 35%; 애니메이션 AVIF 시작점 CRF 23(0–63); 인코딩은 "the slowest of all encoders"(멀티스레드로 개선) — [web.dev, Deploying AVIF](https://web.dev/articles/avif-updates-2023)
- AVIF 브라우저: Chrome/Opera 2020, Firefox 2021, Safari 2022부터; 미지원 브라우저는 "won't be able to parse that image file at all"이므로 폴백 필수, "You shouldn't sacrifice a more resilient web for the sake of a more performant one" — [web.dev, Learn Images: AVIF](https://web.dev/learn/images/avif)
- (2차 자료·블로그 권고치) 콘텐츠 이미지 WebP 76–82 / AVIF 48–58, 일반 범위 WebP 70–82 / AVIF 45–60; "quality numbers are starting points, not universal constants"(인코더마다 척도가 다름) — [LessMB](https://lessmb.com/blog/best-image-compression-settings-for-web-publishing)
- `<picture>`는 "breakpoint-based art direction entirely in HTML"을 가능하게 하며 크롭·구도를 브레이크포인트마다 바꿀 수 있다 — [Smashing Magazine, Responsive Images Done Right](https://www.smashingmagazine.com/2014/05/responsive-images-done-right-guide-picture-srcset/)

**지연 로딩·플레이스홀더**
- `loading="lazy"`: Chrome의 뷰포트 거리 임계값은 빠른 4G 1,250px, 3G 이하 2,500px; 4G에서 "97.5% of lazy-loaded images were fully loaded within 10ms of becoming visible"; "Don't lazy-load images that are likely to be in-viewport when the page loads, especially LCP images"; `width`·`height`가 없으면 0×0으로 취급돼 한꺼번에 로드될 수 있음; Chrome 77+, Firefox 121+, Safari 16.4+ — [web.dev, Browser-level image lazy loading](https://web.dev/articles/browser-level-image-lazy-loading)
- 플레이스홀더 비교: 16×16 WebP 데이터 URI ≈ 100–200바이트(브라우저 네이티브 디코드), BlurHash 20–30자(JS 디코더 필요, base64 변환 시 "about 10 times larger"), ThumbHash(알파·종횡비 지원, JS 필요); Mux는 "increased quality and avoiding the requirement of JavaScript"를 이유로 약 150바이트 더 큰 LQIP를 선택 — [Mux, A clear look at blurry image placeholders](https://www.mux.com/blog/blurry-image-placeholders-on-the-web)
- ThumbHash는 BlurHash 대비 "Encodes more detail in the same space", "Also encodes the aspect ratio", "Gives more accurate colors", "Supports images with alpha"; 대신 파라미터를 조절할 수 없음; JS·Rust·Swift·Java 공식 구현 — [evanw/thumbhash](https://github.com/evanw/thumbhash)

**다크 모드**
- `<picture><source srcset="dark.jpg" media="(prefers-color-scheme: dark)"><img src="light.jpg" alt="…"></picture>`로 테마별 소스 제공; 라이트 이미지의 투명도를 낮추는 방식은 "Dimming all content images like that is not an inclusive design strategy"(저대비·호버 의존·이미지 속 글자 인지 저하); `<source>`에 `alt`가 없고 소스 전환에 뷰 트랜지션이 없다는 한계; 일러스트는 SVG 내부 미디어 쿼리로 처리 가능 — [Sara Soueidan, Rethinking Dark Mode Image Strategies](https://www.sarasoueidan.com/newsletter/issue-2025-10-31/)
- web.dev: 사진은 `grayscale(50%)` 정도의 채도 저하, 아이콘은 `invert(100%)`, 인라인 SVG는 `currentColor`로 상속(`<use href>`에도 적용); 순백 대신 `rgb(250, 250, 250)`로 "glowing and bleeding" 방지 — [web.dev, prefers-color-scheme](https://web.dev/articles/prefers-color-scheme)

### Inferences
- **KOSAI의 시각물은 원칙적으로 인라인 SVG + CSS 토큰**으로 그린다. 그러면 (a) 다크 모드가 `currentColor`/`var(--fg-1)`로 자동 해결되고(사이트 토글과 OS 설정 불일치 문제 없음), (b) 요청 수·용량이 0에 가깝고, (c) 듀오톤·그레인 같은 후처리가 필요 없다. 래스터는 OG 카드(크롤러용)와 랜딩/About의 사진 한두 장뿐이다.
- 래스터를 쓸 때의 규격(조사자 권고, 위 출처 기반): `<picture>`로 AVIF(sharp quality 50~58, effort 6~9 — 빌드 시 1회이므로 느려도 됨, `4:2:0` 서브샘플링 검토) → WebP(quality 78~82) → JPEG(quality 80, mozjpeg) 순; 폭 `640/960/1440/1920` 4단계; 항상 `width`·`height`; 접힘 아래만 `loading="lazy"` + `decoding="async"`; 플레이스홀더는 JS 없는 16×16 WebP 데이터 URI(≈150B) 또는 배경색 한 칸.
- 사진의 종이 팔레트 정합: 빌드 시 sharp/Pillow로 흑백화 후 먹 `#141414`→종이 `#f9f8f6` 2색 매핑(듀오톤)을 **파일에 구워** 넣는 편이 CSS 블렌드보다 안전하다(브라우저별 `mix-blend-mode` 차이 회피, 다크 모드는 별도 파일 또는 SVG 마스크). 그레인은 CSS `feTurbulence` 오버레이 대신 파일에 미세하게 넣는다(contrast(170%) brightness(1000%)식 트릭은 성능·색역 손실).
- 다크 모드 사진은 `filter: brightness()`로 뭉개지 말고, (1) SVG/토큰으로 그렸다면 자동, (2) 래스터라면 다크 전용 파일을 두고 사이트 토글(`data-theme`)에 따라 `src`를 바꾸는 작은 스크립트 — `prefers-color-scheme` `<picture>`만으로는 KOSAI 토글을 못 따른다.

### Gaps
- Chrome 외 브라우저(Safari·Firefox)의 lazy-load 임계값은 확인하지 못했다.
- 국내 인코더 실무값(예: 네이버·카카오의 AVIF 품질 기준)은 찾지 못했다. 품질 범위는 블로그 권고치(2차 자료)임을 유의.
- Safari에서 `mix-blend-mode`·`feTurbulence` 성능 수치는 확보하지 못했다.

## 6. 차트가 곧 이미지 — 작은 차트를 아름답게, 그리고 이미지를 대체할 수 있는가

### Takeaway
Economist·FT·Tufte의 결론은 같다: 차트의 아름다움은 **뺄셈**(프레임·격자·눈금·범례·이중축 제거)과 **위계**(제목 → 부제(단위·기간) → 데이터 → 출처)에서 온다. 리서치 사이트에서 규격이 엄격한 작은 차트는 이미지를 충분히 대체하며, 실제로 그 자체가 브랜드 이미지가 된다(Economist의 빨간 탭, FT의 차트 언어).

### Cited Findings
- Economist 스타일가이드의 규격: 표준 인쇄 차트 제목 Econ Sans Bold 9.5/11pt, 부제 Econ Sans Cnd Regular 8/9.5, 축 라벨 Cnd Light 7.5/9 ~ 7/7.5, 출처 Cnd Light 6.5pt 75% 검정; 선 두께 표기 1pt / 0.5pt / 0.4pt(도면상 데이터선·축·격자로 읽힘 — 추정); "Where possible, put units and date information on a second line at smaller font size"; 각주 기호 순서 `* † ‡ § ** †† ‡‡ §§` — [Economist visual styleguide (PDF)](https://sa.ipaa.org.au/wp-content/uploads/2026/02/Economist-CHARTstyleguide_20170505.pdf)
- 같은 문서의 색 규칙: 색 순서 1–6 고정, "Use grey for 'other' / 'dont know' etc", "Where categories are chronological, use light-to-dark scale", "If categories form meaningful groups, use colour to reinforce that", "Differentiate positive/negative values by colour only where there is a meaningful difference i.e. imports / exports", "You may need to swap in other colours for charts with more than 4 categories" — [같은 PDF, pp.13–16](https://sa.ipaa.org.au/wp-content/uploads/2026/02/Economist-CHARTstyleguide_20170505.pdf)
- 같은 문서의 이중축 경고: "Double scales can be good at showing correlations and are economical with space. But they can also be confusing/misleading." 피할 것: "Avoid breaking the scales without good reason", "If you are plotting above and below a zero line make the zero lines align", "Avoid mixing disparate measures to force visual correlation"; 안 되면 "try splitting the chart into panels or indexing the variables" — [같은 PDF, p.21](https://sa.ipaa.org.au/wp-content/uploads/2026/02/Economist-CHARTstyleguide_20170505.pdf)
- Datawrapper 선 차트 지침: "Use colors, line width and line dashes to make your most important values stick out", 덜 중요한 선은 회색; "Consider turning off automatic labeling and place the labels yourself"(라벨 색 = 선 색); "Line charts have the big advantage that they don't need to start from zero" 단 0에 가까우면 0 기준선 추가; "Consider using annotations and highlight ranges to add explanations" — [Datawrapper, What to consider when creating line charts](https://www.datawrapper.de/blog/line-charts)
- Tufte: 스파크라인은 "data-ink ratio = 1.0", 프레임·눈금·비데이터 요소 없음, 금융은 5:1 비율(2절) — [Tufte](https://www.edwardtufte.com/notebook/sparkline-theory-and-practice-edward-tufte/)
- FT Visual Vocabulary: 목적별 차트 선택 포스터, 뉴스룸 전체 교육의 핵심 — [Talking Biz News](https://talkingbiznews.com/they-talk-biz-news/graphics-and-data-visualization-at-the-financial-times/); [chart-doctor 저장소](https://github.com/Financial-Times/chart-doctor)
- (내부 참조 — URL 없음) 이 환경의 dataviz 스킬 `references/marks-and-anatomy.md`의 고정 마크 규격: 선 **2px** round join/cap, 마커 **≥8px**(r≥4), 면 채움은 계열색 **~10% 불투명도**, 격자·축은 표면에서 한 단계 벗어난 회색 **1px 헤어라인 실선(점선 금지)**, 겹치는 마크는 표면색 2px 링, 단일 계열은 범례 없음, 스탯 타일의 스파크라인은 "12-point sparkline in the de-emphasis hue, current period in the accent", 글자는 절대 데이터 색을 입지 않음.

### Inferences
- **KOSAI 소형 차트 규격 초안**(Economist·Tufte·Datawrapper·내부 규격 종합): 선 1.5px(스파크라인) / 2px(본문 차트), 마지막 값 점 r=3~4px + 표면색 링 2px, 격자 없음 또는 헤어라인 1px 실선 최대 3줄, y축은 0 강제 없음(가격)·비율은 0 포함, 색은 먹 1 + 강조 1(헌장 2장의 강조색 결정을 따름) + 회색 1, 4개 선 초과 시 스몰 멀티플, 이중축 금지, 범례 대신 선 끝 직접 라벨, 제목(문장형) → 부제(단위·기간, 작은 글자) → 출처 75% 먹. 이렇게 하면 종목 페이지의 차트 셋(가격·수급·재무)이 서로 다른 라이브러리 기본값처럼 보이지 않는다.
- **"아름다운 차트가 이미지를 대체할 수 있는가"에 대한 답은 리서치 사이트에 한해 "그렇다"**다. Economist는 리더 블록에서 사진 대신 단순화한 차트를 쓰고, Bloomberg Futures는 차트 애니메이션만으로 주간 영상을 만들며, Tufte는 표에 스파크라인을 넣어 "5,000 numbers"를 더했다. 대체가 실패하는 경우는 차트가 라이브러리 기본 스타일(격자·범례 박스·툴팁 그림자)로 남아 있을 때다.
- Economist의 "웹 차트는 인쇄 폭으로 만들고 179.22%로 내보낸다"는 방식은 KOSAI의 "인쇄된 리포트" 은유와 직접 통한다: 차트를 **인쇄물 규격(pt)으로 설계하고 px로 환산**하면 화면 차트가 종이 차트의 밀도를 얻는다.

### Gaps
- FT의 차트 스타일 수치(선 두께·격자·팔레트 HEX)는 원문 확보에 실패했다. Alan Smith의 『How Charts Work』는 존재만 확인했다 — [Goodreads](https://www.goodreads.com/book/show/63127668-how-charts-work).
- Economist PDF의 "1pt / 0.5pt / 0.4pt"가 각각 어느 요소의 두께인지는 도면 레이아웃에서 추정한 것이다.
- Bloomberg 토큰은 제3자 재구성(shadcn.io)이라 1차 자료가 아니다.

## 7. 접근성과 성능 — alt 텍스트, LCP, 이미지 CDN vs 정적

### Takeaway
장식 이미지는 `alt=""`, 정보 이미지는 짧은 설명, 차트 같은 복잡한 이미지는 **정보를 페이지의 다른 곳(표·본문)에** 둔다는 WAI 결정 트리가 기준이다. 성능은 "LCP 요소 하나에만 `fetchpriority="high"`, 접힘 아래만 lazy"가 핵심이고, 빌드 시점에 변형을 미리 만드는 정적 사이트에는 이미지 CDN이 필수가 아니다.

### Cited Findings
- WAI alt 결정 트리: 이미지에 글자가 있고 그 글자가 근처에 실제 텍스트로도 있으면 "Use an empty alt attribute"; 링크/버튼 안이면 "communicate the destination of the link or action taken"; 의미가 있는 단순 그래픽은 "a brief description of the image in a way that conveys that meaning"; **그래프·복잡한 정보는 "Include the information contained in the image elsewhere on the page"**; 근처 텍스트와 중복이면 빈 alt; 순수 장식이면 빈 alt — [W3C WAI, An alt Decision Tree](https://www.w3.org/WAI/tutorials/images/decision-tree/)
- Fetch Priority: 뷰포트 안 이미지도 처음엔 "Low"로 시작해 레이아웃 후 "High"로 올라가며 이 지연이 LCP를 늦춘다; Chrome 117부터 첫 5개 큰 이미지(>10,000px²)는 "Medium"; Google Flights는 히어로에 `fetchpriority="high"`로 LCP 2.6s → 1.9s; 비핵심 캐러셀에 `low`를 준 Oodle은 로드 2초 단축; CSS 배경 LCP는 preload + `fetchpriority="high"`; 대상은 "the single LCP image"와 소수의 핵심 자원만 — [web.dev, Fetch Priority API](https://web.dev/articles/fetch-priority)
- lazy loading 임계값·`width/height` 필수·LCP 이미지 lazy 금지(5절) — [web.dev](https://web.dev/articles/browser-level-image-lazy-loading)
- 이미지 CDN: "40–80% savings in image file size", URL 파라미터로 크기·포맷·품질 변환, 클라이언트 힌트/UA/Save-Data로 포맷 자동 선택; 대부분 무료 티어·사용량 과금, 셀프 호스팅(Thumbor 등)은 "sites with engineering staff who are comfortable maintaining their own infrastructure"에 적합 — [web.dev, Image CDNs](https://web.dev/articles/image-cdns)
- OG 이미지 크기 메타(`og:image:width/height`)로 첫 공유 시 즉시 렌더(2절) — [Meta](https://developers.facebook.com/docs/sharing/webmasters/images/)

### Inferences
- KOSAI의 스파크라인·차트 SVG는 **`role="img"` + 한 줄 `aria-label`(예: "삼성전자 1년 종가 추이, 52주 최저 대비 +18%")**로 두고, 값은 이미 표·본문에 있으므로 WAI의 "정보를 다른 곳에" 조건을 자연스럽게 만족한다. 순수 장식(섹터 태피스트리의 배경 등)은 `aria-hidden="true"`.
- 정적 GitHub Pages라면 이미지 CDN보다 **빌드 시 변형 생성**이 맞다: 사진이 손에 꼽을 만큼 적고, 나머지는 인라인 SVG라 CDN이 절감할 바이트가 없다. OG PNG 2,682장은 정적 파일로 두고 파일명에 내용 해시를 넣어 캐시한다.
- 히어로 이미지가 없으면 LCP 요소는 제목 텍스트가 된다 — 이때 진짜 병목은 이미지가 아니라 **웹폰트**다(헌장의 글꼴 CDN 결정과 연동). 이미지 전략상 "히어로 이미지 없음"은 LCP에 유리하다.

### Gaps
- 한국 접근성 지침(KWCAG)의 이미지 대체텍스트 조항은 검색 예산 소진으로 확인하지 못했다(WAI 기준으로 대체).
- 웹폰트가 LCP에 미치는 정량 자료는 이번 범위에서 수집하지 않았다(다른 장의 몫).

## KOSAI 적용 제안 — 우선순위 12개 (제작 레시피 · 하지 말 것)

*전제: 바탕 `#f9f8f6` · 먹 `#141414` · 헤어라인 · 카드 없음. 강조색은 헌장 2장에서 사장이 정하기 전엔 미정이며 아래는 "강조 1색"으로만 쓴다. 모든 시각물은 Python 빌드 스크립트(`scripts/stock_page.py`·`build_stock_pages.py`·아침 워크플로)에서 자동 생성되는 것을 기준으로 썼다.*

### 1. 기본 방침 — "이미지 없음"을 방치가 아니라 결정으로 만든다 (최우선)
- **왜**: 프리미엄 리서치 사례(Economist·FT·Bloomberg·Linear)는 사진·일러스트 대신 차트·제품 화면을 쓰고, 스톡을 명시적으로 배제한다(1절). "AI 티"의 대부분은 장식(그라디언트·3D·카드)에서 나온다(4절).
- **레시피**: 종목·섹터·브리핑 페이지의 시각 요소를 셋으로 한정 — (a) 규격 차트(6절 규격), (b) 데이터 명판 스파크라인(제안 2), (c) 타이포그래피(큰 숫자·문장형 제목). 랜딩을 제외한 어떤 페이지에도 래스터 이미지를 두지 않는다. `check_all.sh`에 "루트·staging HTML에 `<img src=*.jpg|png|webp>`가 있으면 실패" 검사를 추가한다(OG 메타와 `preview/`는 제외).
- **하지 말 것**: 스톡 사진, 서울 야경/전광판/악수, 히어로 그라디언트, 3D 오브젝트, "빈 곳을 채우는" 아이콘.

### 2. 종목별 "데이터 명판" — 1년 종가 스파크라인 SVG (2,682장 자동)
- **왜**: Tufte의 금융 스파크라인(5:1, 프레임 없음, 색 최소, 정상 범위 밴드)은 검증된 형식이고, 데이터에서 결정론적으로 나오므로 시드가 필요 없다(2절). 종목마다 다른 유일한 이미지가 되면서도 "그림"이 아니라 "정보"다.
- **레시피**: `scripts/stock_page.py`에 `sparkline_svg(closes, w=300, h=60)`를 둔다. 인라인 `<svg viewBox="0 0 300 60" role="img" aria-label="…">`; 경로 `stroke="currentColor" stroke-width="1.5" fill="none" stroke-linejoin="round" stroke-linecap="round"`; 52주 고저 밴드는 `fill="currentColor" fill-opacity=".06"`; 마지막 점 `r="3.5"` 강조색 + 표면색 링 2px; 축·격자·범례 없음; 오른쪽에 마지막 값·기간 텍스트는 HTML로. 데이터가 60일 미만(신규 상장)이면 그리지 않고 "리포트 준비 중" 등급 규칙을 따른다. 다크 모드는 `currentColor`가 자동 처리. 검사: 같은 입력이면 바이트 단위로 같은 SVG(스냅샷 테스트, `same-paragraphs.test.mjs`와 같은 방식).
- **하지 말 것**: 그라디언트 면 채움, 글로우, 애니메이션, 등락에 따라 선 색 전체를 빨강/파랑으로 바꾸기(Economist: 의미 있는 차이일 때만 색), 종목마다 다른 비율.

### 3. OG 카드 전 페이지 자동 생성 — 1200×630 타이포그래피 카드
- **왜**: 공유 카드는 사이트 밖에서 보이는 유일한 "이미지"다. GitHub·Vercel은 얼굴/사진 대신 맥락 정보 카드를 택했고, 카드가 있는 트윗의 참여율이 40% 높다는 Vercel의 주장이 있다(2절).
- **레시피**: 종이 `#f9f8f6` 배경, 먹 `#141414` 글자, 좌상단 "KOSAI 리서치 · 날짜", 중앙 종목명(큰 세리프/산세리프는 헌장 결정에 따름) + 티커·시장, 하단 한 줄 결론과 제안 2의 스파크라인(먹 1.5px, 이미지 폭의 60%). 생성은 둘 중 하나: (A) Node `satori` + `@resvg/resvg-js` — 폰트는 **TTF/OTF**(woff2 불가), 한글 서브셋 폰트를 Buffer로 공급, 누락 글리프는 `loadAdditionalAsset`; (B) Python Playwright로 템플릿 HTML을 `page.screenshot()` — GitHub 방식(러너 메모리 ≥1GB, `document.fonts.ready` 대기). 출력 PNG(또는 JPEG q90 mozjpeg) ≤ 300KB(추정 목표), 파일명 `og/{ticker}-{contenthash}.png`, `<meta property="og:image">` + `og:image:width/height` 명시, robots에 `Allow: /og/`. 변경된 종목만 재생성(해시 캐시) — 2,682장 전량은 13~36분(추정)이라 아침 워크플로에 넣지 말고 별도 잡으로.
- **하지 말 것**: 기업 로고 삽입(상표), 이모지, 사진, 다크 버전(크롤러엔 테마가 없다), 카드 안 글자를 이미지 생성 모델로 만들기.

### 4. 섹터 페이지 — 스파크라인 태피스트리(스몰 멀티플)
- **왜**: Tufte의 "500 sparklines on A3"처럼 인접 배열이 비교·탐색을 돕고(2절), Economist 패널 차트는 24pt 간격·흰 배경만으로 판을 만든다(1절). 섹터의 "얼굴"이 데이터 자체가 된다.
- **레시피**: 시총 상위 24~40 종목의 스파크라인(제안 2와 같은 함수, `w=140 h=28`)을 CSS grid(6열 데스크톱·3열 휴대폰, 간격 24px)로 배열, 각 칸 아래 종목명·등락 텍스트. 헤어라인 구분선만, 카드 없음. 전체를 `<section aria-labelledby>`로 묶고 개별 SVG는 `aria-hidden`, 값은 아래 표에.
- **하지 말 것**: 히트맵 무지개, 트리맵 3D, 종목별 색 부여, 호버 애니메이션 남발.

### 5. 차트 규격서 하나로 통일(차트 독트린)
- **왜**: Economist·FT·Tufte·Datawrapper의 공통 규칙(6절). 라이브러리 기본 스타일이 남아 있으면 "차트가 이미지를 대체"하지 못한다.
- **레시피**: `docs/design/chart-spec.md`에 고정값 — 선 2px round, 마커 ≥8px + 표면색 링 2px, 격자 없음 또는 헤어라인 1px 실선 ≤3, 축은 표면에서 한 단계 벗어난 회색, 색은 먹·강조 1·회색(기타/미응답은 회색), 4개 선 초과 시 스몰 멀티플, **이중축 금지**(패널 분할 또는 지수화), 범례 대신 선 끝 직접 라벨, 제목(문장) → 부제(단위·기간, 작은 글자) → 출처 75% 먹, 각주 기호 `* † ‡ §`, 글자는 데이터 색을 입지 않음. 인쇄 규격(pt)으로 설계하고 px로 환산(Economist 방식). 브리핑·종목·섹터의 모든 차트 생성 코드가 이 파일의 상수를 import한다.
- **하지 말 것**: 점선 격자, 범례 박스, 그림자 툴팁, 상승/하락 외의 빨강·초록 사용, 0에서 시작하지 않는 막대.

### 6. 홈(그리고 마지막에 랜딩)의 단 하나의 시각물 — "시장 한 장" 데이터 아트
- **왜**: 데이터 아트는 리서치 사이트가 가질 수 있는 유일하게 정당한 장식이며(Visual Cinnamon·Bloomberg Futures), 노이즈 그라디언트(Stripe식)는 2026년엔 "AI 티"다(2·4절).
- **레시피**: 아침 워크플로가 매일 다시 그리는 정적 SVG 한 장 — 예: 코스피200 종목의 1년 지수화 경로를 먹 0.5px 12% 불투명도로 겹치고, 지수(코스피)만 강조색 1.5px, 오늘 날짜에 세로 헤어라인. 또는 섹터별 폭 = 시총, 높이 = 1년 수익률의 막대 띠. 색 셋(먹·강조·회색), 애니메이션 없음, `prefers-reduced-motion`과 무관하게 정적. 파일 크기 ≤ 150KB(추정, 경로 단순화 `round(1)`), 인라인이 아니라 `<img src=*.svg>`로 캐시(다크 모드는 SVG 내부 `@media`+사이트 토글용 두 벌 또는 `currentColor` 인라인).
- **하지 말 것**: WebGL 메시 그라디언트, 파티클, 지구본, 랜덤 시드 패턴, 보라/틸.

### 7. 다크 모드 이미지 규칙 — 필터 금지, 토큰으로 그린다
- **왜**: 콘텐츠 이미지를 어둡게 필터링하는 것은 "not an inclusive design strategy"(Soueidan), 사진 반전은 사용자가 싫어한다(web.dev)(5절). KOSAI는 사이트 자체 토글(`data-theme`)이 있어 `prefers-color-scheme` `<picture>`가 토글을 못 따른다.
- **레시피**: 모든 SVG는 `currentColor`·`var(--fg-1)`·`var(--bg-1)`만 사용(하드코딩 HEX 금지 — 검사 추가). 래스터가 불가피하면 `light`/`dark` 두 파일을 만들고 `auth-state`처럼 작은 스크립트가 `data-theme`에 따라 `src`를 교체, 초기 렌더는 `<picture>`의 `prefers-color-scheme`로. 다크 표면의 순백 대신 `rgb(250,250,250)`급 밝기 사용.
- **하지 말 것**: `img { filter: brightness(.8) }` 일괄 적용, 사진 `invert()`, 다크 전용 파일 없이 라이트 사진 투명도 낮추기.

### 8. 사진은 랜딩·About에만, 한 페이지 한 장, 한 가지 처리
- **왜**: 프리미엄 사례는 사진을 브랜드 페이지에서만 쓰고 의뢰하거나 단일 피사체로 찍는다(Mercury·Robinhood·Goldman)(3절). 데이터 페이지에 사진을 넣으면 반복과 클리셰가 불가피하다.
- **레시피**: (1) 피사체는 "해석에 열린 정물"(종이·잉크·자·연필·인쇄물 등 리포트 은유) — 인물·건물·화면 금지; (2) 조달은 우선 의뢰 촬영, 차선은 크라우드픽 확장 라이선스(JPG 5,000원) 또는 게티이미지뱅크 월 10컷 39,000원 한 달; (3) 처리는 빌드 시 sharp/Pillow로 흑백 → 먹 `#141414`/종이 `#f9f8f6` 듀오톤 매핑 → 미세 그레인을 **파일에 구움**; (4) 출력 `<picture>` AVIF(q52, effort 8, 4:2:0) → WebP(q80) → JPEG(q80 mozjpeg), 폭 640/960/1440/1920, `width/height` 명시, 접힘 아래만 `loading="lazy" decoding="async"`, 플레이스홀더는 16×16 WebP 데이터 URI; (5) 히어로로 쓴다면 그 한 장에만 `fetchpriority="high"` + preload.
- **하지 말 것**: Unsplash 무료 사진의 무가공 사용(경쟁사와 동일 사진·릴리스 불명), 사진 위 반투명 카드, 컬러 사진과 흑백 사진 혼용, 서울 야경·전광판·악수·노트북 앞 사람.

### 9. 아이콘·스팟 도해 — "기술적 일러스트" 한 종류, 규칙은 토스페이스에서 빌린다
- **왜**: Robinhood가 복잡한 아트워크를 버리고 "easy to replicate and scale"한 기술적 일러스트로 간 이유(1·4절); 토스페이스의 일관성 규칙(시선 방향·45°·단일 팔레트)은 소규모에도 적용 가능(4절).
- **레시피**: 필요 최소 아이콘(검색·메뉴·테마·관심종목·외부링크 등 ≤16개)만 24px 그리드, 선 1.5px round, 먹 단색 `currentColor`, 채움 없음, 모서리 반경 2px 이내, 각도 45° 통일, 방향 요소는 왼→오. 스팟 도해(예: 지표 설명)는 같은 선 규격의 SVG 다이어그램으로 — 그림이 아니라 도면. 하나의 SVG 스프라이트 파일 + `<use href>`.
- **하지 말 것**: 토스페이스 폰트 자체 사용(곧바로 "토스 같다"), 3D 이모지, 광택 블롭, 두 가지 선 굵기 혼용, 색 채움 아이콘.

### 10. "AI 티" 게이트 — 발행 전 점검표(체크리스트를 코드로)
- **왜**: AI 티는 정의상 "평균값"이라 개별 판단보다 규칙이 잘 잡는다(925 Studios·Wikipedia AI slop)(4절).
- **레시피**: `docs/design/no-ai-look.md`에 8항목(색: 인디고/보라/틸 그라디언트 금지 · 형태: 3D 블롭/유리/아이소메트릭 금지 · 질감: 플라스틱 광택 금지 · 인물: 손/글자 100% 확대 검사 · 글자: 실제 폰트로만 · 레이아웃: 둥근 카드 3열/카드 그림자 금지 · 카피: 숫자·고유명사 없는 문장 금지 · 출처: 생성형 이미지 사용 시 기록). 자동화 가능한 것은 검사로: CSS에서 `linear-gradient(`가 `#`시작 두 색 이상으로 쓰이면 경고, `box-shadow`가 카드 규칙 밖에서 쓰이면 경고, 저장소에 `*.png|jpg` 신규 추가 시 PR 코멘트로 점검표 출력.
- **하지 말 것**: "조금만" 그라디언트, 랜딩만 예외, 생성형 3D 마스코트.

### 11. 접근성·성능 규칙을 이미지 전략에 내장
- **왜**: WAI 결정 트리(복잡한 이미지는 정보를 다른 곳에), LCP 이미지 하나만 high, 접힘 아래만 lazy, `width/height` 필수(5·7절).
- **레시피**: 스파크라인 `role="img" aria-label="종목명 1년 종가 추이, 52주 저점 대비 +N%"`(값은 표에 있으므로 충분), 태피스트리 개별 SVG는 `aria-hidden`, 장식 SVG는 `alt=""`/`aria-hidden`; 모든 `<img>`에 `width height`; 페이지당 `fetchpriority="high"`는 0~1개; OG는 정적 파일(이미지 CDN 불필요 — 정적 사이트에서 절감할 바이트가 없다); Lighthouse 이미지 감사 항목을 `check_all.sh`에 추가(속성 누락 검사).
- **하지 말 것**: LCP 이미지에 `loading="lazy"`, 히어로 여러 장에 `fetchpriority="high"`, alt에 "이미지"·"차트"만 적기, 차트 정보를 alt에만 두기.

### 12. 유지보수 — 시각물 생성기 하나, 결정론, 스냅샷 검사
- **왜**: Bloomberg Futures가 "4 테마 × 7 팔레트"로 변주를 제한해 자동화를 가능하게 했고(1절), GitHub은 OG를 캐시·계측했다(2절). KOSAI는 이미 문단 자르기·팔레트를 검사로 지킨다(`same-paragraphs.test.mjs`·`patch_light_palette.py --check`).
- **레시피**: `scripts/visuals.py` 한 모듈에 `sparkline_svg` · `tapestry_svg` · `market_svg` · `og_card`를 두고, 시안(`preview/`)·스테이징·실사이트 생성기가 모두 이걸 import(옷은 한 곳 원칙과 동일). 입력 고정 시 출력 바이트 동일(스냅샷 테스트 3종목 + 태피스트리 1섹터). OG는 내용 해시 캐시, 아침 워크플로에는 시장 한 장(제안 6)만 포함하고 OG 전량은 주 1회 별도 잡. 저장소에 래스터 총량 상한(예: 5MB, 추정)을 검사로 둔다.
- **하지 말 것**: 페이지 종류마다 다른 차트 코드, 손으로 고친 SVG 커밋, 시드 난수 사용, OG를 요청 시점에 생성하는 서버 도입(정적 사이트 원칙과 충돌).
