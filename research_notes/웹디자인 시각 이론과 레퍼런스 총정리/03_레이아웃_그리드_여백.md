# 03 레이아웃·그리드·여백 — 에디토리얼 이론과 실측 레퍼런스, 데이터 화면과 휴대폰

조사 범위: 그리드 체계(열 수·비대칭·폭·거터·마진), 여백 척도와 리듬, 상자 없이 구조 만드는 장치, 데이터 밀도 화면(표), 반응형(컨테이너 쿼리·clamp·휴대폰 리듬·바텀시트·표), 장문 구조(목차·읽기 폭), 첫 화면 구성, 일관성 장치(토큰·프리미티브).
기준(현재 KOSAI 옷, `scripts/comp_common.py` · `scripts/stock_page.py` 에서 확인): `--wrap:1120px` · `--pad:32px`(≤820px 에서 20px) · 헤더 60px · 리포트 본문 두 단 `grid-template-columns:200px minmax(0,1fr); gap:64px` · 절 `max-width:720px`(넓은 절 880) · 절 아래 여백 88px(휴대폰 64) · 목차 `top:84px` · 휴대폰 목차는 44px 밑줄 탭 · 본문 `17px/28px`(휴대폰 16/27) · 문단 간격 20px.
방법: 이론은 1차 자료(Bringhurst 를 옮긴 webtypography.net, Every Layout, NN/g, Carbon, Apple HIG 원문 JSON, KRDS, JCR 논문)를 우선했다. stripe.com · linear.app · vercel.com · apple.com/newsroom · notion.com · mercury.com · theguardian.com · developer.mozilla.org 는 **2026-09-26 에 실제 HTML/CSS 를 내려받아 grep 으로 잰 값**이고 "실측" 으로 표시했다(렌더링한 값이 아니라 CSS 선언값이다). ft.com 은 403 응답이었지만 응답 본문에 FT 디자인 시스템(o3) CSS 가 들어 있어 그 값을 썼다. nytimes.com · economist.com 은 403, mckinsey.com 은 연결이 끊겨 재지 못했다(Gaps). "추정"·"계산" 이라 쓴 숫자는 출처가 아니라 내 계산이다.

## 1. 에디토리얼 그리드 — 12열 대 8/6열, 비대칭, 레퍼런스의 컨테이너·거터·마진

### Takeaway
실측한 레퍼런스는 거의 모두 **데스크톱 12열 → 태블릿 8열 → 휴대폰 4열**, 거터 16~24px 이고, 페이지 컨테이너는 **1200~1320px**(Vercel 1200 · KRDS 1200 · Notion 1252 · Guardian 1300 · FT 1320), 장문 본문 칸은 **690~770px**(Apple 692 · MDN 768) 에 모인다. 휴대폰 좌우 마진은 **16~24px** 이다. KOSAI 의 1120/720/20 은 이 띠 안에 있고, 문제는 폭 자체가 아니라 중간 폭(821~1000px)에서 두 단이 본문을 너무 좁히는 것이다(6절).

### Cited Findings
- 모듈 그리드는 여백(margin) 안의 판면을 열과 행, 일정한 거터로 나눈 "필드" 들이며, 글과 그림이 필드를 통째로 차지한다. 뮐러브로크만의 견본은 8·20·32 필드를 흔히 쓴다(2차 요약 · 원서 미열람) — [maxsoweski/claude-design-skills, Müller-Brockmann Grid Systems 요약](https://github.com/maxsoweski/claude-design-skills/blob/main/skills/muller-brockmann-grid-systems/SKILL.md); 개요 [Wikipedia, Grid (graphic design)](https://en.wikipedia.org/wiki/Grid_(graphic_design))
- Van de Graaf/Tschichold 캐논: 2:3 판형에서 안쪽:위:바깥:아래 여백이 **2:3:4:6**, 안쪽 여백은 바깥의 절반, 판면 높이 = 종이 폭 — [Wikipedia, Canons of page construction](https://en.wikipedia.org/wiki/Canons_of_page_construction)
- Bringhurst: 한 단 본문은 **45~75자**가 무난하고 **66자**가 이상, 여러 단이면 **40~50자**. Rutter 의 웹 적용: 한 글자 평균 0.5em 이므로 **33em ≈ 66자**, em 폭은 글자를 키워도 행길이를 유지 — [webtypography.net 2.1.2](https://webtypography.net/2.1.2)
- Every Layout 의 공리: "measure 는 60ch 를 넘지 않는다" — `:root{--measure:60ch}` + `max-inline-size` — [Every Layout, Axioms](https://every-layout.dev/rudiments/axioms/)
- Material 3 창 크기 등급: Compact <600dp · Medium 600~839 · Expanded ≥840; 모든 브레이크포인트에서 마진과 글자 크기를 조정해 **한 줄 40~60자** 유지(검색 요약 · 원문 페이지는 404) — [M3 Breakpoints](https://m3.material.io/foundations/layout/applying-layout); [Android codelab](https://developer.android.com/codelabs/adaptive-material-guidance)
- KRDS(범정부 디자인 시스템) 표준형: small ≥360 **4열·거터16·마진16** / medium ≥768 **8열·16·24** / large ≥1024 **12열·24·24** / xlarge ≥1280 12열·24·24. 최대 콘텐츠 폭 **1200px**(마진 24 포함 기준점 1248). 8pt 간격, 헤더→브레드크럼 24 · 좌측→본문 64 · 본문→푸터 64 · 브레드크럼→h1 40(모바일 32) — [KRDS 레이아웃](https://www.krds.go.kr/html/site/style/style_05.html)
- **FT o3 그리드(실측)**: 휴대폰 4열·gap 16px·양끝 bleed 8px → 중간 단계 8열·gap 24 → ≥1024px 12열·gap 24, 열 폭은 `(1320px − 거터합)/12` → ≥1368px 부터 1320px 고정 열 + 양옆 `minmax(0,auto)`. 그리드 영역 이름에 `bleed-left · content-start … content-end · bleed-right` 가 있다 — [ft.com CSS](https://www.ft.com)
- **Apple Newsroom(실측)**: 12열 `--sk-cssgrid-columns:12`, 거터 24px. `.section-content` 폭 **980px**(>1068) · **692px**(735~1068) · **87.5%**(≤734). 390px 에서 좌우 여백 ≈ 24.4px(계산) — [apple.com/newsroom CSS](https://www.apple.com/newsroom/)
- **Stripe(실측)**: `--hds-space-layout-columns` 4/8/12, `--hds-space-layout-gap` 16px, `--hds-space-layout-page-margin` 16px(좁은 화면)·0, `--hds-space-layout-content-margin` 16px — [stripe.com CSS](https://stripe.com/)
- **Vercel(실측)**: `--geist-page-width:1200px`, `--geist-page-margin:var(--geist-space-gap)` = **24px**, 래퍼는 `width: page-width + margin; padding-inline: page-margin` — [vercel.com CSS](https://vercel.com/)
- **Notion(실측)**: 섹션 `max-width:1252px; margin:0 auto`, 거터 `--g-grid-gutter` 기본 24px, 히어로를 `full-bleed-start/end · content-start/end · center-start/end` 이름 선으로 배치 — [notion.com CSS](https://www.notion.com/)
- **Mercury(실측)**: `--grid-total-columns:12` → 넓은 화면 16, `--grid-max-width:1952px`, 거터·마진을 `--gap-md`·`--gap-lg` 의미 토큰으로 — [mercury.com CSS](https://mercury.com/)
- **Guardian(실측)**: `max-width` 값이 740 · 980 · 1140 · 1300px 에 몰려 있다(브레이크포인트 겸 컨테이너) — [theguardian.com](https://www.theguardian.com/international)
- **Linear(실측, 부분)**: 브레이크포인트 성격의 `max-width` 640(81회)·1024·768·1280, 폭은 `min(var(--homepage-max-width),100vw) − 2×outer-padding` 을 열 수로 나눈 `--stage-column` 으로 계산(최대폭 값 자체는 못 찾음), 헤더 높이 변수 57/65px — [linear.app CSS](https://linear.app/)

### Inferences
- 12열은 2·3·4·6 으로 나뉘어 표·카드·두 단을 한 체계로 다룰 수 있어 표준이 되었다. 리포트처럼 "좁은 본문 + 목차" 는 12열의 **3 + 8 + 1(빈 열)** 비대칭으로 읽을 수 있다: KOSAI 안쪽 폭 1056px(1120−2×32) 에서 목차 200 + 간격 64 + 본문 720 = 984, 오른쪽에 72px 가 비어 스위스식 "빈 열" 효과가 난다(계산).
- 황금비·2:1 같은 비율은 "본문 대 곁단" 에만 의미가 있다. 720:200 ≈ 3.6:1 로 곁단이 가벼워 목차가 본문을 누르지 않는다 — 곁단을 240(MDN 수준) 이상으로 키울 이유는 없다(추정).
- Tschichold 의 "바깥·아래 여백이 더 크다" 는 웹에서 **페이지 아래·절 아래 여백 > 위 여백** 으로 옮길 수 있다(히어로 위 32 · 아래 36 인 현재 비율은 이미 그 방향).

### Gaps
- NYT·Economist·FT 기사 본문 폭, McKinsey 인사이트 페이지는 403/연결 끊김으로 재지 못했다. Linear 의 `--homepage-max-width`, Stripe 데스크톱 컨테이너 최대폭도 내려받은 CSS 에 선언이 없었다(다른 번들이나 인라인 JS 로 추정).
- Material 3 의 등급별 마진 dp(16/24) 는 원문을 열지 못해 확인하지 못했다.

## 2. 여백이 곧 고급감 — 간격 척도, 섹션 패딩, 미시/거시 여백, '허공에 뜸' 피하기, 베이스라인

### Takeaway
여백은 실제로 고급·신뢰로 읽힌다(JCR 2006). 실측한 고급 사이트는 **4/8 기반 척도에서 48 이후 8~16 단위로 커지는** 척도를 쓰고, 섹션 세로 여백은 **휴대폰 48~64 · 데스크톱 80~144px** 이다. 허공에 뜨지 않게 하는 규칙은 하나다 — **묶음 사이 여백은 묶음 안 여백의 2배 이상**이고, 떠 있는 덩어리는 선·눈썹·왼쪽 정렬선으로 붙잡는다.

### Cited Findings
- 광고의 흰 여백은 대형 광고사 크리에이티브 디렉터들이 "고급·상류" 의미로 쓰고, 소비자 실험에서도 여백이 많은 광고가 브랜드를 **더 높은 품질·명성·신뢰**로 지각하게 했다 — [Pracejus, Olsen, O'Guinn, "How Nothing Became Something", Journal of Consumer Research 33(1), 2006](https://academic.oup.com/jcr/article-abstract/33/1/82/1822622); 요약 [Semantic Scholar](https://www.semanticscholar.org/paper/How-Nothing-Became-Something:-White-Space,-History,-Pracejus-Olsen/b2829dd1db1e8e09c5ede257a03f620e09b97736)
- "여백은 더하지 말고 덜어라 — 지나치게 많이 주고 시작해 만족할 때까지 줄여라. 요소 하나만 볼 때 '조금 많다' 가 전체 UI 에서는 '딱 맞다' 가 된다." 동시에 "대시보드처럼 한 화면에 많이 보여야 하면 촘촘함이 맞다 — 기본값이 아니라 의도한 결정이어야 한다" — [Refactoring UI 발췌 PDF, "Start with too much white space"](https://refactoring-ui.nyc3.cdn.digitaloceanspaces.com/Refactoring%20UI%20-%20Start%20with%20too%20much%20white%20space.pdf)
- Refactoring UI 척도는 4·8·16·24·32·48·64…, "묶음 사이 간격 > 묶음 안 간격"(2차 요약, 원문 해당 장 미열람) — [LobeHub, Refactoring UI skill 요약](https://lobehub.com/skills/comeonoliver-skillshub-refactoring-ui)
- **Stripe 간격 원자(실측)** `--hds-space-core-*`: 1·2·4·6·8·12·16·20·24·28·32·36·40·44·48·56·64·72·80·88·96 … 200px(48 이후 8px 단위). 섹션 `padding-block`: 휴대폰 core-600 = **48px**, 태블릿 core-700 = **56px**, 데스크톱 core-1000 = **80px**(일부 섹션 36px). 히어로 최소 높이 `min(68svh, 826px)` — [stripe.com CSS](https://stripe.com/)
- **Vercel(실측)**: 간격 토큰 8·12·24·40·64·96·128px; 그리드 구획 사이 `--grid-divider-gap: calc(72px|120px|140px − cell-padding)`, cell-padding 24/40/48 — 즉 구획 리듬 72→120→140px — [vercel.com CSS](https://vercel.com/)
- **Mercury(실측)**: 원자 1·8·12·16·20 … 112·128·144·160·192·224·240px; 의미 토큰이 화면 폭마다 원자를 바꿔 가리킨다 — `--layout-padding-xl` 96→112→128→144, `--hero-padding-default` 32→40→64→72→80, `--gap-3xl` 80→96→112→128 — [mercury.com CSS](https://mercury.com/)
- **Linear(실측)**: `--padding-bottom` 112 / 48 / 28px 세 단계 — [linear.app CSS](https://linear.app/)
- Apple HIG: "관련 항목을 묶어 관계를 드러내라 — 음의 공간(negative space), 컨테이너 모양, 구분선을 쓸 수 있다", "정렬과 들여쓰기로 위계를 전하라 — 정렬된 항목은 관련 있다고, 들여쓴 항목은 앞 항목에 종속된다고 지각한다" — [Apple HIG, Layout (원문 JSON)](https://developer.apple.com/design/human-interface-guidelines/layout)
- Utopia: 유동 글자 척도의 step 0 을 기본 단위로 배수를 곱해 T셔츠 크기(S·M·L…) 간격을 만들고, 두 뷰포트 극(예: 320·1500px) 사이를 `clamp()` 로 보간한다. 한 단계씩 건너뛰는 "쌍"(S→M 등)과 임의 쌍(S→L)으로 휴대폰에서 더 크게 줄어드는 간격을 만든다 — [Smashing, Meet Utopia](https://www.smashingmagazine.com/2021/04/designing-developing-fluid-type-space-scales/); [Utopia space calculator](https://utopia.fyi/space/calculator/)
- 베이스라인: "행간은 기준 단위의 정수배, 모든 요소가 거기 붙는다"(뮐러브로크만 요약, 2차) — [claude-design-skills 요약](https://github.com/maxsoweski/claude-design-skills/blob/main/skills/muller-brockmann-grid-systems/SKILL.md). `text-box-trim`(`text-box: trim-both cap alphabetic`)은 글자 위아래 반행간을 잘라 "눈에 보이는 여백" 으로 리듬을 잴 수 있게 한다 — Chrome 133 · Safari 18.2 · Firefox 154 지원, Baseline 신규(2026-08) — [Chrome for Developers](https://developer.chrome.com/blog/css-text-box-trim); [MDN text-box-trim](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-box-trim); [caniuse](https://caniuse.com/mdn-css_properties_text-box-trim)
- **MDN(실측)**: 본문 행간 `--font-line-content:1.75`, 제목 1.25 — [developer.mozilla.org CSS](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Grid_layout)

### Inferences
- **미시 여백**(글자·행·문단: 행간 28, 문단 20)은 읽기 속도를, **거시 여백**(절 88~96, 페이지 위아래)은 가격감을 만든다. KOSAI 는 미시는 이미 맞고(행간 28 = 4×7, 문단 20), 거시에서 고급감을 더 얻을 수 있다: 절 여백 88 → 96(데스크톱)은 Stripe 80·Vercel 120 사이다.
- "허공에 뜸" 은 (1) 안쪽 여백 ≥ 바깥 여백으로 근접성이 깨질 때, (2) 덩어리마다 왼쪽 시작선이 다를 때, (3) 큰 여백 위에 붙잡는 선이 없을 때 생긴다(추정). 해법은 여백을 줄이는 것이 아니라 **위계 3단(16 / 32 / 96)** 을 지키고 절 머리에 헤어라인과 번호를 두는 것이다.
- 엄격한 4px 베이스라인 그리드는 한글·라틴·숫자가 섞이고 글자 크기가 여럿인 웹에서 유지가 어렵다. 현실적인 방법은 **모든 행간·여백을 4의 배수로** 두고 제목·눈썹에만 `text-box-trim` 을 거는 것이다. 다만 `cap alphabetic` 은 라틴 대문자 높이 기준이라 한글 글자가 그 선 위로 솟을 수 있어 시안에서 확인해야 한다(추정).

### Gaps
- Refactoring UI 의 "척도 인접값은 약 25% 이상 벌린다" 규칙은 원문 해당 장을 열지 못해 확인하지 못했다.
- '여백과 고급감' 의 웹 화면 대상 정량 연구(광고 지면이 아닌)는 찾지 못했다.

## 3. 상자 없이 구조 만들기 — 헤어라인, 번호, 눈썹, 매달린 구두점, 러닝헤드, 풀블리드, 벤토

### Takeaway
카드 없이도 묶음은 **여백 · 구분선 · 정렬 · 번호** 넷으로 충분히 드러난다(Apple HIG 가 셋을 같은 급으로 든다). 풀블리드는 그리드 안의 **이름 붙은 선**(FT `bleed-left`, Notion `full-bleed-start`)으로 처리하는 것이 표준이 됐다. 벤토 그리드는 2026년 디자이너들이 "질렸다" 고 꼽은 항목이라, 종이 리포트 방향에는 맞지 않는다.

## 4. 데이터 밀도 화면 — 표의 행 높이, 선 대 줄무늬, 고정 머리·첫 열, 숫자 정렬, 밀도와 고급감

### Takeaway

## 5. 반응형 — 컨테이너 쿼리, clamp 간격, 휴대폰 리듬, 바텀시트, 표 쌓기, safe area

### Takeaway

## 6. 장문 구조 — 목차(데스크톱 곁단·휴대폰 탭), 번호, 진행, 읽기 폭

### Takeaway
장문 페이지의 표준은 **곁단 목차(200~240px) + 간격 32~64 + 본문 680~768px**, 좁아지면 곁단을 접는다. MDN 은 본문 최소 496px 를 지키려고 접는 지점을 계산으로 정한다. KOSAI 는 820px 에서야 접어서 **821~1000px 구간의 본문이 490~670px 로 좁아진다**(계산) — 여기가 고칠 곳이다. 한글 본문은 한 줄 **40~60자**가 권장이고 720px·17px 는 약 42자라 맞다.

- 진행 표시(읽기 진행 막대)는 이번 조사에서 효과 근거를 찾지 못했다 — 목차의 현재 절 표시(이미 있음)로 충분하다(추정).

### Gaps
- Stripe 문서·Notion 문서·FT 롱리드의 목차 폭과 `top` 오프셋은 CSS-in-JS 라 선언값을 뽑지 못했다. 읽기 진행 막대의 효과에 대한 1차 연구는 찾지 못했다.

## 7. 홈·첫 화면 구성 — 글 먼저 대 이미지 히어로, 폴드, F/Z 패턴, 비싸 보이는 첫 화면

### Takeaway
사용자는 여전히 **보는 시간의 57% 를 첫 화면**, **74% 를 첫 두 화면(≈2160px)** 에 쓴다(NN/g 2018). F 패턴은 서식 없는 글·효율 추구·낮은 관여라는 조건에서 생기는 "실패 패턴" 이다. 따라서 콘텐츠 사이트의 비싼 첫 화면은 **큰 이미지가 아니라 여백 속에 놓인 제목 한 줄 + 오늘의 실제 목록**이 첫 화면에 들어오는 구성이다.

### Cited Findings
- 2018 시선추적(120명, 13만 고정점): 보는 시간의 **57%** 가 폴드 위, **74%** 가 첫 두 화면(2160px 까지). 2010년(80%)보다 낮지만 폴드 뒤 급감 패턴은 같다 — [NN/g, Scrolling and Attention](https://www.nngroup.com/articles/scrolling-and-attention/)
- F 패턴의 세 조건: 웹용 서식이 거의 없는 글 · 효율 우선 · 낮은 관여. 대안 패턴: 레이어케이크 · 점 찍기 · 마킹(휴대폰에서 시선 고정, 화면이 올라감) · 건너뛰기 · 몰입 — [NN/g F-pattern 2017](https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/)
- Stripe 히어로 최소 높이 `min(68svh, 826px)`(실측) — 마케팅 사이트도 첫 화면 전체를 쓰지 않고 다음 내용을 엿보이게 한다 — [stripe.com CSS](https://stripe.com/)
- Mercury 히어로 여백 32→80px 단계(실측) — [mercury.com CSS](https://mercury.com/)
- 여백 = 고급·신뢰 지각 — [Pracejus et al., JCR 2006](https://academic.oup.com/jcr/article-abstract/33/1/82/1822622)

### Inferences
- 390×844 에서 브라우저 틀을 빼면 보이는 높이는 대략 660~750px(추정). 헤더 60 + 위 여백 48 + 눈썹·제목 ≈120 + 여백 32 를 빼면 **목록 3~5행**이 첫 화면에 들어온다 — 57% 의 시간을 실제 리포트에 쓰게 된다.
- 첫 화면을 비싸 보이게 하는 것은 (1) 제목 좌우와 위의 넉넉한 여백, (2) 한 개의 강한 글자 위계(큰 제목 하나, 나머지 작고 회색), (3) 목록의 엄격한 정렬선, (4) 장식 없음이다(1~3절 종합, 추정).

### Gaps
- Z 패턴에 대한 최근 1차 연구는 찾지 못했다(주로 2차 블로그). 한국 금융 사이트 첫 화면 구성에 대한 정량 자료는 없었다.

## 8. 일관성 장치 — 간격 토큰, 레이아웃 프리미티브, 작은 팀이 정렬을 지키는 법

### Takeaway
실측한 팀들은 모두 **원자 토큰(px 값) → 의미 토큰(용도) → 화면 폭마다 의미 토큰이 가리키는 원자를 바꾸는** 2층 구조를 쓴다(Stripe `hds-space-core` → `layout-gap`, Mercury `spacing-*` → `gap-*`/`layout-padding-*`, Vercel `geist-space-*` → `geist-gap`/`page-margin`). 여기에 Every Layout 식 프리미티브 몇 개(Stack·Center·Sidebar)를 두면 작은 팀도 페이지마다 여백을 새로 정하지 않게 된다.

### Cited Findings
- Every Layout 프리미티브: Stack(세로 간격) · Box(안쪽 여백) · Center(가운데 + measure) · Cluster · Sidebar(두 단) · Switcher(threshold 기본 `var(--measure)`) · Cover · Grid · Frame · Reel · Imposter · Icon; measure 는 `60ch` — [Every Layout, Axioms](https://every-layout.dev/rudiments/axioms/)
- Stripe 2층 토큰(실측): `--hds-space-core-200:16px` → `--hds-space-layout-gap` · `--hds-space-layout-content-margin` · `--hds-space-layout-page-margin`; 섹션은 `--section-container-pbs-dt/-tb` 로 폭별 값 — [stripe.com CSS](https://stripe.com/)
- Mercury(실측): `--layout-padding-sm:var(--gap-xl)` · `-md:var(--gap-2xl)` · `-lg:var(--gap-3xl)` 이고 `--gap-*` 가 폭마다 다른 `--spacing-*` 를 가리킴 — [mercury.com CSS](https://mercury.com/)
- Vercel(실측): `--geist-gap:var(--geist-space-gap)`(24) · `--geist-gap-half`(12) · `--geist-gap-quarter`(8) · `--geist-page-margin`(24) — [vercel.com CSS](https://vercel.com/)
- KRDS: 8pt 체계, `gap-3:8px` · `gap-5:16px` · `gap-7:24px` 같은 이름 토큰 — [KRDS 레이아웃](https://www.krds.go.kr/html/site/style/style_05.html)
- Utopia: 한 기본 단위에서 전체 간격을 파생 — [Utopia](https://utopia.fyi/space/calculator/)

### Inferences
- KOSAI 는 이미 "생성기 한 곳(comp_common.CSS)에서 모든 페이지를 만든다" 는 구조라, 토큰을 `:root` 에 두고 생성기 CSS 의 날 px 여백을 토큰으로 바꾸기만 하면 된다. 그 뒤 `check_all.sh` 에 "척도 밖 여백 값" 검사를 붙이면 CLAUDE.md 의 "기억 대신 검사" 원칙과 맞는다(추정).

### Gaps
- 토스 디자인 시스템(TDS)의 간격·레이아웃 토큰 원문은 공개 글에서 찾지 못했다(toss.tech 가이드 글은 문서화 방식 위주).

## KOSAI 적용 제안

우선순위 순. 값은 모두 시안(preview/)에서 사장 실기기 확인 뒤 스테이징·실사이트 생성기에 넣는 것을 전제로 한다(CLAUDE.md 디자인 헌장 절차).

**1. (최우선) 목차 두 단이 본문을 짓누르는 구간을 없앤다.** 목차→탭 전환점을 820 → **960px** 으로, 두 단 간격을 고정 64 → **`clamp(40px, 5vw, 64px)`** 로. 헤더 메뉴의 820 전환은 그대로 두고 목차만 따로 둔다. 근거: 821px 에서 현재 본문 493px(≈29자) → 변경 후 961px 에서 ≈649px, MDN 의 본문 최소 496·최대 768 과 같은 논리(6절).

**2. 간격 척도를 토큰으로 고정한다(4 기반, 48 이후 16 단위 · Stripe·Vercel·Mercury·KRDS 수렴값).**

| 토큰 | 값 | 쓰임 |
|---|---|---|
| `--s-1` | 4px | 아이콘–글자, 숫자–단위 |
| `--s-2` | 8px | 눈썹→제목, 칩 사이 |
| `--s-3` | 12px | 목록 행 안 위아래 |
| `--s-4` | 16px | 한 묶음 안 요소 사이 |
| `--s-5` | 20px | 문단 사이(현행 20 유지) |

**3. 페이지 폭 표 — 텍스트 페이지는 지금 폭, 데이터 페이지만 넓힌다.**

| 페이지 | 바깥 폭 `--wrap` | 좌우 `--pad` (데스크톱 / ≤820 / <360) | 본문 칸 | 근거 |
|---|---|---|---|---|
| 종목 리포트 · 브리핑 | 1120 (유지) | 32 / 20 / 16 | 목차 200 + `clamp(40,5vw,64)` + 절 **720** (넓은 절 880) | Apple 692 · MDN 768 · 한글 ≈42자 |

| 로그인 · 가입 · 동의 | — | 20 | 폼 칸 **400** (현행) | 폼은 한 열 |

**4. 그리드 — 12 / 8 / 4열.** 데스크톱(>1024) 12열·거터 24, 태블릿(821~1024) 8열·거터 24·마진 32, 휴대폰 4열·거터 16·마진 20(<360 에서 16). 리포트는 12열의 "3 + 8 + 빈 1" 비대칭으로 읽히게 두고(오른쪽 72px 공백은 채우지 않는다), 홈·업종 표는 12열 전체를 쓴다.

**5. 절의 리듬(리포트).** 절 아래 여백 88 → `--gap-section`(96 / 64). 절 머리: 헤어라인 `1px var(--hair)` → 24px → 눈썹(번호 `01` + 절 이름, 12~13px · `--ink-55`) → 8px → h2 → 24px → 첫 문단. 문단 20 · 행간 28 은 유지(CLAUDE.md 의 `.prose p 20px` 짝 규칙). 목차 `top` 은 헤더 60 + 24 = **84px** 유지.

**6. 업종·목록 표.** 행 높이 **44px**(데스크톱, 13~14px 글자) · 휴대폰 **48px**(손가락). 줄무늬 없이 행 사이 `1px var(--hair)`, 호버·선택만 `--surface-2`. 머리 행: 12px · 500 · `--ink-55`, 표가 한 화면을 넘을 때만 `position:sticky; top:60px`. 숫자 열·그 머리글 **오른쪽 정렬** + `tabular-nums`, 등락률은 소수 둘째 자리 고정. 첫 열은 종목명(사람이 읽는 식별자, NN/g).

**7. 휴대폰 표는 쌓지 않는다(비교가 목적이므로).** 종목명 열 고정(`position:sticky; left:0`, 스크롤이 생기면 오른쪽에 `1px var(--line)`), 보이는 숫자 열은 **3개까지**, 나머지는 가로 스크롤 — 스크롤 신호는 점이 아니라 **마지막 열이 반쯤 잘려 보이게** 한다(NN/g). 볼 열 고르기는 기존 업종 바텀시트와 같은 옷의 짧은 시트로.

**8. 홈 첫 화면은 글 먼저.** 이미지 히어로 없이 위 여백 `--gap-page-top`(48 / 80) → 날짜 눈썹 → 제목 한 줄 → 32px → **오늘의 리포트 목록**. 390×844 에서 목록 3~5행이 첫 화면에 들어와야 한다(보는 시간의 57%). 전체 높이 히어로·벤토는 쓰지 않는다.

**9. 상자 대신 장치.** 카드 테두리·그림자 대신 절 번호 + 눈썹 + 헤어라인. 인용·어록 블록에 `hanging-punctuation: first`(사파리만, 점진적 향상). 풀블리드가 필요한 곳(업종 표를 넓은 화면에서 넓게)은 `grid-template-columns: [full-start] minmax(var(--pad),1fr) [content-start] min(100% - 2*var(--pad), 1056px) [content-end] minmax(var(--pad),1fr) [full-end]` 식 이름 선으로.

**10. 레이아웃 프리미티브 셋을 생성기에 둔다.** `.stack > * + * { margin-block-start: var(--stack, var(--s-5)) }` · `.center { max-inline-size: var(--measure, 720px); margin-inline: auto; padding-inline: var(--pad) }` · `.with-toc`(1번의 두 단). 새 페이지는 이 셋과 토큰만 쓴다.

**11. 검사로 지킨다.** `check_all.sh` 에 생성기 CSS 의 `margin`·`padding`·`gap` 값이 2번 척도(0·1·2·4·8·12·16·20·24·32·40·48·64·96·128)나 토큰 밖이면 걸리는 검사를 붙인다(예외는 주석으로). 목차 전환점(960)과 `--wrap` 값도 스테이징·실사이트가 같은지 본다.

**12. 제목·눈썹의 반행간 자르기(시험).** `h1, h2, .eyebrow { text-box: trim-both cap alphabetic }` 를 시안에만 걸어 사파리 실기기에서 한글이 대문자 높이 선 위로 솟는지 확인한다. 솟으면 `text-box-edge` 를 글꼴 전체 높이(`text`) 로 바꾸거나 쓰지 않는다. 지원: Chrome 133 · Safari 18.2 · Firefox 154, 모르는 브라우저는 무시하므로 안전.

**13. (낮음) 컨테이너 쿼리는 목록 부품에만.** 같은 리포트 목록 부품이 홈(넓음)과 곁단(좁음)에 같이 쓰일 때 `container-type: inline-size` + `@container (width < 480px)` 로 2줄 배치로 바꾼다. 페이지 뼈대는 지금처럼 미디어 쿼리로 둔다(2025-08 Widely available 이라 사용 자체는 안전).
