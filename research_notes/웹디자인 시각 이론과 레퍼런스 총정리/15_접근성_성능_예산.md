## 1. 대비 — WCAG 2.2 비율 vs APCA Lc (본문·보조·헤어라인)

### Takeaway
라이트 본문(#141414/#f9f8f6 = 17.4:1, Lc 101)과 72% 보조(7.1:1, Lc 82)는 넉넉하지만, **55% 잉크(3.99:1, Lc 65)는 WCAG AA(4.5:1) 미달**이고 KOSAI 스테이징에서 442번이나 쓰인다. 다크는 WCAG로는 전부 통과하는데 **APCA로는 72% 보조가 Lc −58, 55%가 Lc −38로 약하다** — 다크 모드의 보조 글자는 WCAG 비율이 과대평가한다는 APCA의 지적이 그대로 나타난다. 권장: 라이트 55%→62%, 다크 72%→80%.

### Cited Findings
- WCAG 2.2 1.4.3(AA): 텍스트 4.5:1, 큰 텍스트 3:1, 비활성·장식(incidental)·로고는 요구 없음. 1.4.11(AA): UI 구성요소 경계와 의미 있는 그래픽은 인접색과 3:1 — [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- KWCAG 2.2 5.4.3 "텍스트 콘텐츠와 배경 간의 명도 대비는 4.5 대 1 이상"(18pt 이상·14pt 굵은 글꼴은 3:1, 로고·장식 예외) — WCAG와 같은 수치 — [KWCAG 2.2](https://a11ykr.github.io/kwcag22/)
- APCA 수준: **Lc 90** 본문 권장(18px/300 또는 14px/400 이상), **Lc 75** 본문 최소(18px/400, 16px/500, 14px/700 이상), **Lc 60** 본문이 아닌 콘텐츠 텍스트 최소(24px/400, 18px/600, 16px/700), **Lc 45** 큰 제목(36px/400, 24px/700), **Lc 30** 플레이스홀더·비활성 텍스트 등 "스팟" 텍스트 절대 최소, **Lc 15** 구분선 등 비의미 비텍스트 절대 최소. ### Inferences
- **본문 15–16px/400**: WCAG 4.5:1(가능하면 7:1), APCA Lc 75 이상(권장 90). KOSAI 본문은 ink 100%(Lc 101)라 이미 최상. 보조 본문(요약·캡션 14–15px)에는 ink-72(라이트 Lc 82 / 다크는 80%로 올려 Lc −68).
- **12px 라벨**(표 머리·눈썹·단위): WCAG 4.5:1 필수. APCA 는 12px/400 을 본문 등급으로 권하지 않으므로 12px 라벨은 **500–600 굵기 + 라이트 ink-62 / 다크 ink-80** 이 안전선. ink-55 를 12–13px 에 쓰는 자리는 전부 교체 대상.
- **플레이스홀더**: APCA 최소 Lc 30, WCAG 는 플레이스홀더도 텍스트로 보는 해석이 일반적이라 4.5:1 을 권장(이번 조사에서 W3C 원문 확인은 못 함). 절충안: 라이트 ink-60(4.72:1), 다크 ink-55(5.47:1). 레이블은 플레이스홀더가 아니라 별도 `<label>` 로(KWCAG 7.3.2 레이블 제공).
- **비활성(disabled)**: WCAG 1.4.3 예외라 ink-30 을 써도 규정 위반은 아니나, 비활성임을 색만으로 알리지 말고 `disabled`/`aria-disabled` 로 함께 전달.
- **헤어라인**: 순수 장식 구분선은 대비 요구 없음(Lc 15 권장). 하지만 **입력칸·토글·탭의 경계처럼 "구성요소를 알아보는 데 필요한" 선은 1.4.11 의 3:1** — 현재 `--line`(1.34:1)을 입력 테두리로 쓰면 실패. 입력칸은 테두리 0.47 알파 또는 배경면(surface-2) 대비·밑줄 두께로 식별되게.
- 다크 모드에서 WCAG 와 APCA 의 판정이 크게 갈린다. 법적 기준(KWCAG·WCAG 2.2)은 비율이므로 비율로 합격선을 지키고, APCA 는 "읽기 편함" 목표치로 병행하는 것이 현실적이다.

### Gaps
- Vercel(Geist)·Apple(웹)의 보조 텍스트 실제 값은 이번에 추출하지 못했다(Geist 페이지는 CSS가 동적으로 로드되어 실패). Apple 은 HIG 의 4.5:1 규정만 확인.
- WCAG 2.2 에서 플레이스홀더를 1.4.3 대상 텍스트로 명시한 원문은 확인하지 못했다.

## 2. 색각이상(CVD) — 한국식 빨강↑/파랑↓는 안전한가

### Takeaway
한국 남성 5.9%·여성 0.4%가 색각이상이고 대부분 적록 계열이다. **빨강/파랑 대비는 적록 색각이상(protan·deutan)에서도 ΔE00 42–54로 뚜렷이 갈리지만, 미국식 빨강/초록은 deutan 에서 ΔE00 1–6으로 사실상 같은 색이 된다.** 다만 KOSAI 의 up/down 은 **밝기가 거의 같아(휘도비 1.04)** 흑백 인쇄·전색맹·저대비 화면에서는 구별되지 않고, protan 에게 up 빨강은 어두운 올리브(#544c2d)로 보여 본문 회색과 헷갈린다 → **색 + 부호(+/−) + 화살표(▲▼) 3중 표기**가 필수.

### Cited Findings
- "국내에서는 남성의 5.9%, 여성의 0.4%가 색각이상"; 녹색계열이 가장 흔하고 적색계열이 다음, 청색계열·완전색맹은 매우 드묾 — [질병관리청 국가건강정보포털](https://health.kdca.go.kr/healthinfo/biz/health/gnrlzHealthInfo/gnrlzHealthInfo/gnrlzHealthInfoView.do?cntnts_sn=1469)
- KWCAG 2.2 5.4.1 "색에 무관한 콘텐츠 인식"(색만으로 정보를 전달하지 않기)이 33개 검사항목에 포함 — [KWCAG 2.2](https://a11ykr.github.io/kwcag22/)
- 시뮬레이션 방법: Machado, Oliveira, Fernandes (2009) 생리학 기반 CVD 시뮬레이션 행렬 — [Machado et al. 2009](https://www.inf.ufrgs.br/~oliveira/pubs_files/CVD_Simulation/CVD_Simulation.html)

### Inferences
- 빨강/파랑 관례는 적록 색각이상에 **우연히 유리한 선택**이다. 색상 자체를 바꿀 필요는 없다. 바꿔야 할 것은 "색만으로" 방향을 알리는 자리다.
- 표·목록의 등락률은 **항상 부호를 붙인다**(+3.45% / −1.20%, 마이너스는 하이픈 대신 U+2212 "−" 권장 — 스크린리더 발음은 아래 5절 검증 항목). 헤드라인 숫자·스파크라인 옆에는 ▲▼ 를 덧붙이되 `aria-hidden` 으로 숨기고 읽기용 "상승/하락" 텍스트를 따로 둔다.
- 차트: 두 계열을 색으로만 나누지 말고 선 모양(실선/점선)·직접 라벨을 쓴다. 등락 배경칩(`--up-bg` 8% 알파)은 휘도 차가 거의 없으므로 글자색·부호가 주된 신호여야 한다.
- 흑백 인쇄(리포트 PDF 저장 시)에서 up/down 은 같은 회색이 된다 → 인쇄 스타일에서도 부호가 남는지 확인.

### Gaps
- 한국인의 protan/deutan/tritan 세부 비율 1차 통계는 찾지 못했다(질병관리청은 서열만 제시).
- Machado 행렬은 선형 RGB 적용 여부에 따라 결과가 약간 다르다(여기선 선형 RGB). 실제 사용자 검증은 아님.

## 3. 키보드·포커스·터치 타깃

### Takeaway
스테이징 Home/stock/Reports 에 **`:focus-visible` 규칙이 0개, 건너뛰기 링크 없음, `outline:0` 1곳**이다(브라우저 기본 링에 의존). 프리미엄 사이트다운 링은 "2px 실선 잉크 + 2px 간격" 하나로 통일하면 되고, 터치 타깃은 법적 하한 24px(WCAG AA)·KWCAG 6mm 대각선이 아니라 **Apple 기본 44pt 를 목표**로 잡는다.

### Cited Findings
- WCAG 2.2: 2.4.1(A) 반복 블록 건너뛰기 수단, 2.4.7(AA) 키보드 포커스 표시가 보이는 모드, **2.4.11(AA, 2.2 신규) 포커스 받은 구성요소가 작성자 콘텐츠(고정 헤더 등)에 완전히 가려지지 않을 것**, 2.4.13(AAA) 포커스 표시 영역이 "구성요소 둘레 2 CSS px 두께 이상 + 포커스 전후 3:1" — [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- 2.5.8 Target Size (Minimum, AA): 포인터 타깃 24×24 CSS px 이상. 예외: 간격(24px 지름 원을 각 타깃 중심에 놓았을 때 겹치지 않으면 통과), 동등 대안, 문장 속 인라인 링크, UA 기본 컨트롤, 필수 — [W3C Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). 2.5.5(AAA)는 44×44 — [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- Apple HIG: iOS/iPadOS 기본 컨트롤 **44×44pt, 최소 28×28pt**; macOS 28/20pt; "컨트롤 사이 간격도 크기만큼 중요" — [Apple HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- Android 접근성 검사기: 터치 타깃 48×48dp 권장 — [Google Accessibility Scanner 도움말](https://support.google.com/accessibility/android/answer/7101858)
- KWCAG 2.2 6.1.3 조작 가능: "모든 콘트롤은 대각선 방향의 길이를 6.0mm 이상으로 제공하는 것이 바람직하다"; 6.1.2 "초점은 논리적으로 이동해야 하며, 시각적으로 구별할 수 있어야 한다"; 6.4.1 반복 영역 건너뛰기 — [KWCAG 2.2](https://a11ykr.github.io/kwcag22/)
- HTML `<dialog>` 의 `showModal()` 은 바깥을 inert 로 만들고 Esc 로 닫힌다 — [MDN dialog](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/dialog)
- [저장소 실측] 스테이징 Home 의 고정 높이 컨트롤: 30px×3, 32, 36, 38, 40×2, 44×4, 48×1.

### Inferences
- **포커스 링 규격(제안)**: `:focus-visible{outline:2px solid var(--ink);outline-offset:2px;border-radius:inherit}` — 라이트 17.4:1, 다크 16.4:1 로 2.4.13(AAA)까지 충족. 색 배경(등락칩·검정 단추) 위에서는 `box-shadow:0 0 0 2px var(--bg),0 0 0 4px var(--ink)` 이중 링. `:focus` 에서 outline 을 지우는 규칙(`outline:0`)은 `:focus:not(:focus-visible)` 로 한정.
- **건너뛰기 링크**: 헤더 첫 요소로 `<a class="skip" href="#main">본문 바로가기</a>` — 포커스될 때만 보이게. KWCAG 6.4.1 심사에서 가장 먼저 보는 항목.
- **고정 헤더와 2.4.11**: 투명 sticky `.nav` + 상하 12px 띠(`#kosEdgeTop/Bot`) 때문에 Tab 으로 이동한 요소가 헤더 밑에 숨을 수 있다 → `html{scroll-padding-top:헤더높이+8px}`. 띠는 `pointer-events:none` 이므로 포커스를 가리지는 않지만 확인 필요.
- **탭 순서**: 로고 → 건너뛰기 → 주 메뉴 → 검색 → 테마 → 계정 순. 모바일 메뉴(`.mmenu`)·업종 시트가 열리면 `<dialog>`/`inert` 로 뒤를 잠그고, Esc 로 닫고, 닫힌 뒤 여는 단추로 포커스를 되돌린다. 로그인 가림창(`.kg-*`)도 같은 규칙.
- **터치 타깃 적용**: 탭 스트립(현재 30–36px) → 높이 44px(글자 크기는 그대로, 패딩으로). 표 행 전체가 링크라면 행 높이 44px 이상(데이터 밀도가 문제면 40px + 행 간 간격으로 24px 원 테스트 통과). 아이콘 단추(테마·관심종목 별) → 시각 크기 20–24px, **히트 영역 44×44**(패딩 또는 `::after` 확장). 인라인 링크는 2.5.8 예외. iOS 사파리에서 1 CSS px ≈ 1pt 이므로 44pt ≈ 44 CSS px(추정).
- KWCAG 6mm 대각선은 휴대폰 CSS px 로 한 변 약 23px 수준(390px 폭 ≈ 71.5mm 기준 계산, 추정) — WCAG 24px 와 거의 같은 "최소선"이지 목표가 아니다.

### Gaps
- 실제 키보드 순회·포커스 가림 여부는 이 환경에서 브라우저로 확인하지 않았다(정적 grep 결과만).

## 4. 모션 선호 — 부드러운 스크롤·View Transitions·등장 효과

### Takeaway
lenis 는 이미 "움직임 줄이기·터치"에서 스스로 꺼지지만, **CSS 의 reduced-motion 규칙은 `.mmenu` 애니메이션 하나뿐이고 `@view-transition{navigation:auto}` 는 조건 없이 켜져 있다.** 크로스페이드는 위험이 낮은 편이지만, 확대·슬라이드·패럴랙스·자동 반복은 모두 `prefers-reduced-motion` 뒤로 보내는 것이 규칙이다.

### Cited Findings
- WCAG 2.3.3 Animation from Interactions(AAA): 상호작용이 일으키는 모션 애니메이션은 필수 요소가 아니면 끌 수 있어야 한다 — [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- Apple HIG: 과도한 움직임은 "주의 산만, 어지럼증, 경우에 따라 발작"을 일으킬 수 있고, Reduce Motion 이 켜지면 "확대·축소·스케일·주변부 움직임을 포함한 자동·반복 애니메이션을 줄여라" — [Apple HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- Chrome 문서: `@media (prefers-reduced-motion){::view-transition-group(*),::view-transition-old(*),::view-transition-new(*){animation:none!important}}` 로 끌 수 있으나, "reduced motion 은 움직임 없음이 아니다" — 관계를 표현하는 더 약한 애니메이션으로 대체하는 선택지도 제시 — [Chrome: Same-document view transitions](https://developer.chrome.com/docs/web-platform/view-transitions/same-document)
- `prefers-reduced-motion` 은 OS 설정을 CSS 로 노출 — [MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion); DevTools 에서 에뮬레이트 가능 — [Chrome DevTools: Emulate CSS media features](https://developer.chrome.com/docs/devtools/rendering/emulate-css)
- KWCAG 6.3.1: 초당 3–50회 깜빡임·번쩍임 금지; 6.2.2 정지 기능 제공(자동 변경 콘텐츠) — [KWCAG 2.2](https://a11ykr.github.io/kwcag22/)
- [저장소 실측] 스테이징 CSS 의 reduced-motion 규칙: `@media (prefers-reduced-motion:reduce){.mmenu.open{animation:none}}` 1개 + JS 쪽 matchMedia 1개(lenis 끄기).

### Inferences
- **전정기관 자극 요소**(위험 순): 스크롤 연동 패럴랙스·확대(줌), 화면 전체 슬라이드 전환, 스크롤 가로채기(관성 스크롤 포함), 무한 반복 배경 움직임(프리즘·그라디언트 흐름), 큰 면적 회전. 불투명도만 바뀌는 짧은 크로스페이드(≤250ms)는 가장 약한 축.
- 규칙 제안: (1) `@media (prefers-reduced-motion:reduce){*,*::before,*::after{animation-duration:.01ms!important;animation-iteration-count:1!important;transition-duration:.01ms!important;scroll-behavior:auto!important}}` 를 공통 CSS 에; (2) View Transitions 는 reduced 에서 `animation:none` 또는 120ms 이하 페이드로; (3) 등장(reveal) 효과는 콘텐츠를 **처음부터 보이게** 두고 모션만 얹는 방식(모션이 꺼지면 opacity 0 에 갇히지 않도록); (4) 시세 숫자 깜빡임(틱 하이라이트)은 1회·300ms 이내, 초당 3회 초과 금지.
- 사이트 안에 "모션 줄이기" 토글(테마 단추 옆)을 두면 OS 설정을 모르는 사용자도 끌 수 있다 — 2.3.3 을 넘어서는 배려.

### Gaps
- 크로스페이드 자체가 전정 증상을 유발한다는 정량 연구는 찾지 못했다(위 위험 순서는 Apple 가이드의 범주에 근거한 추론).

## 5. 한국어 접근성 — KWCAG 2.2, 인증마크, 스크린리더 현실

### Takeaway
국내 법적 기준은 **KWCAG 2.2(KS X OT0003:2022, 4원칙·14지침·33검사항목)** 이고 수치 기준은 WCAG 와 같다(4.5:1 등). 2.1 대비 10개 항목이 새로 들어왔다(문자 단축키, 고정된 참조 위치, 포인터 관련 4개, 도움 정보, 접근 가능한 인증, 반복 입력). 스크린리더는 **국내 PC 는 센스리더가 우세, 모바일은 VoiceOver·TalkBack** — 원/억/조와 %·▲▼ 읽기는 공식 자료가 없어 실측 검증이 필요하다.

### Cited Findings

### Inferences
- **인증마크**: 과기정통부 지정 인증기관의 "웹 접근성 품질인증"은 KWCAG 2.2 기준 전문가 심사 + 사용자 심사로 알려져 있다. 무료 서비스인 지금 KOSAI 에 의무는 불명확하나, 유료화(법인·사업자의 서비스 제공) 시점에는 장애인차별금지법상 전자정보 접근 제공 의무 대상인지 **변호사 확인 필요**(CLAUDE.md 의 유료화 체크리스트에 추가 권장).
- **lang**: 리포트의 영문 본문(영문 320자 예산으로 자르는 블록)은 `lang="en"` 을 컨테이너에 달아야 3.1.2 충족 — 센스리더·VoiceOver 가 영어 음성으로 전환.
- **숫자 읽기(검증 프로토콜)**: `1,234억 원`, `12.3조`, `+3.45%`, `−1.20%`(U+2212)와 `-1.20%`(하이픈), `▲2.1%`, `2026.09.26`, `PER 12.3배` 를 NVDA+Chrome, 센스리더+Chrome/Edge, VoiceOver(iOS 사파리), TalkBack(Chrome) 네 조합에서 녹음·기록. 결과가 들쭉날쭉한 기호는 시각 기호를 `aria-hidden="true"` 로 숨기고 `<span class="sr-only">상승 3.45퍼센트</span>` 처럼 읽기용 문구를 둔다. `aria-label` 은 비대화형 `<span>` 에서 무시되는 경우가 많아 sr-only 텍스트가 더 확실하다.
- **표**: 재무표·밸류에이션표는 `<caption>`(표 제목), 열 머리 `<th scope="col">`, 연도·항목 행 머리 `<th scope="row">`, 단위("단위: 억 원")는 caption 이나 머리에. 등락 셀의 색은 부호로 보완(2절).
- **차트 대체 텍스트**: SVG 에 `role="img"` + `aria-label="삼성전자 주가 1년: 5.4만→7.1만 원, 31% 상승, 최고 7월"` 같이 **요약 한 문장**, 그 아래 `<details>` 로 원자료 표. 스파크라인은 장식이면 `aria-hidden`, 의미가 있으면 요약 숫자를 텍스트로.
- **대체 텍스트 관례(국내 심사 경향)**: 로고는 서비스명만("KOSAI"), 링크 이미지는 목적지("홈으로"), 장식 이미지는 `alt=""`. 라이트/다크 로고 두 장(`.lt`/`.dk`)이 동시에 DOM 에 있으면 숨겨진 쪽이 `display:none` 이어야 두 번 읽히지 않는다.

### Gaps
- **센스리더 점유율 정량 통계**, 스크린리더별 **억·조·% 발음 방식**에 대한 공개 자료는 찾지 못했다 → 직접 실측이 필요.

- OpenWAX(NIA 자동 점검 도구)의 현재 배포 상태는 확인하지 못했다.

## 6. Core Web Vitals — 임계값과 "프리미엄 사이트" 실측

### Takeaway
합격선은 **LCP ≤ 2.5s · INP ≤ 200ms · CLS ≤ 0.1(75퍼센타일)**. 2025년 모바일에서 셋을 다 통과하는 사이트는 48%뿐이고, **떨어지는 이유는 대부분 LCP(로딩)** 다. KOSAI 같은 텍스트 중심 정적 사이트는 이미지가 아니라 **폰트·동기 데이터 스크립트**가 LCP 를 잡아먹는 구조라, 이것만 고치면 상위권에 들 수 있다.

### Cited Findings
- 2025 Web Almanac(2025년 7월 CrUX): 좋은 CWV — 모바일 **48%**(2023 36% → 2024 44%), 데스크톱 56%. 모바일 좋은 LCP **62%**, INP 77%, CLS 81%; 데스크톱 LCP 74%, INP 97%, CLS 72%. 임계값: LCP 2.5초 미만, INP 200ms 이하, CLS ≤ 0.1 — [Web Almanac 2025 Performance](https://almanac.httparchive.org/en/2025/performance)
- 같은 자료: LCP 요소가 이미지인 비율 모바일 76%·데스크톱 85.3%; LCP 이미지 형식 JPG 57%, PNG 26%, WebP 11%; 웹폰트 사용 모바일 87%; preload 사용 15–16%, preconnect 22%; **상위 1,000개 사이트의 모바일 좋은 INP 53% → 63%(2024→2025)** — [Web Almanac 2025 Performance](https://almanac.httparchive.org/en/2025/performance)

### Inferences
- "프리미엄 = 빠름"의 실제 기준: 상위 사이트도 모바일 INP 좋은 비율이 63% 수준이라, **셋 다 통과(모바일)** 만으로 전체 웹의 상위 절반, LCP ≤ 1.8s·INP ≤ 100ms·CLS ≤ 0.05 면 상위권으로 볼 수 있다(목표치는 제안).
- KOSAI 의 LCP 요소는 대개 **텍스트(리포트 제목·본문 첫 문단)** 일 것이다(이미지 히어로가 없음, 추정). 텍스트 LCP 는 폰트 로딩·렌더 차단 스크립트·JS 렌더링에 좌우된다.
- **INP 위험 지점**: 스크리너(2,682종목 필터·정렬), 검색 자동완성(stocks.js 1.1MB 를 순회), 테마 전환(전체 리페인트), lenis 가 켜진 데스크톱 휠 처리. 긴 작업(50ms+)을 `requestIdleCallback`/`scheduler.yield()` 로 쪼개는 것이 표준 처방.
- **CLS 위험 지점**: 폰트 swap(Pretendard ↔ 시스템 폴백 폭 차이), 로그인 상태에 따라 헤더 단추가 바뀌는 것(auth-state 가 늦게 그림), 페이월 덮개 삽입.

### Gaps
- **kosai.kr·네이버 증권·토스증권·Linear·Apple 의 CrUX 실측은 얻지 못했다** — PageSpeed Insights API 가 무키 일일 할당량 초과(2026-09-26). 다음 단계: CrUX API 키로 조회하거나 `PSI` 웹 UI 에서 수동 기록. kosai.kr 은 트래픽이 적어 CrUX 표본이 없을 가능성이 높다 → 자체 RUM(web-vitals 라이브러리 → analytics.js) 필요.
- 국내 금융 사이트의 CWV 통계를 모은 공개 자료는 찾지 못했다.

## 7. 한국어 폰트 전략 — Pretendard 를 어떻게 싣나

### Takeaway
**가장 큰 성능 문제다.** 스테이징 모든 페이지가 **Pretendard 전체 글리프 woff2 4벌(각 772–799KB, 합 약 3.1MB)을 `preload`** 한다. Pretendard 공식 배포의 **dynamic subset(유니코드 범위 92조각)** 으로 바꾸면 실제 종목 페이지 한 장이 굵기당 20조각·약 223KB, 첫 화면만 보면 더 적다. preload 는 0–1개로, 굵기는 2–3개로 줄인다.

### Cited Findings
- [저장소 실측] `fonts/Pretendard-Regular.woff2` 790,752B, Medium 804,544B, SemiBold 813,380B, Bold 818,524B(ExtraBold 830,488B 는 preload 안 함). 스테이징 Home·stock·Reports·brief 모두 4개를 `<link rel="preload" as="font">`, `@font-face` 는 `font-display:swap`, `unicode-range` 없음.
- Pretendard 1.3.9 배포 파일 [jsDelivr 패키지 목록에서 실측]: 정적 Regular 전체 woff2 **748KB**, KS X 1001(2,350자) 서브셋 **261KB**, 정적 Regular dynamic subset **92조각 합 1,135KB(조각 최소 3.9 / 중앙 12.9 / 최대 19.3KB)**, 가변(Variable) 전체 **2,009KB**, 가변 dynamic subset 92조각(조각 중앙 33.8KB, 합 2,888KB) — [jsDelivr: pretendard@1.3.9](https://data.jsdelivr.com/v1/package/npm/pretendard@1.3.9/flat), [pretendard-dynamic-subset.css](https://cdn.jsdelivr.net/npm/pretendard@1.3.9/dist/web/static/pretendard-dynamic-subset.css)
- [직접 계산: 위 CSS 의 unicode-range 에 실제 페이지 글자를 대조] `preview/stock/005930.html`(정적 종목 페이지) 고유 글자 505자 → **20조각 · 약 223KB/굵기**; `staging/brief.html` 405자 → 14조각 · 160KB; `staging/Home.html`(JS 렌더 전) 181자 → 10조각 · 114KB. (JS 로 그리는 글자는 미포함이라 실제는 더 많을 수 있음.)
- Google Fonts 한국어: 한국어 웹 텍스트를 분석한 머신러닝 토픽 모델로 17,000여 글리프를 **100개 조각**으로 나누어 unicode-range 로 제공, 기존 최선 방식보다 **38% 적은 바이트** — [Google Developers Blog](https://developers.googleblog.com/google-fonts-launches-korean-support/), [Google Fonts + 한국어](https://googlefonts.github.io/korean/)
- web.dev: preload 는 폰트를 일찍 발견하게 하지만 "다른 리소스를 불러올 브라우저 자원을 빼앗는" 대가가 있고 신중히 써야 함; `font-display:optional` 은 텍스트 지연 100ms 이하·swap 에 의한 레이아웃 이동 없음, `swap` 은 "레이아웃 이동이 없을 만큼 일찍 전달"할 때; WOFF2 만 쓰라; `@font-face` 는 `<head>` 에 인라인 — [web.dev Font best practices](https://web.dev/articles/font-best-practices)
- `size-adjust`·`ascent-override`·`descent-override`·`line-gap-override` 로 로컬 폴백 글꼴의 치수를 웹폰트에 맞춰 swap 시 CLS 를 줄인다; Next.js 13+·Nuxt 3 은 자동 적용 — [web.dev CSS size-adjust](https://web.dev/articles/css-size-adjust), [Chrome: Improved font fallbacks](https://developer.chrome.com/blog/font-fallbacks)

### Inferences
- **첫 방문 폰트 전송량 추정**: 현재 ≈ **3.1MB**(4벌 preload, 캐시 전). dynamic subset + 3굵기면 종목 페이지 ≈ 3 × 223KB ≈ **0.67MB**, 첫 화면(제목·요약)만이면 굵기당 10–14조각 수준. 조각은 페이지 사이에서 공유·캐시되므로 두 번째 페이지부터는 거의 0.
- **"Slow 4G" 가정(1.6Mbps) 추정**: 3.1MB 폰트만 약 15초 분량의 대역폭 — preload 가 높은 우선순위로 HTML·CSS·데이터 스크립트와 경쟁하므로 LCP 를 늦추고, swap 이 늦게 일어나 CLS 도 키운다(추정, 실측 필요).
- **굵기 수**: 400·600·700 세 개로 충분(500 은 600 으로 흡수). 또는 가변 dynamic subset 한 벌(조각이 정적의 약 2.6배이므로 굵기 3개 이상 쓸 때만 이득).
- **preload**: dynamic subset 에서는 어떤 조각이 필요한지 미리 알 수 없으므로 preload 하지 않는다. 꼭 하려면 "숫자·라틴·기본 문장부호 조각" 1개만.
- **font-display**: 본문은 `swap` + **폴백 치수 맞춤**(`@font-face{font-family:"Pretendard Fallback";src:local("Apple SD Gothic Neo"),local("Malgun Gothic");size-adjust:…;ascent-override:…}`), 장식 제목 글꼴(세리프 도입 시)은 `optional`.
- **대안 — 사이트 전용 서브셋**: 2,682 종목명 + 리포트 본문 전체의 사용 글자를 모아 `pyftsubset` 으로 1벌 생성하면 KS X 1001(261KB)보다 작을 가능성(추정 1,500–2,000자). 다만 새 글자가 나오면 깨질 위험이 있어 dynamic subset 이 운영상 안전.
- 자체 호스팅 유지가 맞다(GitHub Pages 동일 출처, 서드파티 연결 없음). CSS 는 공식 `pretendard-dynamic-subset.css` 를 저장소로 복사해 경로만 `../fonts/` 로.

### Gaps
- 폴백 글꼴(Apple SD Gothic Neo·맑은 고딕)과 Pretendard 의 정확한 `size-adjust` 값은 계산하지 않았다(capsize/fontaine 로 산출 필요).
- KOSAI 페이지의 실제 LCP·CLS 에 폰트가 기여하는 몫은 실측하지 않았다.

## 8. 이미지·JS·Firebase 예산 — 효과 라이브러리 판정

### Takeaway
효과 JS 는 문제가 아니다(lenis 5.7KB gz). **문제는 모든 페이지에 붙는 Firebase(스테이징 약 178KB gz — Firestore 111KB 포함)와 종목 페이지의 동기 데이터 스크립트(약 352KB gz, 원본 1.9MB)** 다. GSAP+ScrollTrigger(46KB gz)는 랜딩 한정, three.js(170KB gz)는 KOSAI 에선 불가 판정.

### Cited Findings
- [저장소·CDN 실측, gzip -9]
  - 효과: `lenis.js` 19.0KB → **5.7KB gz**(npm lenis 1.3.4 min 4.7KB gz), `smooth-scroll.js` 2.7KB gz, 저장소 루트 `gsap-min.js` **28.3KB gz** + `scrolltrigger-min.js` **18.0KB gz** = 46KB gz, three.js r169 `three.module.min.js` 687KB → **169.6KB gz** — [jsDelivr three@0.169.0](https://cdn.jsdelivr.net/npm/three@0.169.0/build/three.module.min.js), [jsDelivr gsap@3.13.0](https://cdn.jsdelivr.net/npm/gsap@3.13.0/dist/gsap.min.js), [jsDelivr lenis@1.3.4](https://cdn.jsdelivr.net/npm/lenis@1.3.4/dist/lenis.min.js)
  - Firebase 10.12.2(gstatic): app **22.4KB gz**, auth **39.7KB gz**, functions 4.5KB gz, **firestore 111.0KB gz** — [gstatic firebase-firestore.js](https://www.gstatic.com/firebasejs/10.12.2/firebase-firestore.js). `staging/auth-state.js` 가 auth·**firestore**·functions 를 정적 import 하고 모든 스테이징 페이지 꼬리에 `type="module"` 로 붙음 → 약 **178KB gz**(실사이트 루트 auth-state 는 firestore 없음 ≈ 67KB gz).
  - 자체 모듈(gz): staging auth-state 11.5, demo-backend 11.4(스테이징 전용), analytics 5.7(`<head>` 동기), auth-guard 4.5, paywall 2.3, watchlist 2.2.
  - 데이터: `data/stocks.js` 1,139KB → **173KB gz**, `reports-index.js` 552KB → **136KB gz**, `valuation.js` 247KB → 43KB gz. 스테이징 stock.html 은 셋을 **본문 중간(47% 지점)에 동기 `<script>`** 로, Home 은 앞 둘을 68% 지점에 로드.
  - 이미지: `assets/og-image.png` 1200×630, **213KB**; `prism-env.png` 14KB; `prism-blender.jpg` 10.5KB.
- LCP 이미지 형식은 여전히 JPG·PNG 가 대부분(WebP 11%) — [Web Almanac 2025 Performance](https://almanac.httparchive.org/en/2025/performance)

### Inferences
- **판정**
  - lenis(5.7KB gz): **유지**. 이미 터치·reduced-motion 에서 꺼짐. 단, 데스크톱 INP 에 휠 핸들러가 끼는지 한 번 측정.
  - GSAP+ScrollTrigger(46KB gz): **랜딩(index.html)에만**, `defer`, reduced-motion 이면 로드 자체를 건너뛰기. 리포트·종목 페이지에는 CSS `animation-timeline:view()`/IntersectionObserver(0KB)로 충분.
  - three.js(170KB gz + WebGL GPU 비용): **불가**. 프리즘 효과는 이미 14KB PNG 로 해결된 상태 — 정지 이미지·CSS 그라디언트 유지. 랜딩 히어로 한정 실험이라도 "지연 로드 + 저전력·reduced-motion 차단 + 정지 폴백"이 조건.
- **Firebase**: 로그인 상태 표시만 필요한 페이지(브리핑·리포트·종목)에 Firestore·Functions 를 싣지 말고 **동적 `import()`** 로 필요한 순간(관심종목 저장·결제)에만. 헤더의 로그인 표시는 저장소에 이미 있는 `auth-hint.js` 식 로컬 힌트로 먼저 그리고 auth 는 `requestIdleCallback` 뒤에 → 첫 로드 JS ≈ 67KB → 목표 ≤ 40KB(auth 만 지연).
- **데이터 스크립트**: 종목 상세의 글은 이미 정적 HTML(`stock/{ticker}.html`, `stock_page.py`) 방향이므로, 전 종목 1.1MB `stocks.js` 는 검색창에 **포커스할 때** 불러오도록. 리포트 목록·스크리너처럼 전체 데이터가 필요한 페이지만 `defer` 로.
- `analytics.js`(5.7KB gz)는 `<head>` 동기 → `defer` 또는 `async`.
- **이미지 예산**: OG 1200×630 은 규격 그대로 두되 **≤ 100–150KB**(PNG8 양자화 또는 JPEG q80; OG 크롤러 호환 때문에 AVIF/WebP 는 OG 에 쓰지 않음 — 업계 통용 관행, 이번에 1차 출처 미확인). 본문 히어로 이미지를 쓰게 되면 AVIF ≤ 100KB(모바일 폭 기준)·WebP 폴백·`width/height` 지정·LCP 이미지만 `fetchpriority="high"`, 나머지 `loading="lazy"`. 차트는 SVG 인라인(2–10KB).

### Gaps
- gstatic·GitHub Pages 의 실제 brotli 전송 크기는 재지 않았다(gzip -9 추정치).
- lenis 가 INP 에 주는 영향은 측정하지 않았다.

## 9. 도구 — 무엇으로 지키나

### Takeaway
KOSAI 는 이미 `check_all.sh` 로 "되돌아오지 않게" 막는 문화가 있다. 같은 방식으로 **대비 토큰 검사(스크립트)·axe-core(Playwright)·Lighthouse CI 예산** 세 개를 넣으면 이 문서의 목표치가 기억이 아니라 검사로 지켜진다.

### Cited Findings
- APCA 계산 기준과 Lc 수준표 — [APCA in a Nutshell](https://git.apcacontrast.com/documentation/APCA_in_a_Nutshell.html)
- DevTools 에서 `prefers-reduced-motion`·색 구성 등 미디어 기능 에뮬레이트 — [Chrome DevTools: Emulate CSS media features](https://developer.chrome.com/docs/devtools/rendering/emulate-css)
- 도구 원천: [Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci), [@axe-core/playwright](https://www.npmjs.com/package/@axe-core/playwright), [WebPageTest](https://www.webpagetest.org/)

### Inferences
- `scripts/check_contrast.py`(가칭): 이번 조사의 계산 코드(WCAG 비율 + APCA + 알파 합성)를 옮겨, 토큰 조합별 합격선(본문 7:1·보조 4.5:1·입력 테두리 3:1, APCA 는 경고만)을 `check_all.sh` 에 연결.
- Playwright + axe-core: 스테이징 22장 × 라이트/다크 × reduced-motion 에서 `color-contrast`, `region`, `skip-link`, `target-size` 규칙 위반 0.
- Lighthouse CI: `budgets.json` 에 font ≤ 300KB, script ≤ 150KB(gz), 총 ≤ 600KB, LCP ≤ 2.5s(모바일 에뮬), CLS ≤ 0.05 를 걸고 GitHub Actions 에서 표본 5장(Home·stock 대표 2·brief·Reports).
- 실측(RUM): `web-vitals` 로 LCP·INP·CLS 를 analytics.js 이벤트로 보내면 CrUX 표본이 없는 규모에서도 75퍼센타일을 볼 수 있다.
- CVD: Chrome DevTools "Emulate vision deficiencies" + 이번 계산 스크립트로 차트 색 추가 시 ΔE00 ≥ 20(protan/deutan) 검사.

### Gaps
- OpenWAX·국내 인증기관의 자동 점검 도구 최신판은 확인하지 못했다.

### 우선순위 권고

1. **[성능·최우선] 폰트 교체** — Pretendard 4벌 전체 preload(≈3.1MB)를 **공식 dynamic subset(unicode-range 92조각)** 으로 바꾸고 preload 를 지운다. 굵기는 400/600/700 셋. 종목 페이지 한 장 추정 ≈ 0.67MB → 페이지 이동 시 거의 0. `comp_common.CSS`·`stock_page.py` 의 `@font-face` 한 곳만 고치면 스테이징·정적 종목 페이지가 같이 바뀐다.
2. **[성능] Firebase 다이어트** — `staging/auth-state.js` 의 Firestore(111KB gz)·Functions 정적 import 를 필요한 순간의 `import()` 로. 로그인 표시는 로컬 힌트로 먼저 그리고 auth 는 유휴 시간에. 목표: 콘텐츠 페이지 첫 로드 JS ≤ 100KB gz.
3. **[접근성] 보조 텍스트 토큰 올리기** — 라이트 `--ink-55` 0.55→**0.62**(3.99→5.03:1), 다크 `--ink-72` 0.72→**0.80**(Lc −58→−68), 다크 `--ink-55` 는 12px 이상 굵은 라벨 전용. 442개 사용처를 토큰 한 곳에서 바꾸는 일이라 비용이 거의 없다. 플레이스홀더는 ink-30 → 라이트 0.60 / 다크 0.55.
4. **[접근성] 포커스·건너뛰기** — `:focus-visible` 2px 잉크 링 + offset 2px 를 공통 CSS 에, "본문 바로가기" 링크, `scroll-padding-top` 으로 고정 헤더 가림(2.4.11) 방지. 모바일 메뉴·업종 시트·로그인 가림창은 `<dialog>`/`inert` + Esc + 포커스 복귀.
5. **[접근성·금융] 등락 표기 규칙 고정** — 모든 등락 숫자에 +/− 부호(U+2212), 헤드라인·요약엔 ▲▼(aria-hidden) + sr-only "상승/하락". 색만으로 방향을 알리는 칩·차트 금지. 다크 등락색은 #ff8a7f/#8cb2ff 로 밝히는 안을 시안에서 비교.
6. **[모션] reduced-motion 공통 블록** — 모든 animation/transition/scroll-behavior 를 끄는 블록 + `@view-transition` 을 `prefers-reduced-motion:no-preference` 안으로(또는 reduced 에서 `animation:none`). reveal 효과는 "기본 보임" 원칙. 사이트 내 "모션 줄이기" 토글은 선택.
7. **[성능] 데이터 스크립트 지연** — 정적 종목 페이지(`stock/{ticker}.html`)로의 이전을 서두르고, `stocks.js`(1.1MB)는 검색창 포커스 때, `analytics.js` 는 `defer`. 스테이징 stock.html 의 본문 중간 동기 스크립트 3개는 LCP 의 직접 원인 후보.
8. **[CLS] 폴백 치수 맞춤** — Apple SD Gothic Neo·맑은 고딕 폴백에 `size-adjust`/`ascent-override` 를 계산해 적용하고, 헤더 계정 단추 자리는 로그인 여부와 무관하게 폭을 예약.
9. **[터치] 44px 규칙** — 탭 스트립·아이콘 단추·관심종목 별·표 행 링크의 히트 영역을 44×44 로(시각 크기는 유지). 24px 원 간격 테스트는 최소선일 뿐 목표가 아니다.
10. **[한국어] lang·표·차트** — 영문 리포트 블록에 `lang="en"`, 재무표에 `<caption>`·`scope`, 차트에 한 문장 요약 + 원자료 표. 숫자 읽기(억·조·%·−·▲)는 NVDA·센스리더·VoiceOver·TalkBack 에서 **직접 녹음 검증** 후 sr-only 문구 규칙을 정한다(공개 자료 없음).
11. **[검사로 지키기] check_all.sh 에 셋 추가** — ① 대비 토큰 검사(WCAG 합격선 + APCA 경고), ② Playwright+axe-core(22장 × 라이트/다크), ③ Lighthouse CI 예산(font ≤ 300KB · script ≤ 150KB · LCP ≤ 2.5s · CLS ≤ 0.05). "기억 대신 검사가 막는다"는 저장소 원칙을 접근성·성능에도 적용.
12. **[측정] RUM 과 CrUX** — `web-vitals` 로 LCP·INP·CLS 를 analytics 로 수집(트래픽이 적어 CrUX 표본이 없을 가능성). 유료화 전에 KWCAG 2.2 전문가 점검(인증마크 취득 여부는 법적 의무 확인 후 결정 — 유료화 체크리스트에 추가).
