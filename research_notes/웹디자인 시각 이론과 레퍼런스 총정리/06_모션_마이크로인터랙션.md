# 모션 · 마이크로인터랙션 — 고급 웹 제품의 움직임 체계 (KOSAI 용)

> 조사일 2026-09-26. 1차 출처(디자인 시스템 원본 토큰 파일 · 표준 명세 · 브라우저 벤더 블로그 · NN/g · 설계자 본인 글)를 우선했다.
> **자체 실측** 표시는 이 조사에서 직접 잰 값이다. 2026-09-26 에 각 사이트 첫 페이지 HTML 과 거기 걸린 CSS(최대 12개)를 받아 `transition`·`animation` 선언의 지속 시간과 `cubic-bezier` 를 셌다. JS 가 나중에 넣는 스타일은 빠져 있으니 "그 사이트가 CSS 에 박아 둔 값"으로만 읽어야 한다.
> 곡선 진행률(예: "25% 시점에 77% 진행")은 3차 베지어를 수치로 풀어 계산한 값이다(추정 아님, 계산).

## 1. 원칙 — Material 3 · Apple HIG · IBM Carbon · Kowalski · Rauno, 그리고 '고급'과 '싸구려'를 가르는 것

### Takeaway
주요 시스템과 설계자들이 같은 말을 한다. 목적 있는 움직임만 쓰고, 짧게(대략 300ms 아래) 끝내고, 시작은 빠르고 끝은 부드럽게(ease-out), 튕김은 거의 없이, 언제든 끊을 수 있게 만든다. 자주 하는 동작일수록 덜 움직인다. 고급스러움은 움직임을 **더하는** 데서가 아니라 **빼고 다듬는** 데서 나온다.

### Cited Findings
**Apple HIG (Motion) 원문**
- "Add motion purposefully, supporting the experience without overshadowing it." / "Don't add motion for the sake of adding motion. Gratuitous or excessive animation can distract people and may make them feel disconnected or physically uncomfortable." — [Apple HIG Motion](https://developer.apple.com/design/human-interface-guidelines/motion)
- "Aim for brevity and precision in feedback animations… it tends to feel lightweight and unobtrusive." — [Apple HIG Motion](https://developer.apple.com/design/human-interface-guidelines/motion)
- "In apps, generally avoid adding motion to UI interactions that occur frequently." / "Let people cancel motion… don't make people wait for an animation to complete." / "Make motion optional… avoid using it as the only way to communicate important information." — [Apple HIG Motion](https://developer.apple.com/design/human-interface-guidelines/motion)
- WWDC23 스프링 지침: 기본은 bounce 0("the most versatile"), 15% 는 "doesn't feel very bouncy yet… a little more brisk", 30% 부터 튕김이 느껴지고, **0.4 넘으면 UI 에는 과장**. 스프링은 속도를 이어받아 제스처 인계·중간 끊김이 자연스럽다. stiffness = (2π ÷ duration)², mass = 1 — [WWDC23 Animate with springs](https://developer.apple.com/videos/play/wwdc2023/10158/)

**IBM Carbon — productive vs expressive**
- Productive = 일을 끝내게 돕는 효율적 움직임. Expressive = 감정·브랜드를 전하는 두드러진 움직임(중요한 순간에만) — [Carbon Motion](https://carbondesignsystem.com/elements/motion/overview/)
- 원본 토큰 파일 값: 지속 시간 fast-01 **70** ms(버튼·토글) · fast-02 **110**(작은 요소 페이드) · moderate-01 **150**("Default transition speed") · moderate-02 **240**(펼침·토스트) · slow-01 **400**(큰 펼침·중요 알림) · slow-02 **700**(배경 어둡게·큰 히어로) — [carbon/packages/motion/src/dtcg/motion.json](https://github.com/carbon-design-system/carbon/blob/main/packages/motion/src/dtcg/motion.json)
- 곡선: productive standard `(0.2,0,0.38,0.9)` · entrance `(0,0,0.38,0.9)` · exit `(0.2,0,1,0.9)` / expressive standard `(0.4,0.14,0.3,1)` · entrance `(0,0,0.3,1)` · exit `(0.4,0.14,1,1)`. standard 는 "화면 안에서 움직이는 요소"용, entrance 는 "화면에 들어오는 요소"용 — [motion.json](https://github.com/carbon-design-system/carbon/blob/main/packages/motion/src/dtcg/motion.json)
- ⚠ carbondesignsystem.com 페이지를 요약 도구로 읽었을 때는 slow-01 350 · slow-02 500 과 다른 expressive 곡선이 나왔다. 저장소의 원본 토큰 파일(위)이 400/700 이므로 원본을 따른다 — [Carbon Motion 페이지](https://carbondesignsystem.com/elements/motion/overview/) vs [motion.json](https://github.com/carbon-design-system/carbon/blob/main/packages/motion/src/dtcg/motion.json)

**Material 3**
- 곡선: standard `(0.2,0,0,1)` · standard decelerate `(0,0,0,1)` · standard accelerate `(0.3,0,1,1)` · emphasized decelerate `(0.05,0.7,0.1,1)` · emphasized accelerate `(0.3,0,0.8,0.15)` · emphasized 는 2구간 경로 — [M3 Motion 토큰(Android 문서)](https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md)
- 지속 시간: short1–4 = 50/100/150/200 · medium1–4 = 250/300/350/400 · long1–4 = 450–600 · extra-long1–4 = 700–1000 ms — [같은 문서](https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md)
- M3 Expressive 스프링(감쇠비/강성): fast spatial 0.9/1400 · default spatial 0.9/700 · slow spatial 0.9/300 · fast effects 1.0/3800 · default effects 1.0/1600 · slow effects 1.0/800. **effects(색·투명도)는 감쇠비 1.0 = 튕김 없음**, spatial(위치·크기)만 0.9 — [같은 문서](https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md)

**Emil Kowalski (Sonner·Vaul 제작자)**
- "Your animations should also usually be shorter than 300ms." 드롭다운 180ms 가 400ms 보다 반응이 빠르게 느껴진다 — [Great Animations](https://emilkowal.ski/ui/great-animations) · [You Don't Need Animations](https://emilkowal.ski/ui/you-dont-need-animations)
- "Never animate keyboard initiated actions." 하루 수백 번 쓰는 Raycast 는 애니메이션이 0. "A hover effect is nice, but if used multiple times a day, it would likely benefit the most from having no animation at all." — [You Don't Need Animations](https://emilkowal.ski/ui/you-dont-need-animations)
- ease-out 이 기본("starts fast… gives the impression of a quick response"), CSS 기본 곡선은 "usually not strong enough" → 더 센 사용자 곡선 권장 — [Great Animations](https://emilkowal.ski/ui/great-animations) · [7 Practical Animation Tips](https://emilkowal.ski/ui/7-practical-animation-tips)
- `scale(0)` 에서 시작 금지(0.93 이상), 누름 `:active` 에 `scale(0.97)`, 움직임은 나온 자리(transform-origin)에서, 툴팁은 하나가 열린 뒤 옆 툴팁은 지연·애니메이션 0 — [7 Practical Animation Tips](https://emilkowal.ski/ui/7-practical-animation-tips)

**Rauno Freiberg (Vercel) — "Invisible Details of Interaction Design"(2023-07)**
- 자주 쓰는 동작의 애니메이션은 반복될수록 인지 부담이 되고 느리게 느껴진다. 명령 메뉴 예: "It's tempting to throw an opacity and scale fade on the overlay. But if we… consider the interaction frequency being hundreds of times a day…" — [rauno.me](https://rauno.me/craft/interaction-design)
- 움직임은 공간 관계(어디서 왔는가)를 전하고, 끊을 수 있어야 한다 — [rauno.me](https://rauno.me/craft/interaction-design)
- Vercel Web Interface Guidelines(같은 계열): "Never `transition: all`", "Compositor-friendly(`transform`·`opacity`)", "Interruptible", "Correct transform origin", "Only animate when it clarifies cause & effect or adds deliberate delight", 구현 선호 CSS > WAAPI > JS 라이브러리, 5초 넘는 자동 재생엔 정지 단추 — [Vercel Web Interface Guidelines](https://vercel.com/design/guidelines)

**토스(한국 금융)**
- 인터랙션을 넣는 기준은 "더 명확한 피드백, 사용성 개선". 정적 UI 로 충분하면 넣지 않는다. 대출 심사 로딩(20~30초)에 실시간 상품 정보를 보여 주자 이탈률·결과 도달률이 "소폭" 개선. 반면 전체 탭 사이드바·신분증 인식·카드 발급 화면 인터랙션은 지표 변화 없음. easing 을 `spring.quick`·`bezier.expo` 같은 이름의 토큰으로 iOS·Android·Web 에 공통화(Rally 라이브러리) — [토스 테크 "인터랙션, 꼭 넣어야 해요?"(2023-09-07)](https://toss.tech/article/interaction)

### Inferences
- **고급으로 읽히는 것**: 짧음(≤300ms) · 강한 ease-out · 튕김 0(또는 ≤0.15) · 끊김 가능 · 나온 자리에서 나옴 · 적은 종류의 값이 반복(토큰) · 자주 하는 동작엔 움직임 없음. **싸구려·'AI 티'로 읽히는 것**: 500ms 넘는 길이, `linear`·브라우저 기본 `ease` 로만 된 무른 움직임, 통통 튀는 overshoot, `scale(0)` 팝, 섹션마다 떠오르는 스크롤 리빌, 카운트업·마키·타이핑 효과, 스크롤 가로채기. 위 출처들의 금지 목록을 합친 것이다.
- M3 가 색·투명도 스프링(effects)을 감쇠비 1.0 으로 둔 것은, 튕김은 '위치'에만 의미가 있고 '색'이 튕기면 이상하다는 뜻이다. KOSAI 처럼 위치 이동이 거의 없는 사이트에는 스프링 자체가 필요 없다.
- Carbon 의 productive/expressive 구분을 KOSAI 에 대면 사이트 전체가 **productive** 이고 expressive 를 쓸 자리는 없다(랜딩 첫 화면 하나를 예외로 두더라도).

### Gaps
- m3.material.io 원 페이지는 JS 로만 그려져 읽지 못했다. Android 문서의 같은 토큰으로 대신했다.
- Apple 웹사이트(apple.com)의 사내 모션 지침은 공개 문서가 없다. 실측값만 있다(2절).

## 2. 숫자 — 상호작용별 지속 시간, 고급 사이트가 실제로 쓰는 곡선, 스프링, 응답 시간 문턱

### Takeaway
UI 전환은 **100~300ms**, 넓게 잡아도 400ms 안이다. 문턱은 셋이다. 100ms(즉각으로 느낌), 400ms(Doherty · 흐름이 끊기지 않음), 1s(생각이 끊기기 시작). 고급 사이트들의 실측 최빈값도 **150 · 200 · 240 · 300 · 320ms** 에 몰려 있다. 곡선은 시작이 빠른 ease-out 계열(Stripe `(.25,1,.5,1)`, Mercury `(.2,1,.4,1)`, Vercel `(0,0,.2,1)`·`(.16,1,.3,1)`)이 주류이고, Apple 만 대칭형 `(.4,0,.6,1)` 을 많이 쓴다.

### Cited Findings
**지각·응답 문턱**
- 0.1s "the limit for having the user feel that the system is reacting instantaneously" · 1.0s "the limit for the user's flow of thought to stay uninterrupted" · 10s "the limit for keeping the user's attention focused" — [Nielsen, Response Times: 3 Important Limits (1993)](https://www.nngroup.com/articles/response-times-3-important-limits/)
- Doherty 문턱: 400ms 아래로 주고받으면 생산성이 오른다(Doherty & Thadani, IBM Systems Journal 1982) — [Laws of UX](https://lawsofux.com/doherty-threshold/)
- INP: 200ms 이하 good · 200~500 개선 필요 · 500 초과 poor. 반응은 "the next frame" 에 시각 피드백으로 보여야 한다 — [web.dev INP](https://web.dev/articles/inp)

**상호작용별 지속 시간**
- NN/g: 일반 범위 100~500ms, 체크박스·토글 같은 단순 피드백 ~100ms, 모달처럼 화면이 크게 바뀌면 200~300ms, 500ms 부터 "a real drag", 대부분 100~400ms. **들어올 때가 나갈 때보다 길다**(예: 팝업 300ms 등장, 200~250ms 퇴장). 100ms 는 "almost feels like an instantaneous jump" — [NN/g Animation Duration (Laubheimer, 2020)](https://www.nngroup.com/articles/animation-duration/)
- 로딩 표시: 최소 표시 지연 150~300ms, 한 번 보이면 최소 300~500ms 유지(깜빡임 방지) — [Vercel Web Interface Guidelines](https://vercel.com/design/guidelines)
- 스프링 라이브러리 기본값(참고): Motion(Framer Motion) 트윈 기본 0.3s(키프레임 여럿이면 0.8s), 스프링 bounce 기본 0.25 · damping 10 · mass 1 · restSpeed 0.1 · restDelta 0.01 — [Motion transitions](https://motion.dev/docs/react-transitions) · [Motion spring](https://motion.dev/docs/spring)

— 계산값(3차 베지어 수치 풀이)

**스프링 ↔ 시간 환산(계산)**
- Apple 식 stiffness=(2π/d)² 로 거꾸로 풀면 M3 spatial 스프링의 체감 길이는 fast 1400 → **168ms**, default 700 → **237ms**, slow 300 → **363ms**. effects 3800/1600/800 → 102/157/222ms. 반대로 d=0.2s → k≈987, d=0.3s → k≈439(mass 1, 튕김 0이면 임계 감쇠 c=4π/d ≈ 63/42) — 계산([WWDC23](https://developer.apple.com/videos/play/wwdc2023/10158/) 식 + 임계 감쇠 2√k 로 검산)

### Inferences
- 고급 사이트의 "기본 한 박자"는 150~200ms(Vercel · Mercury · Toss · Linear), "큰 한 박자"는 240~320ms(Stripe 내비 240/300 · Apple 헤더 240/320)다. 헌장의 120/200/280 은 이 두 무리 사이에 잘 들어간다.
- **헌장의 `--ease-out` 은 이름과 모양이 어긋난다.** `(0.2,0,0.38,0.9)` 은 Carbon 이 '화면 안에서 움직이는 요소'에 쓰는 standard 곡선이고 시작이 느리다. 전체의 25% 가 지났을 때 31% 밖에 안 움직여 CSS 기본 `ease`(41%)보다도 굼뜨다. 200ms 짜리면 첫 50ms 동안 거의 멈춰 있다. 지금 스테이징의 `(.2,.8,.2,1)`(77%)은 Stripe·expo-out 과 같은 무리이고 Emil 이 말하는 "센 ease-out" 에 해당한다. 들어오는 움직임·상태 변화에는 스테이징 곡선을 표준으로 삼는 편이 근거와 맞다.
- Apple 의 `(.4,0,.6,1)` 대칭형은 제품 사진이 크게 움직이는 마케팅 페이지용이다. 리서치 도구의 반응성 기준으로 삼기에는 느리다.
- 스프링은 제스처를 이어받아야 할 때(끌어 닫는 바텀 시트) 값어치가 있다. 클릭으로 열고 닫는 KOSAI 에는 베지어 2~3개로 충분하다.

### Gaps
- Linear 의 `--ease-out-quad` 실제 값, Stripe·Apple 의 JS 애니메이션(WAAPI·GSAP 등)은 CSS 실측에 잡히지 않았다.
- motion.dev 스프링 문서의 stiffness 기본값은 가져온 요약에 "1" 로 나와 믿기 어렵다(과거 Framer Motion 문서의 100 과 다름). 확인하지 못했다.
- "고급으로 느낀다"를 직접 잰 지각 실험(지속 시간·곡선 × 고급감 평점)은 찾지 못했다. 위 판단은 설계 지침과 실측 관행에서 끌어낸 것이다.

## 3. 스크롤 — Lenis·Locomotive, 부드러운 스크롤을 쓰는 곳과 안 쓰는 곳, CSS 스크롤 구동 애니메이션, 패럴랙스, 스크롤 리빌

### Takeaway
스크롤은 사이트에서 가장 자주 하는 입력이다. NN/g 는 속도나 방향을 바꾸는 스크롤을 사용자 통제를 해치는 것으로 본다. 목적이 분명한 방문자일수록 참을성이 적다. Lenis 는 옛 가짜 스크롤(transform 방식)보다 훨씬 덜 망가뜨리지만 대가가 있다. Safari 에서는 60fps 에 묶이고 저전력 모드에서는 30fps, iframe 위에서는 멈추고, scroll-snap 을 못 쓴다. 이번에 잰 핀테크·SaaS 7곳은 첫 HTML 에 Lenis·Locomotive 흔적이 없었다. 패럴랙스는 '재미'만 올렸고 사용성·만족도는 그대로였으며 멀미 사례가 나왔다.

### Cited Findings
**스크롤 가로채기(NN/g)**
- 정의: 스크롤의 속도나 방향을 바꾸는 패턴. "Altering the normal pace or direction of scrolling can contradict user expectations, control, and freedom." 목표 지향 방문자는 "little patience", 기기가 고장 난 줄 안 참가자도 있었다. 휴대폰에서 더 나쁘다. 권고: 기능적 가치가 있을 때만, 글 많은 구간 금지, 휴대폰 금지, 보통 스크롤과 섞을 것 — [NN/g Scrolljacking 101 (Sara Paul, 2023-08-06)](https://www.nngroup.com/articles/scrolljacking-101/)

**Lenis 자체 문서(README · KOSAI 가 쓰는 1.3.26 계열)**
- "Runs on native scroll — wraps the browser's own scroll, so position: sticky, anchor links, and accessibility keep working" — [Lenis README](https://github.com/darkroomengineering/lenis)
- 기본값 lerp 0.1 · duration 1.2s("Useless if lerp defined") · easing `(t)=>Math.min(1, 1.001 - Math.pow(2, -10*t))` · smoothWheel true · syncTouch false — [Lenis README](https://github.com/darkroomengineering/lenis)
- `respectReducedMotion` 기본 **true**. 줄임 모드면 lerp 를 1로 강제(입력과 1:1)하고 프로그램 스크롤은 즉시 이동. 설정 변경을 새로고침 없이 따라간다 — [Lenis README · Reduced motion](https://github.com/darkroomengineering/lenis)
- Limitations 원문: "no support for CSS scroll-snap", "**capped to 60fps on Safari … and 30fps on low power mode**", "smooth scroll will stop working over iframe since they don't forward wheel events". 앵커 링크는 `anchors:true` 를 켜야 동작 — [Lenis README](https://github.com/darkroomengineering/lenis)
- 실제 비판 사례: 한 개인 사이트 감사 이슈. "hijacks the site's single highest-frequency interaction (scrolling)" for every visitor, 줄임 모드 검사 없음, `autoRaf:true` 가 "a persistent requestAnimationFrame loop for the entire lifetime of every page view" 를 돌린다. 권고는 줄임 모드에서 끄기, 스크롤할 때만 rAF 돌리기 — [kollitsch.dev issue #1998](https://github.com/davidsneighbour/kollitsch.dev/issues/1998)

**쓰는 곳 · 안 쓰는 곳**
- 자체 실측: apple.com · stripe.com · vercel.com · linear.app · mercury.com · toss.im · robinhood.com 의 첫 HTML 에 `lenis`·`locomotive` 문자열 0건(JS 번들 안까지는 확인하지 않았으니 약한 증거) — 자체 실측
- KOSAI 스테이징: Lenis 1.3.26, `duration 0.6` · easing `1-(1-t)^3`, 손가락(`pointer:coarse`)·줄임 모드면 켜지 않음, **rAF 를 페이지 수명 내내 돌린다**(`function frame(t){ lenis.raf(t); requestAnimationFrame(frame); }`) — 자체 확인(`staging/smooth-scroll.js` 78–79행)

**CSS 스크롤 구동 애니메이션(`animation-timeline: scroll()/view()`)**
- Safari 26 부터 지원. 대표 쓰임은 읽기 진행 막대와 화면에 들어올 때의 요소 애니메이션. 넓은 시야를 움직이는 효과는 `@media not (prefers-reduced-motion)` 으로 감쌀 것 — [WebKit, A guide to scroll-driven animations with just CSS (2025-06-20)](https://webkit.org/blog/17101/a-guide-to-scroll-driven-animations-with-just-css/)
- Chrome·Edge 115(2023-07)부터, Safari 26(2025-09), Firefox 는 안정판 미지원. `CSS.supports("animation-timeline: scroll()")` 로 감지 — [MDN Scroll-driven animations](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll-driven_animations) (검색 요약 기준)

**패럴랙스**
- 퍼듀 연구(N=86, 43/43): 패럴랙스 쪽이 '재미'만 유의하게 높았다. 사용성·즐거움·만족·시각적 호감은 차이가 없었다. **참가자 2명이 멀미를 겪고** 사용성 문제를 보였다 — [Frederick, Purdue 학위논문 (2013)](https://docs.lib.purdue.edu/cgi/viewcontent.cgi?article=1025&context=cgttheses) · [Journal of Usability Studies 판](https://dl.acm.org/doi/abs/10.5555/2817315.2817318)
- 전정 장애 유발 요인: 화면 대비 움직임의 크기, **방향·속도 불일치(패럴랙스·스크롤재킹)**, 빠르게 먼 거리를 가는 것. 투명도·색 변화는 대체로 안전하다 — [Val Head, A List Apart (2015-09-08)](https://alistapart.com/article/designing-safer-web-animation-for-motion-sensitivity/)
- 패럴랙스·움직이는 그라데이션·배경 영상은 줄임 모드에서 **없애야 할** 장식 — [web.dev prefers-reduced-motion](https://web.dev/articles/prefers-reduced-motion)

### Inferences
- **Safari 60fps 제한이 KOSAI 에 주는 뜻:** ProMotion(120Hz) 맥북에서 보통 스크롤은 120Hz 로 돈다. 그런데 Lenis 를 켜면 휠 스크롤이 60fps 로 떨어진다. '부드럽게' 하려던 장치가 좋은 화면에서는 오히려 덜 부드러울 수 있다(README 의 제한에서 끌어낸 추론 · 실기기 확인 필요). 사장이 쓰는 아이폰은 손가락 입력이라 이미 꺼져 있어 영향이 없다.
- 리서치 사이트 방문자는 NN/g 가 말한 '목표 지향' 사용자다. 부드러운 휠은 가로채기(속도·방향 변경) 가운데 가장 약한 형태다(방향은 그대로, 멈추는 데 614ms 꼬리). 지금 조건(데스크톱 휠만 · 0.6s · 줄임 모드 끔)은 합리적인 절충이다. 다만 **rAF 를 늘 돌리는 것**은 이슈 #1998 이 지적한 바로 그 형태다. 스크롤하지 않을 때도 매 프레임 콜백이 돈다.
- 스크롤 리빌(섹션마다 아래에서 떠오름)은 두 가지 문제를 낳는다. 첫째, 글이 늦게 보인다. 둘째, 헌장이 경계하는 템플릿 느낌이 난다. 굳이 쓴다면 CSS `view()` 타임라인의 투명도만으로 하되, 헌장대로 **0건**이 맞다.
- 읽기 진행 막대(리포트 상단 2px)는 스크롤 구동 애니메이션이 가장 정당한 쓰임이다. 투명도·크기 변화만 있고, 입력을 따라가고, 정보(얼마나 읽었나)를 준다. Firefox 에서는 그냥 안 보이면 된다(점진적 향상).

### Gaps
- Awwwards 수상작 중 Lenis 사용 비율 같은 정량 자료는 찾지 못했다.
- Lenis 가 Safari 120Hz 화면에서 체감상 더 나쁜지 비교한 실험은 없다. 실기기 확인이 필요하다.
- Locomotive Scroll 의 최신판이 Lenis 위에서 다시 만들어졌다는 이야기는 1차 출처로 확인하지 못했다.

## 4. 페이지 전환 — 문서 간 View Transitions

### Takeaway
문서 간 View Transitions(`@view-transition{navigation:auto}`)는 Chrome·Edge 126+ 와 Safari 18.2+ 에서 돈다. Firefox 는 아직 안 된다(같은 문서 안의 전환만 144 부터). 명세의 기본 크로스페이드는 **250ms** 이다. 같은 출처(origin)에서만 동작하고, Chrome 은 이동이 4초를 넘으면 전환을 건너뛴다. 조용히 없어져도 괜찮은 점진적 향상이므로, 본문 크로스페이드와 고정 헤더 정도로 좁게 쓰는 것이 맞다.

### Cited Findings
- 문서 간 전환은 Chrome 126 · Edge 126 에서 출시, Safari 18.2+ 지원, Firefox 미구현. **같은 출처만**. "If a navigation takes too long–more than four seconds in Chrome's case–then the view transition is skipped with a TimeoutError." `blocking=render` 는 Core Web Vitals 영향을 재 볼 수 있을 때만 — [Chrome for Developers, Cross-document view transitions](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document)
- "WebKit for Safari 18.2 adds support for cross-document View Transitions with `@view-transition`" + `view-transition-name: auto`, View Transition Classes·Types, `pageswap`·`pagereveal` 이벤트 — [WebKit, Safari 18.2](https://webkit.org/blog/16301/webkit-features-in-safari-18-2/)
- 같은 문서 전환은 Baseline(Chrome 111 · Safari 18 · Firefox 144 — 2025-10-14). `match-element` 자동 이름은 Chrome 137 · Safari 18.4 · Firefox 144. Firefox 144 초판에는 전환 types 가 없다 — [Chrome, View transitions in 2025](https://developer.chrome.com/blog/view-transitions-in-2025)
- 명세의 UA 스타일시트: `::view-transition-group(*)` 의 `animation-duration: 0.25s` — [CSS View Transitions Level 1](https://drafts.csswg.org/css-view-transitions-1/)
- 방향이 있는 이동(다음/이전)은 `pageswap`·`pagereveal` 에서 이동 정보를 보고 전환 type 을 바꿔 준다 — [Chrome cross-document](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document)
- KOSAI 스테이징은 이미 `@view-transition{navigation:auto}` + `.kos-staging-bar{view-transition-name:kos-bar}` · `.nav{view-transition-name:kos-nav}` 로 본문만 크로스페이드한다 — 자체 확인(`scripts/comp_common.py`)

### Inferences
- 크로스페이드는 투명도만 바꾸므로 Val Head 기준으로 전정 안전 쪽이다. 줄임 모드에서도 없앨 필요는 없다. 다만 헌장 규칙("이동은 페이드로")에 맞춰 줄임 모드에서는 120ms 로 줄이거나 `animation:none` 으로 하면 된다.
- 기본 250ms 를 헌장의 200ms(`--dur-2`)로 줄이면 토큰 체계 안으로 들어온다. 헤더·띠만 이름을 붙이고, 종목 로고 같은 '공유 요소 모핑'은 하지 않는 편이 인쇄물 방향에 맞다. 모핑은 위치·크기가 움직이는 큰 동작이라 expressive 쪽이다.
- 함정: ① 같은 페이지 안에서 `view-transition-name` 이 겹치면 전환이 통째로 건너뛰어진다. 목록마다 이름을 붙일 때 조심해야 한다. ② 종목 페이지처럼 무거운 문서는 4초 제한에 걸려 전환이 사라질 수 있는데, 없어져도 무해하다. ③ 스크린숏(스냅샷)을 뜨는 동안 입력이 막힌다. 전환이 길수록 '느린 사이트'로 느껴진다. ④ `#kosEdgeTop/#kosEdgeBot` 같은 fixed 띠가 스냅샷에 포함될 때 iOS 26 사파리의 가장자리 색 샘플링과 어떻게 얽히는지는 실기기로 확인해야 한다.

### Gaps
- 문서 간 View Transitions 를 쓰는 대형 사이트 수 같은 채택 통계는 찾지 못했다(Chrome 블로그도 수치 없음).
- Safari 의 전환 시간 제한 값은 공개된 것을 찾지 못했다.

## 5. 마이크로인터랙션 목록 — 리서치 사이트에서 쓸 것 · 뺄 것, 금융 제품들의 실제

### Takeaway
금융 제품이 모션을 쓰는 곳은 **값이 바뀌는 순간**(Robinhood 의 숫자 롤링·색 번쩍임)과 **기다리는 동안**(토스 대출 심사 로딩)이다. 장식적인 진입 효과에는 쓰지 않는다. KOSAI 처럼 실시간 호가가 없고 글을 읽는 사이트라면 모션은 피드백 확인(담기·복사·탭)과 겹침 요소(메뉴·시트·툴팁)의 열고 닫기로 좁힌다. 카운트업, 차트 그려 넣기, 행 호버 애니메이션은 뺀다.

### Cited Findings
- Robinhood 는 숫자가 바뀔 때 주행 거리계처럼 굴러가는 텍스트 뷰 `ticker` 를 오픈소스로 냈다("Think about how an odometer scrolls…"). 9→1 은 9→0→1 로 짧은 쪽을 택한다 — [robinhood/ticker](https://github.com/robinhood/ticker)
- 토스: 터치 이펙트를 회색 배경에서 '눌리는 느낌의 모션'으로 바꾸자 공지 전부터 긍정 반응. 대출 심사 20~30초 로딩에 실시간 정보를 보여 주자 이탈이 소폭 줄었다 — [토스 테크](https://toss.tech/article/interaction)
- 카운트업의 접근성 문제: 스크린 리더가 그 순간의 중간값(예: 5000 으로 가는 도중의 3100)을 읽는다 → 실제 텍스트로 최종값을 두고, 줄임 모드에서는 바로 최종값으로 — [Savvas Stephanides, accessible animated counter](https://savvasstephanides.hashnode.dev/lets-create-an-accessible-animated-counter)
- 이동은 `left`·`width` 대신 `transform` 으로(레이아웃·페인트 회피) — [web.dev Animations guide](https://web.dev/articles/animations-guide)
- 그 밖의 근거(누름 `scale(.97)`·연속 툴팁 즉시 · 토글 ~100ms · 퇴장이 더 짧게 · 자주 쓰는 호버는 무애니메이션 · 자동 재생 5초 초과 정지 단추)는 1·2절의 Emil · NN/g · Vercel 인용과 같다.

| 숫자(가격·지표) | 바로 최종값, `tabular-nums` | 페이지 진입 카운트업 |
| 차트 | 바로 그려짐. 호버 크로스헤어는 즉시 따라감 | 선 그리기(draw-in)·막대 자라기 |
| 페이지 이동 | 본문 크로스페이드 200ms, 헤더 고정 | 슬라이드·줌·공유 요소 모핑 |

### Inferences
- Robinhood 의 롤링 숫자는 '실시간으로 값이 바뀐다'는 정보를 준다. KOSAI 리포트의 숫자는 정적이다. 같은 효과를 페이지 진입 때 쓰면 정보가 아니라 장식이 된다. 흉내 내면 곧 'AI 티'다.
- 차트 draw-in 은 읽기를 수백 ms 늦추고, 같은 차트를 볼 때마다 반복된다. 빈도 원칙(Emil·Rauno)에 걸린다.
- 관심 종목 담기는 KOSAI 에서 가장 '확인'이 필요한 동작이다. 로그인·Firestore 왕복이 있기 때문이다. 아이콘을 먼저 바꾸고(0.1s 문턱 안) 서버가 실패하면 되돌리는 낙관적 UI 가 INP 와 체감 모두에 맞다.

### Gaps
- Mercury·Ramp·Bloomberg 의 제품(로그인 뒤) 마이크로인터랙션은 공개 자료가 없어 확인하지 못했다. Mercury 는 마케팅 사이트 CSS 실측뿐이다.
- 카운트업이 이해·기억에 미치는 효과를 잰 실험은 찾지 못했다. 반대 근거는 접근성·빈도 원칙뿐이다.
- 복사 확인 유지 시간(1.5~2초)은 관행일 뿐, 출처가 있는 수치를 찾지 못했다.

## 6. 움직임 줄이기 · 성능 · 테마 전환

### Takeaway
움직임을 줄여 달라는 설정에는 **장식은 없애고, 피드백은 페이드로 바꾸는** 것이 정답이다. 움직임을 모두 지우는 것도, 전혀 손대지 않는 것도 답이 아니다. 성능은 `transform`·`opacity` 만 움직이고, `will-change` 는 늘 변하는 요소에만 붙이고, 피드백은 다음 프레임에 보이게(INP ≤200ms) 하면 된다. 원형 리빌 테마 전환은 화면 전체를 크게 움직이는 유행 기법이다. 인쇄물 방향의 사이트에는 200ms 크로스페이드나 즉시 전환이 맞다.

### Cited Findings
- 피드백 애니메이션(장바구니로 날아가는 상품)은 유지하고, 장식(패럴랙스·움직이는 그라데이션·배경 영상)은 줄임 모드에서 제거. JS 애니메이션은 `matchMedia('(prefers-reduced-motion: reduce)')` 의 change 를 듣고 멈춘다. 전정 장애 사용자는 어지럼·메스꺼움·편두통을 겪는다 — [web.dev prefers-reduced-motion](https://web.dev/articles/prefers-reduced-motion)
- 투명도·색 변화는 대체로 안전하고, 큰 이동·방향 불일치·빠른 거리 이동이 위험하다. 애니메이션을 없애라는 게 아니라 목적 · 예고 · 사용자 통제를 주라는 것이다 — [Val Head, A List Apart](https://alistapart.com/article/designing-safer-web-animation-for-motion-sensitivity/)
- Stripe 는 줄임 모드에서 내비 지속 시간 변수들을 `0s` 로 바꾼다(`--navigation-duration:0s` 등). `prefers-reduced-motion` 언급 83건 — 자체 실측(stripe.com CSS)
- "restrict animations to `opacity` and `transform` to keep animations on the compositing stage". `will-change` 는 "use it only if you notice graphics issues", "only add this to elements that are always about to change", 레이어마다 메모리 비용, 끝나면 JS 로 제거 — [web.dev Animations guide](https://web.dev/articles/animations-guide)
- CSS·WAAPI 애니메이션은 메인 스레드가 바빠도 매끄럽다(합성 단계만 쓸 때). 60fps 가 못 되면 나머지는 무의미 — [Emil, Great Animations](https://emilkowal.ski/ui/great-animations)
- 원형 리빌 테마 전환: `startViewTransition` 으로 전후 스냅샷을 뜨고, 새 스냅샷의 `clip-path: circle()` 을 단추 위치에서 화면 먼 구석까지 키운다. 줄임 모드와 미지원 브라우저에서는 즉시 교체로 물러선다 — [Akash Hamirwasia, Full-page theme toggle with View Transitions](https://akashhamirwasia.com/blog/full-page-theme-toggle-animation-with-view-transitions-api/)
- KOSAI 스테이징의 `will-change:transform` 18건은 모두 탭 밑줄(`.ind`, 페이지당 1개)이다 — 자체 확인

### Inferences
- **테마 전환 원형 리빌은 뺀다.** ① 화면 전체를 쓸고 지나가는 큰 움직임이라 Val Head 의 위험 요인(크기·거리)에 해당한다. ② 2023~2025 년 튜토리얼·템플릿에서 퍼진 유행 기법이라 '만든 티'가 난다. ③ 하루 여러 번 누를 수 있는 동작이다(빈도 원칙). 헌장의 `startViewTransition` 200ms 크로스페이드(투명도만)가 안전하면서 번쩍임도 막는다. 없으면 즉시 바꾼다.
- 탭 밑줄 하나에 붙은 `will-change` 는 항상 움직일 수 있는 작은 요소 하나라 web.dev 기준에 맞는 쓰임이다. 목록 행·카드처럼 여러 개에 퍼뜨리지만 않으면 된다.
- 싼 안드로이드 폰에서 무너지는 원인은 대개 스크롤 중 JS(rAF 루프·스크롤 리스너)와 레이아웃을 건드리는 애니메이션이다. KOSAI 는 손가락 기기에서 Lenis 를 끄므로 가장 큰 위험이 이미 빠져 있다. 남은 것은 페이지마다 도는 rAF 루프인데, 데스크톱에서만 돈다.

### Gaps
- 전정 장애 유병률 통계는 1차 출처로 확인하지 못했다(web.dev 도 수치 없음).
- 원형 리빌이 '고급/싸구려'로 지각되는지 잰 자료는 없다. 위 판단은 원칙에서 끌어낸 추론이다.

## 7. 로딩 · 체감 성능 — 스켈레톤, 낙관적 UI, 단계적 드러내기

### Takeaway
1초 안이면 아무것도 보이지 않는 것이 가장 빠르게 느껴진다. 2~10초는 스켈레톤(전체)이나 작은 회전자(부분), 10초가 넘으면 진행 막대를 쓴다. 로딩 표시는 150~300ms 늦게 띄우고, 한 번 뜨면 300~500ms 는 유지해 깜빡임을 막는다. 스켈레톤은 최종 배치와 정확히 같아야 한다(CLS 0).

### Cited Findings
- 1초 미만은 로딩 표시 생략("the quick flashing page can cause users to feel like they can't keep up"). 2~10초는 스켈레톤(전체 페이지)이나 스피너(단일 모듈). 10초 넘으면 진행 막대. 머리·꼬리만 있는 틀뿐인 스켈레톤은 피한다. 반짝임(shimmer)은 체감 대기를 줄일 수 있지만 산만함·접근성 문제가 될 수 있다 — [NN/g Skeleton Screens 101 (Tankala, 2023 · 2026-09 재검토)](https://www.nngroup.com/articles/skeleton-screens/)
- "Minimum loading-state duration" 150~300ms 표시 지연 + 300~500ms 최소 노출, "Stable skeletons… mirror final content exactly to avoid layout shift" — [Vercel Web Interface Guidelines](https://vercel.com/design/guidelines)
- 진행 막대는 정확하지 않아도 기다림을 견딜 만하게 만든다. 처리하는 동안 시선을 붙잡는 요소가 기다림을 가린다 — [Laws of UX, Doherty Threshold](https://lawsofux.com/doherty-threshold/)
- 토스: 20~30초 대출 심사 로딩을 그림 한 장에서 실시간 정보 표시로 바꾸자 이탈률·도달률이 소폭 개선 — [토스 테크](https://toss.tech/article/interaction)

### Inferences
- KOSAI 의 JS 로 그리는 종목 페이지(스테이징 `build_stock_staging.py`)는 데이터 파일을 받는 동안 비어 있다. 여기에는 **최종 배치와 같은 정적 스켈레톤**(회색 막대, 반짝임 없음, 인쇄물 방향)이 맞다. 1초 안에 끝나는 경우가 대부분이라면 300ms 지연 뒤에만 보이게 해야 번쩍이지 않는다.
- 브리핑 생성처럼 10초가 넘는 작업은 사용자 화면에 없으므로 진행 막대가 필요한 자리는 결제(`checkout`) 정도다.
- '단계적 드러내기'(항목을 차례로 페이드 인, stagger)는 목록이 이미 받아져 있는데도 보이는 시점을 늦춘다. 첫 방문 인상 한 번(랜딩)이 아니라면 쓰지 않는다.

### Gaps
- 반짝이는 스켈레톤과 정지 스켈레톤을 비교한 대조 실험은 1차 출처를 찾지 못했다.

### 우선순위 권고

1. **곡선을 먼저 바꾼다(헌장 3.7 수정).** `--ease-out` 을 `(.2,.8,.2,1)` 로 정하고, Carbon standard `(.2,0,.38,.9)` 는 쓰지 않는다. 이름은 ease-out 인데 시작이 CSS 기본 `ease` 보다 느려서, 280ms 시트가 굼뜨게 느껴진다. 스테이징 18곳이 이미 이 값이라 바꿀 것이 거의 없다.
2. **지속 시간을 셋으로 모은다.** 스테이징은 지금 120 · 150 · 180 · 200 · 250 · 300ms 가 섞여 있다. 150 → 120 또는 200, 180(메뉴) → 200, 250 → 200 또는 280, 탭 밑줄 기본 300 → 200. 800ms 6건은 로딩 회전자(`kspin .8s linear infinite`)라 예외로 둔다(헌장 `@keyframes` 화이트리스트의 spin). 헌장 검사 #5(토큰만 허용)를 켤 때 같이 한다.
3. **Lenis 의 rAF 루프를 스크롤할 때만 돌게 고친다.** 지금은 `staging/smooth-scroll.js` 가 페이지 수명 내내 매 프레임 콜백을 돈다. 휠 입력이 오면 시작하고 `lenis.isScrolling` 이 꺼지면 멈추게 한다. 가로채기 비판(#1998)의 성능 쪽 절반을 없앤다.
4. **맥 Safari 에서 Lenis 를 켤지 실기기로 정한다.** README 가 "Safari 60fps 제한"을 밝혀 두었다. 120Hz 맥북 Safari 에서 보통 스크롤과 번갈아 보고, 더 거칠면 Safari 데스크톱에서는 끈다. 아이폰은 이미 꺼져 있다.
5. **페이지 전환을 200ms 로 맞추고 줄임 모드 규칙을 넣는다.** `::view-transition-old(root), ::view-transition-new(root){animation-duration:200ms}` 로 명세 기본 250 을 토큰에 맞춘다. `@media (prefers-reduced-motion: reduce)` 에서는 120ms 또는 `animation:none`. 공유 요소 모핑은 하지 않는다.
6. **줄임 모드는 '없애기 + 페이드로 바꾸기'로 통일한다.** 이동(`transform`)은 120ms 투명도로, 무한 반복은 멈춘다. Lenis 는 이미 꺼져 있다(KOSAI 게이트는 로드 때 한 번 보지만, 1.3.26 자체가 `respectReducedMotion` 으로 설정 변경을 따라간다). 앞으로 넣을 JS 애니메이션은 `matchMedia` 의 change 를 들어야 한다. Stripe 처럼 duration 변수를 `0s` 로 뒤집으면 규칙 한 줄로 끝난다.
7. **관심 종목 담기를 낙관적 UI 로 만든다.** 누르는 순간(다음 프레임) 아이콘을 채우고, Firestore 가 실패하면 되돌리며 알린다. INP 200ms 기준과 0.1s '즉각' 문턱을 둘 다 맞춘다.
8. **테마 전환은 크로스페이드 200ms(투명도만)로 하고 원형 리빌은 금지 목록에 올린다.** 화면 전체를 쓰는 큰 움직임이고, 유행 템플릿 느낌이 나고, 자주 누르는 동작이다.
9. **로딩 규칙을 정한다.** JS 로 그리는 종목 페이지는 300ms 지연 뒤 정지 스켈레톤을 띄우고(최종 배치와 같게, 반짝임 없음), 한 번 뜨면 최소 300ms 유지한다. 1초 안에 끝나면 아무것도 안 보인다.
10. **금지 목록을 검사로 지킨다(헌장 검사 #5 확장).** `transition: all` 0 · `:hover{transform` 0 · 카운트업·IntersectionObserver 리빌 0(지금 0건, 유지) · `@keyframes` 화이트리스트 · 지속 시간은 토큰만. 기억 대신 검사가 막게 한다(저장소 CLAUDE.md 방침).
