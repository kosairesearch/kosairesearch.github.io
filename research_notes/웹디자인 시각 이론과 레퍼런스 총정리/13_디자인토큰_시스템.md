## 1. 토큰 계층과 이름 — 원시 → 시맨틱 → 컴포넌트, 편집형 시스템에 필요한 시맨틱 색의 수, 알파 vs 실색

### Takeaway
큰 시스템은 모두 3층(원시 값 → 의미 → 부품)을 쓰지만, 부품 층은 부품이 많을 때만 값어치가 있다. 색만 놓고 보면 Radix·Geist 가 12단·10단 사다리에 **용도를 박아 넣어**(바탕 / 호버 / 눌림 / 선 / 강한 선 / 채움 / 보조 글자 / 주 글자) 이름만 보고도 쓸 자리를 안다. 편집형·무채색 시스템이라면 시맨틱 색은 **글자 3~4 · 면 3 · 선 2~3 · 등락 2(+배경 2) · 포커스 1** 정도, 대략 15개 안팎이면 충분하다. 알파(농도) 토큰은 흰 카드·종이 바탕 어디서나 같은 규칙이 먹는 장점이 있지만, 이름에 알파 값을 박으면(예: `--ink-55`) 값을 바꾸는 날 이름이 거짓말이 된다.

### Inferences
- 편집형·무채색 사이트는 Radix 12단을 통째로 들일 필요가 없다. 12단의 **용도 칸**만 빌려 오면 된다: 면(1·2·3) = `--bg`·`--surface`·`--surface-2`, 선(6·7·8) = `--hair`·`--line`·`--line-strong`, 글자(11·12) = `--ink-3`·`--ink`. KOSAI 에 없는 칸은 **7~8(대화형 경계·포커스)** 이다 — 입력창 밑줄이 `--line`(1.34:1)뿐이고 포커스 링 토큰이 없다.
- 알파 토큰을 유지하되 이름은 **순서(2·3·4)** 로 바꾸는 것이 낫다. `--ink-55` 를 .62 로 올리는 순간 이름이 거짓이 되고, Radix·Geist 모두 이름에 값이 아니라 단계를 쓴다. 헌장의 `--fg-2/--fg-3` 도 같은 발상이다.
- 부품(component) 토큰 층은 KOSAI 규모(부품 20여 종·작성자 1~2명)에서는 대부분 비용이다. Polaris 처럼 **자주 반복되는 몇 개**(`--control-h`, `--row-pad`, `--measure`)만 두고 나머지는 시맨틱 토큰을 직접 참조하게 하는 편이 추적이 쉽다(추정).
- 알파 대 실색: 알파는 흰 카드와 종이 바탕 위에서 같은 규칙이 먹는다(헌장 논리). 대신 (1) 알파 글자가 겹치면(알파 글자 위에 알파 배경) 대비가 예측 불가, (2) 다크에서 같은 알파 값이 다른 대비를 낸다(`.55` = 라이트 3.99 / 다크 5.47). 그래서 **본문 글자는 실색, 보조·선만 알파**(헌장 방침)가 맞고, 알파 토큰은 라이트·다크 값을 **따로** 정해야 한다.

### Gaps
- Material 3 의 `md.ref/md.sys/md.comp` 층 설명 페이지(m3.material.io)는 이번에 404/빈 페이지여서 원문 인용을 못 했다. 파일 구조로만 확인했다.
- Toss 글은 요약 수준으로만 읽혔다(토큰 개수·정확한 단계 값은 확인 못 함).

## 2. 테마 — `[data-theme]` 변수 · `color-scheme` · `light-dark()` · 시스템 설정 동기화 · 깜빡임 방지

### Takeaway
2024년 이후 표준 무기는 셋이다: (1) `<html data-theme>` 에 **같은 이름의 변수를 두 번** 정의하는 방식(shadcn `.dark`, next-themes `data-theme`), (2) 폼·스크롤바를 맞추는 `color-scheme`, (3) 한 줄에 두 값을 적는 `light-dark()`(Baseline 2024-05). 깜빡임은 **CSS 보다 먼저 도는 head 인라인 스크립트**가 막는다. KOSAI 는 (1)(2)와 인라인 스크립트를 이미 갖췄으므로 `light-dark()` 로 갈아탈 이유는 약하다 — 생성기가 한 사전에서 두 블록을 찍으면 원천은 이미 하나다.

### Cited Findings
- shadcn: 다크 모드는 "같은 토큰을 `.dark` 선택자 안에서 덮어쓴다." 색은 OKLCH(예: 라이트 바탕 `oklch(1 0 0)`, 글자 `oklch(0.145 0 0)`; primary 는 라이트 `oklch(0.205 0 0)` ↔ 다크 `oklch(0.922 0 0)` 으로 뒤집힘) — [shadcn/ui Theming](https://ui.shadcn.com/docs/theming)
- next-themes(Vercel 쪽 사실상 표준 라이브러리) 기능 목록: "prefers-color-scheme 시스템 설정", "color-scheme 로 브라우저 UI 테마", "**로드 시 깜빡임 없음(SSR·SSG 모두)**", "테마 바꿀 때 깜빡임 끄기". 기본은 `<html>` 의 `data-theme` 속성을 바꾼다. 옵션 `enableColorScheme=true`(입력·단추 같은 기본 UI 에 알림), `disableTransitionOnChange`(전환 순간 모든 CSS transition 끄기), CSP 용 `nonce`. v0.0.12 이후 기본 테마는 `system` — [next-themes README](https://github.com/pacocoursey/next-themes/blob/main/next-themes/README.md)
- MDN `light-dark(a, b)`: `color-scheme` 이 **반드시** 설정돼 있어야 하며(`:root{color-scheme:light dark}`), 사용 중인 색 체계가 light 거나 선호가 없으면 첫 값, dark 면 둘째 값. 색과 이미지(`url()`) 둘 다 받는다. 요소별 `color-scheme:light` 로 한 구역만 고정할 수 있다. **Baseline 2024(2024-05부터)** — [MDN light-dark()](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/color_value/light-dark)
- Radix Themes 는 반지름을 `[data-radius='none'|'small'|'medium'|'large'|'full']` 속성의 `--radius-factor`(0 · .75 · 1 · 1.5)로 곱해 테마를 바꾼다 — 속성 하나로 변수 묶음을 갈아끼우는 같은 패턴 — [radix-ui/themes tokens/radius.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/styles/tokens/radius.css)
- Linear 는 3개 입력(base·accent·contrast)에서 테마 전체를 계산한다(1절 참조) — [Linear](https://linear.app/now/how-we-redesigned-the-linear-ui)

**KOSAI 현황 (자체 실측)**
- `comp_common.head()` 가 `<head>` 안에서 `localStorage('kos-theme')`(기본 `'light'`)를 읽어 `data-theme` 을 CSS 전에 심고, `MutationObserver` 로 `theme-color` 메타를 따라 바꾼다. `:root{…color-scheme:light}` / `:root[data-theme="dark"]{…color-scheme:dark}` 로 두 블록 — [scripts/comp_common.py](../../scripts/comp_common.py)
- 기본값이 `'light'` 고정이라 OS 다크 설정을 따르지 않는다. 이는 헌장 결정 2.1(밝은 기본 vs 어두운 기본)에 걸린 문제다 — [헌장 §2.1](../../docs/design/KOSAI-design-charter.md)
- iOS 26 사파리는 `theme-color` 메타를 쓰지 않아 `#kosEdgeTop/Bot` 띠로 푼 이력이 있다(CLAUDE.md 2026-09-24 기록). 테마 기제에서 **메타 태그를 믿지 말 것**의 사내 근거.

### Inferences
- **`light-dark()` 는 이득이 작다.** 이점은 "한 곳에 두 값"인데, KOSAI 는 Python 사전 하나에서 두 블록을 찍으면 같은 효과다. 반면 `light-dark()` 를 쓰려면 `color-scheme` 을 `data-theme` 에 묶는 규칙을 따로 두어야 하고, 알파 값·그림자처럼 색이 아닌 값(그림자 목록 등)은 어차피 두 블록이 필요하다. 옛 모듈 5종(`auth-guard` 등)이 `:root[data-theme=dark] .kg-*` 선택자를 쓰는 것도 속성 방식 유지 쪽 이유다(CLAUDE.md 스테이징 절).
- `data-theme` 가 명시되지 않은 첫 방문에서 OS 설정을 따르게 하려면 인라인 스크립트에 `matchMedia('(prefers-color-scheme:dark)')` 한 줄이면 된다. 다만 기본 테마는 대표 결정(2.1) 사항이므로 **기제는 넣되 기본값은 결정 뒤** 로 두는 것이 안전하다(추정).
- 테마 전환 순간 요소마다 `transition: color` 이 걸려 있으면 화면이 층층이 바뀐다(KOSAI 는 `transition:color .12s` 12곳). next-themes 의 `disableTransitionOnChange` 와 같은 처리(전환 직전 `*{transition:none!important}` 를 한 프레임 넣었다 빼기) 또는 헌장 3.7 의 `startViewTransition` 한 번이 필요하다.

### Gaps
- Vercel·Linear 가 실제로 쓰는 깜빡임 방지 스크립트 원문은 확인하지 않았다(next-themes 가 Vercel 생태계 표준이라는 점만 근거로 삼음).
- `light-dark()` 의 iOS 사파리 최소 버전 숫자는 이번에 원문으로 확인하지 못했다(MDN 은 "Baseline 2024" 로만 표기).

## 3. 값 사다리 — 간격 · 글자 · 반지름 · 그림자 · 모션, 그리고 유동 `clamp()`

### Takeaway
주요 시스템의 간격은 모두 **4px 격자**(Primer 2·4·6·8·12·16·20·24·28·32…, Polaris 1·2·4·6·8·12·16·20·24·32·40·48·64·80·96·112·128, Radix 4·8·12·16·24·32·40·48·64)이고, 작은 쪽은 촘촘하게(2·4·6) 큰 쪽은 성기게(64→80→96) 벌어진다. 반지름은 4·8·12·16 의 4단이 공통 핵심이고, 모션 지속 시간은 50ms 간격 눈금에서 **몇 개만** 쓴다. 글자 크기는 역할+px 이름(Geist `text-copy-16`)이 작은 팀에 가장 읽기 쉽다.

- 글자 크기 18종 → 7~9종 수렴이 토큰화의 가장 큰 효과일 것이다. 다만 12px(52곳)·11px 은 헌장이 "13 아래 크기는 없다"로 정리했으므로, 12→13 전환은 한글 표·차트 라벨이 넘치는지(6절 오버플로 검사)와 짝으로 가야 한다(추정).

- Primer 의 글자 크기 토큰과 Toss 의 간격·글자 사다리 원값은 이번에 확인하지 못했다.
- Geist 문서는 각 클래스의 실제 px 행간·자간 값을 페이지 본문에 싣지 않아 확인하지 못했다.

## 4. 부품 상태 — hover · active · focus-visible · disabled · selected · current, 포커스 링, 터치 목표, "상자 없는" 시스템의 일관성

### Takeaway
상태는 **면 3칸(기본·호버·눌림) + 선 3칸(기본·호버·눌림/포커스)** 으로 사다리에 이미 들어 있다(Radix 3·4·5 / 6·7·8, Geist 100·200·300 / 400·500·600). 포커스는 WCAG 2.4.13 이 "2px 둘레 이상 · 전후 3:1 변화"를 요구하고, Primer 는 2px 을 **포커스 링 전용**으로 못 박았다. 터치 목표는 AA 24px, 권장 44px. 상자·배경 칠이 거의 없는 KOSAI 같은 편집형 시스템은 상태를 **먹의 농도 · 굵기 · 밑줄/표시선**으로 표현하고, 포커스만은 예외 없이 **윤곽선**으로 그린다.

### Cited Findings
- WCAG 2.2 SC 2.4.13 Focus Appearance(AAA): 포커스 표시는 "비포커스 부품의 **2 CSS px 두께 둘레**만큼 이상의 면적" 이고 "포커스·비포커스 상태의 같은 픽셀 사이 대비가 **3:1 이상**". 가장 쉬운 방법은 "부품 둘레의 실선 윤곽", 실무형은 **2px 실선 + offset** — [W3C Understanding 2.4.13](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)
- Primer `borderWidth.thick = 2px`: "MUST use for focus rings on interactive elements. Do NOT use for subtle dividers." `thin`(1px)이 기본 선 — [primer border.json5](https://github.com/primer/primitives/blob/main/src/tokens/functional/size/border.json5)
- Radix: 8단 = "대화형 부품의 강한 선과 **포커스 링**" — [Radix scale](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale); Radix Themes 는 `--focus-*` 를 강조색 사다리에 잇는다 — [radix color.css](https://github.com/radix-ui/themes/blob/main/packages/radix-ui-themes/src/styles/tokens/color.css)
- shadcn 은 포커스 색을 `--ring` 한 토큰으로 둔다 — [shadcn Theming](https://ui.shadcn.com/docs/theming)
- WCAG 2.2 SC 2.5.8 Target Size (Minimum, AA): 포인터 목표는 **24×24 CSS px** 이상. 예외 — 작은 목표라도 각 목표 중심에 지름 24px 원을 놓았을 때 다른 목표·원과 겹치지 않으면 통과, **문장 안 링크** 제외. 중요한 컨트롤은 AAA 2.5.5 의 **44×44** 를 고려하라 — [W3C Understanding 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- Primer 컨트롤 높이: xsmall 24 · small 28 · medium 32 · large 40 · xlarge 48px. `minTarget.fine = 16px`, `minTarget.coarse = 44px` — "거친 포인터 기기에서 터치 접근성을 보장하려면 minTarget 을 쓰라" — [primer functional/size/size.json5](https://github.com/primer/primitives/blob/main/src/tokens/functional/size/size.json5)
- Material 3 상태 층: 호버 8% · 포커스 10% · 눌림 10% 의 **색 덧칠** 방식 — [StateTokens.kt](https://github.com/androidx/androidx/blob/androidx-main/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/StateTokens.kt)
- Geist: 호버 바탕 200 · 눌림 바탕 300 · 호버 선 500 · 눌림 선 600 으로 상태마다 **한 단 이동** — [Geist Colors](https://vercel.com/geist/colors)

**KOSAI 현황 (자체 실측)**
- 생성기 전체에서 `:hover` 56곳, `:focus`·`:focus-within` 7곳(모두 입력창·검색창 밑줄을 `--ink` 로 바꾸는 것), `:focus-visible` **0곳**, `:active` 1곳, `:disabled` 3곳. 단추·링크·탭·아이콘 단추(`.ib`)의 키보드 포커스 표시는 브라우저 기본값에 맡겨져 있다.
- 입력창은 `border-bottom:1px solid var(--line)` — 라이트 1.34:1(`--line` 합성, 자체 계산). 밑줄이 입력창을 알아볼 유일한 단서인 경우 WCAG 1.4.11(비텍스트 3:1)에 걸린다(헌장 3.1 `--line-strong` .44 가 이 칸).
- 헤더 아이콘 단추 `.ib` 38×38px — AA 24px 은 넘고 44px 권장에는 못 미친다.
- 활성 표시는 이미 **먹색 표시선**(`kosInd`: 밑줄·세로선이 `.on` 으로 미끄러짐)과 굵기 600 으로 한다 — 상자 없는 상태 표현의 사내 선례.

### Inferences
- KOSAI 상태 문법 제안(편집형, 칠 없는 쪽):
  - **hover**: 글자 `--ink-2 → --ink`(이미 `.links a` 가 그렇다). 행 단위 목록만 `--surface-2` 바탕 허용.
  - **active(눌림)**: transition 없이 즉시(헌장 3.7). 검은 단추는 `--ink` → `--ink-2` 한 단.
  - **selected / current**: 색이 아니라 **굵기 600 + 표시선 2px `--ink`** + `aria-current`/`aria-selected`. 색만으로 구분하지 않는다.
  - **focus-visible**: 모든 대화형 요소에 `outline:2px solid var(--focus); outline-offset:2px`. `--focus` 는 먹색이면 17.36:1(라이트)·16.42:1(다크)로 3:1 을 넉넉히 넘는다(자체 계산). 검은 단추 위에서는 offset 2px 이 바탕색 틈을 만들어 링이 보인다.
  - **disabled**: `--ink-4`(.30) 글자 + `cursor:not-allowed`. 비활성 부품은 WCAG 1.4.3 대비 예외지만(원문 미확인, Gaps) `--ink-4` 를 **활성 글자**에 쓰면 안 된다.
- `:focus-visible` 0곳은 이번 조사에서 찾은 가장 싼 수정이다. `comp_common.CSS` 한 줄로 22페이지가 같이 고쳐진다.
- 터치: `@media (pointer:coarse)` 에서 `.ib` 등 아이콘 단추의 **누를 수 있는 영역**만 44px 로(보이는 크기는 그대로, `::before` 확장 또는 padding). Primer `minTarget.coarse = 44` 와 같은 발상.

### Gaps
- Apple HIG 의 44pt, Material 의 48dp 권장값은 이번에 원문 페이지를 열지 못했다(Primer·WCAG 2.5.5 의 44 로 대신 근거).
- WCAG 1.4.3 의 "비활성 부품 예외" 원문과, placeholder 글자가 1.4.3 적용 대상인지에 대한 W3C 해석은 이번에 확인하지 못했다. 보수적으로 placeholder 는 4.5:1 을 맞추는 쪽을 권한다(추정).

## 5. 1~2인 팀의 운영 — 단일 원천, 예외 정책, 변경 기록, 디자인 리뷰 체크리스트

### Takeaway
표준 파일 형식(W3C DTCG 2025.10)은 **안정판**이 나왔지만 **테마/모드는 범위 밖**(별도 Resolver 모듈)이다. 플랫폼이 CSS 하나뿐인 KOSAI 에는 Style Dictionary(Node 빌드)가 과하다 — **Python 사전 하나 → CSS 두 블록**으로 이미 단일 원천이 된다. 필요한 것은 도구보다 규칙: 토큰 밖 값 금지 목록, 예외는 사유를 적어 화이트리스트에, 토큰 변경은 CLAUDE.md 식 날짜 기록 + 검사.

### Cited Findings
- W3C Design Tokens Format Module **2025.10**: "Final Community Group Report", 2025-10-28 발행, "안정적인 것으로 간주". 확장자 `.tokens`/`.tokens.json`, MIME `application/design-tokens+json`. 필수 `$value`, 선택 `$type`·`$description`·`$deprecated`·`$extensions`(역도메인 표기). 원시형: color · dimension · fontFamily · fontWeight · duration · cubicBezier · number; 복합형: shadow · border · transition · gradient · typography · strokeStyle. 참조는 `{colors.blue}`(완전한 토큰만 가리킴) 또는 JSON Pointer `$ref`. 그룹 상속 `$extends`. dimension `{"value":16,"unit":"px"}`(px·rem), duration `{"value":200,"unit":"ms"}`, 색 `{"colorSpace":"srgb","components":[…],"alpha":1,"hex":"#0066cc"}`. **테마·모드·실행 중 전환은 다루지 않고 별도 Resolver 모듈로 미룬다** — [designtokens.org TR 2025.10 format](https://www.designtokens.org/tr/2025.10/format/)
- Style Dictionary 는 v4 부터 DTCG 형식을 1급 지원하고, `$value` 가 보이면 `usesDtcg:true` 로 판단한다. 한 인스턴스에 옛 형식(`value`/`type`/`comment`)과 DTCG 형식을 섞을 수 없다 — [Style Dictionary: DTCG](https://styledictionary.com/info/dtcg/) (검색 요약으로 확인); zeroheight 는 토큰 자동화를 Style Dictionary v5 + DTCG 2025.10 으로 올렸다 — [zeroheight help](https://help.zeroheight.com/hc/en-us/articles/48049028236187-Migrating-to-Style-Dictionary-v5-in-tokens-automation) (검색 요약)
- Primer 는 각 토큰에 `$description` 과 사용 규칙(`rules`)을 `$extensions` 로 붙여 **문서를 토큰 파일 안에** 둔다(예: 컨트롤 크기 "dense UI 는 xsmall/small, 표준 폼 medium, 눈에 띄는 CTA 는 large/xlarge") — [primer functional/size/size.json5](https://github.com/primer/primitives/blob/main/src/tokens/functional/size/size.json5)
- Toss 는 Figma Token Studio 에서 디자이너가 커밋하면 웹·React Native·iOS·Android 코드가 자동 생성되게 했다 — 여러 플랫폼이라 자동화가 값어치 있었던 경우 — [toss.tech](https://toss.tech/article/tds-color-system-update)
- Linear 는 98개 변수를 3개 입력으로 줄였다 — 관리 대상 수를 줄이는 것이 곧 거버넌스 — [Linear](https://linear.app/now/how-we-redesigned-the-linear-ui)

**KOSAI 사내 선례**
- 이 저장소는 이미 "기억 대신 검사" 원칙으로 돈다: `patch_light_palette.py --check`(옛 색 복귀 차단), "스테이징 생성기 = 저장소" 검사, `same-paragraphs.test.mjs` 등 — [CLAUDE.md](../../CLAUDE.md)
- 헌장 3장은 "토큰 블록은 한 스크립트가 심고 `--check` 가 지킨다", "폐기 토큰 참조 0건" 검사, 글자 크기 화이트리스트(검사 #3)를 이미 계획했다 — [헌장 §3](../../docs/design/KOSAI-design-charter.md)

### Inferences
- **단일 원천 = `comp_common.py` 안의 Python 사전 `TOKENS`.** 구조는 `{"ink-3": {"light": "rgba(20,20,20,.62)", "dark": "rgba(236,236,234,.60)", "use": "메타·캡션", "min_contrast": 4.5}}`. 여기서 (1) `:root` · `:root[data-theme=dark]` 두 블록, (2) 대비 검사 입력, (3) 사람이 읽는 토큰 표(docs)를 모두 찍는다. `use`·`min_contrast` 는 Primer 의 `$description`/`rules` 역할.

### Gaps

## 6. QA — 스크린샷 차이 · 토큰 린트 · 자동 대비 · 한글 넘침 · 다크 행렬, 작은 팀이 실제로 돌릴 수 있는 것

### Takeaway
작은 팀에서 가장 값싼 순서는 **정적 검사(Python, 밀리초) → 계산된 스타일 비교(브라우저 1회) → 픽셀 스크린샷(환경 고정 필요)** 이다. Playwright 공식 문서도 픽셀 비교는 "OS·버전·설정·하드웨어·전원·headless 여부"로 달라진다며 **같은 환경**에서 돌리라고 한다. 자동 접근성 검사는 "일부 문제만" 잡는다. 따라서 픽셀 스크린샷은 적은 수의 대표 화면에만, 대비는 토큰 표에서 계산으로 전수 검사하는 것이 맞다.

### Cited Findings
- Playwright `await expect(page).toHaveScreenshot()`: 첫 실행에 기준 이미지를 만들고 이후 비교. 기준 파일 이름에 브라우저·플랫폼(`chromium-darwin` 등)이 붙는다. "브라우저 렌더링은 호스트 OS, 버전, 설정, 하드웨어, 전원(배터리 대 어댑터), headless 모드 등에 따라 달라질 수 있다" → 기준을 만든 환경에서 돌려라. 옵션 `maxDiffPixels`, 변하는 요소를 가리는 `stylePath`, 갱신 `--update-snapshots`; 이미지 아닌 값은 `toMatchSnapshot()` — [Playwright: Visual comparisons](https://playwright.dev/docs/test-snapshots)
- `@axe-core/playwright` 의 `AxeBuilder().withTags(['wcag2a','wcag2aa','wcag21a','wcag21aa'])`, `include()/exclude()`, `disableRules()`. "자동 접근성 검사는 흔한 문제 일부를 잡을 수 있지만 많은 문제는 수동 검사로만 발견된다." `exclude()` 한 요소는 모든 규칙에서 빠진다 — [Playwright: Accessibility testing](https://playwright.dev/docs/accessibility-testing)
- Radix 는 글자 단계의 대비를 **APCA**(Lc 60 / Lc 90)로 보장한다 — 사다리를 설계할 때 대비를 계산으로 못 박는 선례 — [Radix scale](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale)
- Linear 는 contrast 입력 하나로 고대비 테마를 자동 생성 — 대비를 사람 눈이 아니라 계산에 맡긴 예 — [Linear](https://linear.app/now/how-we-redesigned-the-linear-ui)

**KOSAI 현황 (자체 실측)**
- `staging/tests/` 에 `layout.test.mjs`(Playwright 레이아웃), `same-*`·`invariants`·`reports-filter` 등 11개. 저장소 어디에도 `toHaveScreenshot`/`maxDiffPixel` 사용은 없다 — 픽셀 회귀 검사는 아직 없다.
- 이미 있는 강력한 가드: "스테이징 생성기 = 저장소"(생성기 출력이 커밋과 바이트 동일) — 토큰 리팩터링에서 **의도치 않은 변화의 1차 탐지기**.
- 현재 토큰의 대비 미달 3건(자체 계산): 라이트 `--ink-55` 3.99:1(11~13px 글자 85곳), `--ink-30` 1.96:1(절 번호·목차 번호·placeholder), 입력 밑줄 `--line` 1.34:1.

### Inferences
- **대비 검사는 브라우저가 아니라 토큰 표에서** 한다: `TOKENS` 의 글자 토큰 × 바탕 토큰(`--bg`·`--surface`·`--surface-2`, 라이트·다크) 조합을 알파 합성 후 계산해 `min_contrast` 와 비교. 12개 조합 정도라 밀리초. axe 는 페이지 위 실제 겹침(알파 위 알파, 이미지 위 글자)을 잡는 2차 그물.
- **토큰 린트는 stylelint 대신 Python 정규식**이 이 저장소에 맞다: CSS 가 `.css` 파일이 아니라 Python 문자열 안에 있어 stylelint 를 붙이려면 먼저 추출해야 한다. 규칙 넷 — ① `#hex`·`rgb(a)` 는 토큰 블록 밖 금지 ② `font-size`/`font:` 크기는 화이트리스트 ③ `border-radius` 화이트리스트 ④ `transition` 시간 화이트리스트 + `transition:all` 금지(헌장 3.7). 예외는 5절 주석 방식.
- **계산된 스타일 스냅샷**이 픽셀보다 작은 팀에 맞다: Playwright 로 페이지 × 테마마다 대표 선택자(본문 `p`, `.sec-h`, 표 `td`, 단추, 링크, 입력창)의 `getComputedStyle` 값(색·글자 크기·행간·반지름·outline)을 JSON 으로 떠 `toMatchSnapshot()`. OS·글꼴 래스터 차이에 흔들리지 않고, "이름만 바꾼 PR 은 값이 0 개 바뀌어야 한다"를 정확히 검사한다.
- **픽셀 스크린샷은 작은 행렬만**: 대표 6화면(Home · 종목 · 리포트 목록 · 브리핑 · 요금제 · 설정) × 라이트/다크 × 390px/1280px = **24장**, GitHub Actions 리눅스 한 환경에서만 기준 생성, `animations:'disabled'`, 가격·날짜 같은 변하는 숫자는 `mask`, `document.fonts.ready` 대기. 2,682 종목 페이지는 등급 셋(v2·v1·준비 중)에서 한 장씩만.
- **한글 넘침 검사**(출처 없음, 사내 필요): 320·390px 에서 `document.documentElement.scrollWidth > clientWidth` 이면 실패, 모든 요소에 대해 `scrollWidth > clientWidth + 1` 이고 `overflow` 가 `visible` 인 것 목록화. 입력 데이터에 가장 긴 종목명·업종명·영문 회사명을 넣은 **극단 픽스처** 페이지를 하나 만든다. `word-break:keep-all` 은 한 단어가 칸보다 길면 넘치므로 `overflow-wrap:anywhere` 가 짝으로 있는지도 본다(현재 `body` 에 있음).
- **실기기 확인**은 자동화 불가 항목으로 남긴다 — iOS 사파리 가장자리 색 문제처럼(CLAUDE.md) 이 환경에 없는 브라우저의 버그가 이미 한 번 있었다.

### Gaps
- APCA 가 WCAG 2.x 적합성 판정 방법이 아니라는 점, WCAG 3 에서의 채택 여부는 이번에 원문으로 확인하지 못했다. 법적·표준 기준은 WCAG 2.x 비율(4.5·3)로 두고 APCA 는 참고로만 쓰는 것을 권한다(추정).
- `stylelint-declaration-strict-value` 등 토큰 린트 플러그인 문서는 받아오지 못했다(저장소 경로 불일치).
- 스크린샷 비교 도구(Chromatic·Percy·Argos 등) 비용 비교는 범위 밖으로 두었다.

## 7. 마이그레이션 — CSS 문자열 생성기에 토큰 층을 넣되 페이지가 뜻하지 않게 바뀌지 않게

### Takeaway
두 단계로 나눈다: **① 이름만 바꾸는 PR(값 변화 0)** → **② 값을 바꾸는 PR(한 번에 한 결정)**. ①은 "생성기 출력 = 저장소" 와 계산된 스타일 스냅샷이 "0 개 바뀜"을 증명하고, ②는 스크린샷 차이를 사람이 승인한다. 옛 이름은 별칭으로 한 릴리스 남기고, 참조 수를 세는 검사가 0 으로 끌어내린다. Toss 도 7년 만의 개편을 **별칭으로 하위 호환을 지키며 주요 서비스부터 단계적으로** 굴렸다.

### Cited Findings
- Toss: "별칭(aliasing)으로 하위 호환을 유지하고, 핵심 서비스에서 먼저 시험한 뒤 모노레포로 체계적으로 굴렸다." "기초 문제를 먼저 완전히 풀고 넓힌다" — [toss.tech](https://toss.tech/article/tds-color-system-update)
- DTCG `$deprecated`(불리언 또는 사유 문자열)로 폐기 예정 토큰을 표시할 수 있다 — [DTCG 2025.10](https://www.designtokens.org/tr/2025.10/format/)
- 헌장 3.8 은 이미 "옛 이름 → 새 이름, 별칭 한 릴리스 유지, 참조는 같은 실행에서 치환, `--check` 가 폐기 토큰 참조 0건을 본다" 는 방식을 정했다(옛 실사이트 기준: `--border-2` 220건 · `--brand-cyan` 88건 · `--radius-xl` 72건) — [헌장 §3, §3.8](../../docs/design/KOSAI-design-charter.md)
- `comp_common.py` 에는 이미 별칭 다리가 있다: `--fg-1:var(--ink)` `--fg-2:var(--ink-72)` `--fg-3:var(--ink-55)` `--bg-1:var(--surface)` `--border-2:var(--line)` `--brand-blue:var(--ink)` `--radius-sm/md/lg:8/12/16px` … — "모듈을 새 이름으로 고칠 때까지의 다리". 실사이트와 같아야 하는 모듈 5종(`social-login` `auth-util` `auth-guard` `auth-emails` `consent`)은 손대지 않는다(`auth-table.test.mjs`) — [comp_common.py](../../scripts/comp_common.py), [CLAUDE.md 스테이징 절](../../CLAUDE.md)

### Inferences
- **이름 충돌을 먼저 푼다.** 생성기의 `--bg`(페이지)·`--surface`(카드) ↔ 헌장의 `--bg-1`(페이지)·`--bg-2`(카드), 그리고 **별칭 다리의 `--bg-1:var(--surface)`(카드!)** 가 서로 다른 뜻이다. 옛 모듈에서 `--bg-1` 은 "표면"으로 쓰였고 헌장은 "페이지 바탕"으로 재정의했다. 실사이트로 옮기는 날(`set_mode('live')`) 이 둘이 부딪히므로, **생성기 이름(`--bg`/`--surface`/`--ink`)을 정본**으로 하고 헌장 3장의 이름표를 생성기 이름으로 고쳐 쓰는 편이 참조 수(생성기 쪽 색 토큰 ~440)로 보나 의미 명료성으로 보나 싸다(추정). 옛 모듈용 `--fg-*`/`--bg-1` 다리는 모듈 5종이 실사이트와 함께 바뀌는 날까지 유지.
- 순서(각 단계 = PR 하나):
  1. **기준 고정** — 22페이지 × 2테마의 계산된 스타일 스냅샷을 만든다(6절). 생성기 출력은 이미 저장소에 고정돼 있다.
  2. **`TOKENS` 사전 도입** — 지금 `CSS` 문자열의 `:root` 두 블록을 사전에서 찍도록 바꾼다. 값 동일 → 생성기 출력 **바이트 동일**이어야 한다(가장 강한 증명).
  3. **새 이름 추가 + 옛 이름 별칭** — `--ink-2`/`--ink-3`/`--ink-4` 를 새로 두고 `--ink-72:var(--ink-2)` 식으로 옛 이름을 잇는다. 계산된 스타일 0 변화.

### B. 테마 방식

1. **정본은 `comp_common.py` 의 Python 사전 `TOKENS`** — 토큰마다 `light` · `dark` · `use` · `min_contrast`(글자·선만). 여기서 `:root{…;color-scheme:light}` 와 `:root[data-theme="dark"]{…;color-scheme:dark}` 두 블록, 대비 검사 입력, 토큰 표 문서, (선택) DTCG `tokens.json` 을 모두 찍는다. `stock_page.py` 의 `PAGE_CSS` 도 이 사전을 쓴다.
2. **`[data-theme]` 속성 방식 유지, `light-dark()` 는 쓰지 않는다** — 원천이 이미 하나이고, 알파·그림자·옛 모듈의 `:root[data-theme=dark] .kg-*` 규칙이 속성 방식에 묶여 있다(2절).
3. **깜빡임 방지 스크립트는 지금 자리(head, CSS 앞) 유지.** 여기에 (a) 저장값이 없으면 `matchMedia('(prefers-color-scheme:dark)')` 를 보는 분기를 넣되 **기본값은 결정 2.1 뒤에 켠다**, (b) `theme-color` 메타 동기화는 다른 브라우저용으로 유지, iOS 26 은 `#kosEdgeTop/Bot` 띠(CLAUDE.md).
4. **전환 순간**: 요소별 `transition:color` 이 층층이 바뀌지 않게 `document.startViewTransition` 200ms 한 번(헌장 3.7), 지원 안 되면 전환 직전 한 프레임 `transition:none`(next-themes `disableTransitionOnChange` 방식).
5. **다크는 밝기로 층을 만든다** — `--surface`·`--surface-2` 를 한 단씩 밝게, 그림자는 `none`(Radix `panel-solid = gray-2`, 헌장 3.5).
